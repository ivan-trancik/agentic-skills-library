Scope note: verified against official docs fetched on 2026-10-07 and against the binaries installed on this machine (Codex CLI 0.160.1 via Homebrew cask at `/opt/homebrew/Caskroom/codex/0.160.1/bin/codex`; Claude Code 2.1.292 at `~/.local/share/claude/versions/2.1.292`). Two empirical probes were run (see Key Question 2). OpenAI's Codex docs under `developers.openai.com/codex/...` now return HTTP 308 redirects to `learn.chatgpt.com/docs/...`; both URLs are given where that happened. ## Key Question 1: The Agent Skills open standard (agentskills.io)

### Takeaway
The spec is small and stable: a `SKILL.md` with six defined front-matter keys (`name`, `description`, `license`, `compatibility`, `metadata`, `allowed-tools`), a recommended `scripts/`, `references/`, `assets/` layout, three-tier progressive disclosure, a 500-line / under-5,000-token guideline for `SKILL.md`, relative file references one level deep, and a Python reference library (`skills-ref`) for validation. It was opened as a standard by Anthropic on 18 December 2025 and the site's Client Showcase lists about 47 products, including Claude Code, ChatGPT and Codex, Cursor, Gemini CLI, GitHub Copilot, VS Code, OpenCode, Goose, Factory, Amp and JetBrains Junie.

### Cited Findings
- Directory layout: "A skill is a directory containing, at minimum, a `SKILL.md` file", with optional `scripts/` ("executable code"), `references/` ("documentation"), `assets/` ("templates, resources") and "Any additional files or directories" — [Agent Skills Specification](https://agentskills.io/specification)
- Front-matter table: `name` (required, "Max 64 characters. Lowercase letters, numbers, and hyphens only. Must not start or end with a hyphen."), `description` (required, "Max 1024 characters. Non-empty. Describes what the skill does and when to use it."), `license` (optional), `compatibility` (optional, "Max 500 characters. Indicates environment requirements (intended product, system packages, network access, etc.)"), `metadata` (optional, "Arbitrary key-value mapping ... a map from string keys to string values"), `allowed-tools` (optional, "Space-separated string of pre-approved tools the skill may use. (Experimental)") — [Agent Skills Specification](https://agentskills.io/specification)
- Additional `name` rules: "Must not contain consecutive hyphens (`--`)" and "Must match the parent directory name"; invalid examples `PDF-Processing`, `-pdf`, `pdf--processing` — [Agent Skills Specification](https://agentskills.io/specification)
- `description` guidance: "Should describe both what the skill does and when to use it" and "Should include specific keywords that help agents identify relevant tasks" — [Agent Skills Specification](https://agentskills.io/specification)
- `compatibility`: "Should only be included if your skill has specific environment requirements"; examples `compatibility: Designed for Claude Code (or similar products)` and `compatibility: Requires git, docker, jq, and access to the internet`; note "Most skills do not need the `compatibility` field." — [Agent Skills Specification](https://agentskills.io/specification)
- `metadata`: "Clients can use this to store additional properties not defined by the Agent Skills spec. We recommend making your key names reasonably unique to avoid accidental conflicts" — [Agent Skills Specification](https://agentskills.io/specification)
- `allowed-tools` example: `allowed-tools: Bash(git:*) Bash(jq:*) Read`; "Experimental. Support for this field may vary between agent implementations" — [Agent Skills Specification](https://agentskills.io/specification)
- Body: "There are no format restrictions"; recommended sections are step-by-step instructions, examples, edge cases; "the agent will load this entire file once it's decided to activate a skill. Consider splitting longer `SKILL.md` content into referenced files." — [Agent Skills Specification](https://agentskills.io/specification)
- Progressive disclosure tiers: "**Metadata** (~100 tokens): The `name` and `description` fields are loaded at startup for all skills", "**Instructions** (< 5000 tokens recommended): The full `SKILL.md` body is loaded when the skill is activated", "**Resources** (as needed)"; "Keep your main `SKILL.md` under 500 lines." — [Agent Skills Specification](https://agentskills.io/specification)
- File references: "use relative paths from the skill root" and "Keep file references one level deep from `SKILL.md`. Avoid deeply nested reference chains." — [Agent Skills Specification](https://agentskills.io/specification)
- Validation: "Use the skills-ref reference library to validate your skills: `skills-ref validate ./my-skill`. This checks that your `SKILL.md` frontmatter is valid and follows all naming conventions." — [Agent Skills Specification](https://agentskills.io/specification)
- `skills-ref` is a Python "Reference library for Agent Skills", Apache 2.0, with CLI commands `skills-ref validate path/to/skill`, `skills-ref read-properties path/to/skill` (JSON metadata) and `skills-ref to-prompt path/to/skill-a path/to/skill-b` (generates an `<available_skills>` XML block), plus Python functions `validate()`, `read_properties()`, `to_prompt()` — [agentskills/agentskills skills-ref](https://github.com/agentskills/agentskills/tree/main/skills-ref)
- The site's page index lists: Overview, Specification, Client Showcase, Quickstart, "Best practices for skill creators", "Optimizing skill descriptions", "Evaluating skill output quality", "Using scripts in skills", and "How to add skills support to your agent" — [agentskills.io llms.txt](https://agentskills.io/llms.txt)
- Client-implementation guidance (what agents are told to do): tier table "1. Catalog: Name + description, Session start, ~50-100 tokens per skill; 2. Instructions: Full SKILL.md body, When the skill is activated, <5000 tokens (recommended); 3. Resources" — [How to add skills support to your agent](https://agentskills.io/client-implementation/adding-skills-support.md)
- Same guide on paths: scan both "a **client-specific directory** and the **`.agents/skills/` convention**" at project and user scope; "The `.agents/skills/` paths have emerged as a widely-adopted convention for cross-client skill sharing. While the Agent Skills specification does not mandate where skill directories live (it only defines what goes inside them), scanning `.agents/skills/` means skills installed by other compliant clients are automatically visible to yours"; "Some implementations also scan `.claude/skills/` (both project-level and user-level) for pragmatic compatibility" — [How to add skills support to your agent](https://agentskills.io/client-implementation/adding-skills-support.md)
- Same guide on collisions and trust: "The universal convention across existing implementations: **project-level skills override user-level skills.**"; "Consider gating project-level skill loading on a trust check" — [How to add skills support to your agent](https://agentskills.io/client-implementation/adding-skills-support.md)
- Same guide on lenient parsing: name not matching directory or over 64 chars → "warn, load anyway"; missing description → "skip the skill"; recommends a fallback for unquoted colons in `description` — [How to add skills support to your agent](https://agentskills.io/client-implementation/adding-skills-support.md)
- Same guide on catalog format and opt-out: `<available_skills><skill><name>…</name><description>…</description><location>/home/user/.agents/skills/pdf-processing/SKILL.md</location></skill></available_skills>`; filter out skills that have "opted out of model-driven activation (e.g., via a `disable-model-invocation` flag)" and "Hide filtered skills entirely from the catalog"; user-explicit activation is "a **slash command or mention syntax** (`/skill-name` or `$skill-name`)"; "Subagent delegation (optional) ... only supported by some clients" — [How to add skills support to your agent](https://agentskills.io/client-implementation/adding-skills-support.md)
- Announcement date and content: on December 18, 2025 Anthropic "announced making its Agent Skills specification an open standard", alongside org-wide management for Team/Enterprise plans and "a directory featuring 'partner-built skills'" from Atlassian, Canva, Notion, Figma, Cloudflare, Stripe and Zapier — [SiliconANGLE, 2025-12-18](https://siliconangle.com/2025/12/18/anthropic-makes-agent-skills-open-standard/)
- Search-result summary (article body could not be fetched) of The New Stack's coverage: "Anthropic published Agent Skills as an open standard on December 18, releasing the specification and SDK at agentskills.io" and "Microsoft, OpenAI, Atlassian, Figma, Cursor, and GitHub have already adopted the standard" — [The New Stack](https://thenewstack.io/agent-skills-anthropics-next-bid-to-define-ai-standards/) (snippet-level evidence only)
- Client Showcase entries (each with a docs link): Claude Code (code.claude.com/docs/en/skills), Claude (platform docs), "ChatGPT & Codex" (developers.openai.com/codex/skills/), Cursor (cursor.com/docs/context/skills), Gemini CLI (geminicli.com/docs/cli/skills/), GitHub Copilot (docs.github.com .../about-agent-skills), VS Code (code.visualstudio.com/docs/copilot/customization/agent-skills), OpenCode (opencode.ai/docs/skills/), Goose, Factory (docs.factory.ai/cli/configuration/skills), Amp (ampcode.com/manual#agent-skills), JetBrains Junie (junie.jetbrains.com/docs/agent-skills.html), OpenHands, Roo Code, Kiro, Mistral Vibe, TRAE, Letta, Firebender, Mux, Emdash, Superconductor, pi, Piebald, Databricks Genie Code, Snowflake Cortex Code, Pulumi Neo, Tabnine, Qodo, Laravel Boost, Spring AI, Hermes Agent, OpenClaw, nanobot, fast-agent, bub, ZeroClaw, Autohand, Command Code, Ona, VT Code, Workshop, Google AI Edge Gallery, Vita, Deep Code, Agentman — [Client Showcase](https://agentskills.io/clients.md)

### Inferences
- The six spec fields are the only portable ones; everything else (Claude Code's `disable-model-invocation`, Codex's `agents/openai.yaml`) is a harness extension layered beside the spec rather than inside it. A skill that must be uploadable to claude.ai or validated by Codex's `quick_validate.py` must keep its front matter to the spec set (see Key Questions 3 and 6).
- Nothing new has been added to the front-matter table since launch that I could find: the fetched spec page lists exactly the six fields above, and both harnesses' docs still refer to the same set.

### Gaps
- No dedicated "changelog" page exists on agentskills.io (the llms.txt index has none), so I could not date individual spec revisions.
- The New Stack article body did not load; the launch-adopter list (Microsoft, OpenAI, Cursor, GitHub) rests on a search snippet plus the Client Showcase, not on the article text.
- I did not fetch agentskills.io's own "Best practices", "Optimizing skill descriptions" or "Evaluating skill output quality" pages; Anthropic's platform best-practices page (Key Question 6) covers the same material.

## Key Question 2: Discovery paths as of late 2026 (Claude Code 2.1.292 and Codex CLI 0.160.1)

### Takeaway
Claude Code reads `~/.claude/skills`, project `.claude/skills` (including parent directories up to the repo root and nested subdirectories on demand), managed-settings `.claude/skills`, `--add-dir` directories, plugin `skills/`, and `~/.claude/skills/synced`; it follows symlinked skill folders but does **not** read `~/.agents/skills` (confirmed by a probe). Codex reads `.agents/skills` in the cwd, its parents and the repo root, `~/.agents/skills`, `/etc/codex/skills`, bundled system skills, and (still, by probe) `~/.codex/skills`; it follows symlinks and has no `codex skills` subcommand.

### Cited Findings
Claude Code
- Locations and priority: "Enterprise" (`.claude/skills/<skill-name>/SKILL.md` in the managed settings directory), "Personal" (`~/.claude/skills/<skill-name>/SKILL.md`), "Project" (`.claude/skills/<skill-name>/SKILL.md`), "Nested" (`<subdir>/.claude/skills/...`, accessible as `/path:skill-name` on a clash), "Additional Directory" (`--add-dir`), "Plugin" (`<plugin>/skills/<skill-name>/SKILL.md` or `<plugin>/SKILL.md`, loaded as `/plugin-name:skill-name`), and claude.ai synced skills downloaded to `~/.claude/skills/synced/` — [Claude Code: Skills](https://code.claude.com/docs/en/skills)
- Parent and nested directories: "Claude Code loads project skills from `.claude/skills/` in the directory where you start it and in every parent directory up to the repository root" and "Skills in a `.claude/skills/` directory below where you started don't load at startup. They load the first time Claude reads or edits a file in that subdirectory" — [Claude Code: Skills](https://code.claude.com/docs/en/skills)
- Symlinks: supported "in enterprise, personal, and project locations; symlink target's `SKILL.md` loads once even if multiple locations link to it" — [Claude Code: Skills](https://code.claude.com/docs/en/skills)
- Local confirmation of symlink following: `ls -la ~/.claude/skills` shows `apply-review -> ~/.agents/skills/apply-review` (and five siblings), and all six appear in this session's available-skills list by their plain names (local observation, `~/.claude/skills`)
- Reserved names: `synced` (any capitalization) and `anthropic-skills` / `anthropic-skills:*` — [Claude Code: Skills](https://code.claude.com/docs/en/skills)
- Relation to `.claude/commands/`: "A file at `.claude/commands/deploy.md` and a skill at `.claude/skills/deploy/SKILL.md` both create `/deploy` and work the same way. Your existing `.claude/commands/` files keep working. Skills add optional features: a directory for supporting files, frontmatter to control whether you or Claude invokes them, and the ability for Claude to load them automatically when relevant."; command files "support same frontmatter as skills except `name` and `paths`"; on a name clash "Skill wins" over a command file — [Claude Code: Skills](https://code.claude.com/docs/en/skills)
- Name resolution: "Enterprise > personal > project"; a user skill "replaces bundled"; plugin skills load alongside as `/plugin:name`; synced skills lose the short name to a local skill and run as `/anthropic-skills:name` — [Claude Code: Skills](https://code.claude.com/docs/en/skills)
- Live change detection: "When you add, edit, or remove a skill under `~/.claude/skills/`, the project `.claude/skills/`, or a `.claude/skills/` inside an `--add-dir` directory, Claude Code picks up the change within the current session, without a restart"; a newly created top-level skills directory needs `/reload-skills`; plugin changes need `/reload-plugins` — [Claude Code: Skills](https://code.claude.com/docs/en/skills)
- Does Claude Code read `~/.agents/skills`? Not according to the docs (no such location is listed) — [Claude Code: Skills](https://code.claude.com/docs/en/skills). Probe on this machine: a skill at `~/.agents/skills/zz-probe-agentsdir/SKILL.md` with no symlink in `~/.claude/skills`; `claude -p "/zz-probe-agentsdir"` answered "`/zz-probe-agentsdir` isn't installed in this session, so it didn't run", and `claude -p` asked to list skills starting with `zz-` answered `NONE` (local experiment, Claude Code 2.1.292). The literal strings `.agents/skills` and `.agents/skills/` do exist inside the 2.1.292 binary (`strings` on `~/.local/share/claude/versions/2.1.292`), but no discovery behaviour was observed.
- Skills-directory plugins: a plugin "You saved ... that has a `.claude-plugin/plugin.json` under `~/.claude/skills/` or the project's `.claude/skills/`" loads with id `<name>@skills-dir`; `claude plugin init <name>` scaffolds "a new plugin at ~/.claude/skills/<name>/ (auto-loads next session as <name>@skills-dir)" — [Plugin loading reference](https://code.claude.com/docs/en/plugins/loading); `claude plugin --help` (local, 2.1.292)
- A project-scope skills-directory plugin "loads only from the `.claude/skills/` of the session's primary working directory" and "doesn't search parent directories up to the repository root the way plain skills and commands do" — [Plugin loading reference](https://code.claude.com/docs/en/plugins/loading)
- Historical caution for installers: "Before v2.1.280, a file named `manifest.json` in `~/.claude/skills/` caused Claude Code to move the skill folders that file listed into a timestamped folder under `~/.claude/skills/.trash/`" — [Claude Code: Skills](https://code.claude.com/docs/en/skills)

### Inferences
- The project's layout (copy to `~/.agents/skills/<name>`, symlink from `~/.claude/skills/<name>`) is exactly what both harnesses need today: Codex reads `~/.agents/skills` natively and Claude Code needs the symlink, which it follows. The probe rules out dropping the symlink.
- Because Codex also still scans `~/.codex/skills` and Claude Code scans `~/.claude/skills`, a same-named skill placed in either legacy location would shadow or duplicate the installed one; the installer only checks `~/.agents/skills/<name>` and `~/.claude/skills/<name>`.
- `.agents/skills` in a project is read by Codex (parents up to repo root) but ignored by Claude Code, which reads `.claude/skills`; a project-level cross-agent install needs both directories (the Vercel CLI's symlink layout does this).

### Gaps
- Codex docs do not state the precedence between `~/.codex/skills` and `~/.agents/skills` or whether same-named skills in both are de-duplicated; not tested.
- Claude Code's binary contains the `.agents/skills` string but no doc or changelog entry (first 100k characters of the CHANGELOG, versions 2.1.286–2.1.292) explains it; the probe shows it is not a user-level discovery path in 2.1.292.
- Whether Codex gates repo-level `.agents/skills` on project trust (`trust_level`) was not verified.

## Key Question 3: Front-matter and behaviour options per harness

### Takeaway
Claude Code accepts all six spec fields plus a large set of its own (`disable-model-invocation`, `user-invocable`, `when_to_use`, `allowed-tools`/`disallowed-tools`, `context: fork` + `agent` + `background`, `model`, `effort`, `argument-hint`/`arguments`, `hooks`, `paths`, `shell`), with `$ARGUMENTS`, `${CLAUDE_SKILL_DIR}` and `!`command`` substitution. Codex keeps `SKILL.md` to spec fields (plus `metadata.short-description`) and puts harness behaviour in `agents/openai.yaml` (`interface.*`, `policy.allow_implicit_invocation`, `dependencies.tools`). To stop `ship` being auto-invoked: `disable-model-invocation: true` in Claude Code and `policy: allow_implicit_invocation: false` in `agents/openai.yaml` for Codex. A reviewer that must run in a forked context is `context: fork` with `agent:` in Claude Code; Codex has no skill-level equivalent (the `review-agent` system skill is delegated to by other agents, not forked by front matter).

### Cited Findings
Claude Code front matter
- "All fields optional; field names use lowercase with hyphens (except `when_to_use`). Frontmatter must start at file's first line between `---` markers." Booleans accept `yes/no/on/off/1/0/true/false` — [Claude Code: Skills](https://code.claude.com/docs/en/skills)
- Core: `name` (defaults to directory name), `description` (recommended; "Claude uses this for auto-invocation; truncated at 1,536 chars (combined with `when_to_use`)"), `when_to_use` ("Additional context for auto-invocation (trigger phrases, example requests); appended to description"), `argument-hint` (e.g. `[issue-number]`), `arguments` (named positional args for `$name`) — [Claude Code: Skills](https://code.claude.com/docs/en/skills)
- Invocation control table: default = "You invoke: Yes / Claude invokes: Yes / Description in context: Always"; `disable-model-invocation: true` = "Yes / Not auto / Not included"; `user-invocable: false` = "No / Yes / Always" — [Claude Code: Skills](https://code.claude.com/docs/en/skills)
- `disable-model-invocation`: "Prevents Claude from loading skill automatically; manual invocation only" and "Claude Code blocks attempt to reproduce skill steps another way, instructing Claude not to." `user-invocable: false`: "Only Claude can invoke; hidden from `/` menu" (for background knowledge) — [Claude Code: Skills](https://code.claude.com/docs/en/skills)
- Tools: `allowed-tools` ("Tools pre-approved without prompting during turn skill invokes; grant clears on next message", e.g. `Bash(git add *)`, `Skill(commit)`), `disallowed-tools` ("Tools removed from Claude's pool while skill active") — [Claude Code: Skills](https://code.claude.com/docs/en/skills)
- Model and effort: `model` ("applies for current turn only"), `effort` (`low|medium|high|xhigh|max`) — [Claude Code: Skills](https://code.claude.com/docs/en/skills)
- Execution context: `context: fork` ("run in isolated subagent context"), `agent` (subagent type, e.g. `Explore`, `Plan`, `general-purpose`; default `general-purpose`), `background` ("With `context: fork`, set to `false` to wait for result; otherwise runs in background", default `true` since v2.1.218) — [Claude Code: Skills](https://code.claude.com/docs/en/skills)
- `context: fork` semantics: "Claude Code starts a new subagent of the type set in the `agent` field and gives it the skill content as its prompt. The subagent doesn't see your conversation history, so the skill's instructions have to stand on their own."; backgrounded forks use "narrower tool set"; forked edits are outside `/rewind` checkpoints; Claude Code waits anyway in `-p`/SDK mode or with `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`; only sensible for skills "with **explicit instructions** (actionable task)" — [Claude Code: Skills](https://code.claude.com/docs/en/skills)
- Other: `hooks` (YAML map, "Hooks registered when skill invoked, persist for session"), `paths` (glob patterns "limiting when skill activates automatically", same format as path-specific rules), `shell` (`bash` or `powershell`), `metadata` ("Claude Code ignores"), `license`, `compatibility` — [Claude Code: Skills](https://code.claude.com/docs/en/skills)
- Placeholders: `$ARGUMENTS`, `$ARGUMENTS[N]`, `$N`, `$name`, `${CLAUDE_SESSION_ID}`, `${CLAUDE_EFFORT}`, `${CLAUDE_SKILL_DIR}` ("Directory containing skill's `SKILL.md`; For referencing bundled scripts/files"), `${CLAUDE_PROJECT_DIR}` (v2.1.196+), `${CLAUDE_PLUGIN_ROOT}`, `${CLAUDE_PLUGIN_DATA}`; `${CLAUDE_SKILL_DIR}` also substitutes inside `allowed-tools` Bash rules, e.g. `allowed-tools: Bash(${CLAUDE_SKILL_DIR}/scripts/render.sh *)` — [Claude Code: Skills](https://code.claude.com/docs/en/skills)

### Inferences
- For `ship`: in Claude Code add `disable-model-invocation: true` (removes the description from Claude's context entirely, so it cannot be auto-selected and Claude is told not to reproduce the steps); in Codex add `agents/openai.yaml` with `policy: allow_implicit_invocation: false` (skill stays available as `$ship`). The `SKILL.md` body and spec fields stay shared; the Claude-only key lives in `SKILL.md` front matter (Codex ignores unknown keys at load, but its own validator would flag it), while the Codex-only policy lives in a sidecar file Claude Code ignores. Note the tension: OpenAI's own authoring guidance says not to make a skill explicit-only merely because it is sensitive; the project's "only when the user explicitly asks" rule is a deliberate choice against that default.
- For the reviewer skills (`review-plan`, `review-design`, `review-loop`): `context: fork` with `agent: general-purpose` (they need Bash) and `background: false` (so the builder waits) would run them in a clean context in Claude Code; the skill text must then be self-contained because the fork does not see the conversation. Codex offers no front-matter fork; the equivalent is delegation to a subagent, as OpenAI's `review-agent` skill assumes ("Use when another agent delegates review").
- `${CLAUDE_SKILL_DIR}` is the Claude-side answer to the project's hard-coded `~/.agents/skills/<name>/script.sh` paths; Codex has no documented equivalent variable, so for Codex the installed absolute path or a relative path from the skill root (per spec and Codex's "agent runs commands from there" convention) remains necessary.
- `when_to_use` is Claude-only and counts toward the 1,536-char cap; `description` alone is the portable trigger text.

### Gaps
- No Codex documentation describes a variable analogous to `${CLAUDE_SKILL_DIR}`; whether Codex injects the skill's absolute location into context (as the agentskills.io `<location>` pattern suggests) was not verified by test.
- Whether Codex accepts and silently ignores unknown `SKILL.md` keys such as `disable-model-invocation` at load time (as opposed to its validator flagging them) was not tested directly.

## Key Question 4: Cross-agent installers, registries and plugin marketplaces

### Takeaway
Three distribution models exist beside a hand-written installer: (1) the Vercel `skills` CLI and skills.sh registry, which copy a skill into a canonical `.agents/skills/<name>` and symlink it into each agent's directory, tracked by `skills-lock.json` with `check`/`update`; (2) Claude Code plugin marketplaces (`.claude-plugin/marketplace.json` + `plugin.json`) with versions, `ref`/`sha` pinning, opt-in auto-update, `renames` and `forceRemoveDeletedPlugins`; (3) Codex plugins (`.codex-plugin/plugin.json`, `.agents/plugins/marketplace.json`, `codex plugin add|list|remove`, `codex plugin marketplace add|list|upgrade|remove`), whose plugins can carry `skills/`. Codex's binary also recognises `.claude-plugin/plugin.json` and `.cursor-plugin/plugin.json`. Instruction-file aggregators (ruler) and the AGENTS.md standard (Agentic AI Foundation) handle the per-agent instruction side.

## Key Question 5: Shared per-user instructions across `~/.claude/CLAUDE.md` and `~/.codex/AGENTS.md`

### Takeaway

## Key Question 6: Authoring best practices (Anthropic, OpenAI, agentskills.io) and portable script references

### Takeaway
Both vendors converge: write the `description` in third person stating what the skill does and when to use it (Codex adds "and should not trigger"), keep `SKILL.md` short (under 500 lines; Codex: "A large upper bound is not a target"), move detail to `references/` one level deep, use scripts only for deterministic or fragile steps, reference bundled files by relative path from the skill root, avoid absolute and Windows paths, and test with realistic prompts (Anthropic: at least three evals, baseline without the skill; OpenAI: five request categories). Codex and Anthropic both ship a `skill-creator`; Claude Code has `/skill-doctor` and `claude plugin eval`.

### Cited Findings

- Degrees of freedom: high (text instructions) when "Multiple approaches are valid"; low ("specific scripts, few or no parameters") when "Operations are fragile and error-prone ... - Naming: `name` max 64 chars, lowercase/numbers/hyphens, "Cannot contain reserved words: 'anthropic', 'claude'"; prefer gerund form (`processing-pdfs`), noun phrases acceptable (`pdf-processing`); avoid `helper`, `utils` — [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Descriptions: "**Always write in third person**. - `claude plugin init <name>` scaffolds a plugin at `~/.claude/skills/<name>/` that auto-loads as `<name>@skills-dir`; `claude plugin validate <path>` validates skills in a directory; `claude plugin eval` requires v2.1.269+ and supports `name@skills-dir` targets — local `claude plugin --help`; [Test plugins with evals](https://code.claude.com/docs/en/plugin-evals)
- Marketplace entries can pin `ref`/`sha`; `renames` and `forceRemoveDeletedPlugins` handle renames and removals; auto-update is opt-in per user or admin — [Marketplace reference](https://code.claude.com/docs/en/plugins/marketplace-reference); [Host and maintain a marketplace](https://code.claude.com/docs/en/plugins/host-marketplace)
- Codex local marketplaces: `~/.agents/plugins/marketplace.json` with `source: {source: "local", path: "./plugins/x"}`; `codex plugin marketplace add ./local-marketplace-root`; cache version `local` — [Package your plugin (OpenAI)](https://developers.openai.com/plugins/build/plugins)
- Codex's `skill-installer` installs from any GitHub repo path via `scripts/install-skill-from-github.py --repo <owner>/<repo> --path <path>` into `$CODEX_HOME/skills` (local `skill-installer/SKILL.md`)
- Claude Code reads a project `AGENTS.md` natively since v2.1.277 and says a `CLAUDE.md` with `@AGENTS.md` "can be left" — [How Claude remembers your project](https://code.claude.com/docs/en/memory)
- Claude Code loads `~/.claude/rules/*.md` for every project and loads user-scope imports without a dialog — [How Claude remembers your project](https://code.claude.com/docs/en/memory)
- A skill named `verify` or `simplify` is auto-run before commits (v2.1.286+) — [Claude Code: Skills](https://code.claude.com/docs/en/skills)
- Before v2.1.280 a `manifest.json` in `~/.claude/skills/` caused skills to be moved to `.trash/` — [Claude Code: Skills](https://code.claude.com/docs/en/skills)

### Inferences
- `ship`: add `disable-model-invocation: true` to `SKILL.md` and ship an `agents/openai.yaml` with `policy: allow_implicit_invocation: false`. Keep the description's "never on your own initiative" sentence as belt-and-braces. Be aware this contradicts OpenAI's default advice; the installer's README should say the choice is deliberate.
- Reviewer skills: for Claude Code, `context: fork`, `agent: general-purpose`, `background: false` would isolate the reviewer and prevent the builder's context from leaking in, at the cost of the skill text having to restate the task; the current design (the other harness's CLI runs the review) already isolates context, so `context: fork` is optional. If adopted, `allowed-tools: Bash(${CLAUDE_SKILL_DIR}/reviewer.sh *)` would remove a permission prompt.
- Front matter hygiene: keep `SKILL.md` to spec keys plus Claude Code's `disable-model-invocation` only where needed; if claude.ai upload or Codex validator cleanliness matters, move Claude-only keys out (Claude Code offers no sidecar, so this is a trade-off). Add `license` and `metadata: {version, source}` so the installer can detect version drift without the HTML marker; `metadata` is spec-legal in both harnesses.
- Script paths: write script invocations relative to the skill root (`scripts/reviewer.sh`), move cross-skill helpers (the runner used by `review-plan`, `review-design`, `review-loop`) into each skill or into a dedicated `review-runner` skill that others call by name, and for Claude Code optionally use `${CLAUDE_SKILL_DIR}`. This makes project-scope installs, `--plugin-dir`, and plugin packaging work unchanged.
- Repo layout and listing: the `skills/<name>/SKILL.md` layout is already Vercel-discoverable; publishing the repo publicly makes `npx skills add <owner>/agentic-skills-library -a claude-code -a codex -g` an alternative installer and gets it onto skills.sh's install-count listing. A `skills-lock.json`-style file (source repo, commit, per-skill hash) written by `install.sh` would enable an `install.sh --check` that compares installed hashes with the repo HEAD, mirroring `skills check`.
- Update checks: record the source commit in `metadata` or the marker comment (e.g. `<!-- agentic-skills-library: managed copy; source <sha> -->`) and have `install.sh --check` diff it against `git rev-parse HEAD`; optionally a `SessionStart` hook (both harnesses support `hooks.json`) could print a one-line "skills are N commits behind" notice.
- Plugin packaging as an opt-in path: for Claude Code, a `.claude-plugin/plugin.json` plus `skills/` directory can be dropped into `~/.claude/skills/<name>/` as a `skills-dir` plugin or published through a `.claude-plugin/marketplace.json` for pinning and `claude plugin update`; for Codex, a `~/.agents/plugins/marketplace.json` with a `local` source, or a Git marketplace added with `codex plugin marketplace add owner/repo`. The cost is namespaced invocation (`/agentic-skills:ship`) and no shared flat-skill behaviour, so keep the flat install as the default.
- Instruction block: on the Claude side, replace the duplicated text with `@~/.agents/instructions/how-to-work-on-a-task.md` (installed from `instructions/`) or a `~/.claude/rules/agentic-skills-library.md` file; keep the verbatim block for Codex, which has no imports. Update the README: Claude Code now reads a project `AGENTS.md` without the `@AGENTS.md` shim (v2.1.277+).
- Guard against `~/.codex/skills` and `~/.claude/skills` duplicates: have `install.sh` warn when a same-named directory exists in `~/.codex/skills/<name>`, since Codex still scans it and would present two skills.
- Validation in CI: run `skills-ref validate` (spec), `claude plugin validate skills/` (Claude Code) and Codex's `quick_validate.py` on each skill; note the latter rejects `compatibility`, so avoid that key if Codex validator cleanliness is a goal.

### Gaps
- Whether Codex de-duplicates or warns on the same skill name in `~/.codex/skills` and `~/.agents/skills` was not tested.
- No public Codex API exists for "update check" of skills; `skill-installer` installs but does not compare versions.
- `claude plugin eval` and skill-creator evals were not run against the project's skills; their fit for review-style skills (which spawn another CLI) is untested.
