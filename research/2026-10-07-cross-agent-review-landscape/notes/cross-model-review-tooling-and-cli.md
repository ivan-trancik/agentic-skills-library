## Q1. Cross-model review tools (zen/PAL MCP, Codex-as-MCP, Claude-as-MCP, Gemini CLI, community Codex/Claude bridges): how they prompt the reviewer, give it the diff, limit permissions, and format findings

### Takeaway
Every working bridge found reduces to one of two mechanisms: spawning the other harness's headless CLI (`codex exec`/`codex review` or `claude -p`) with a bounded prompt and restricted permissions, or wrapping that CLI in an MCP server. None passes a diff as data by default; most tell the reviewer to run `git diff` itself (file paths over content), and the ones that do pass content embed `git diff --binary --no-ext-diff` output in an XML-tagged block. Finding formats converge on severity-ordered lists with `file:line`, a one-line claim, a concrete failure scenario, a fix, and a terminal verdict word (PASS/NEEDS_CHANGES, APPROVED/CHANGES_REQUESTED, LGTM). The official `codex mcp-server` route is gone (removed in favour of `codex app-server`, which is JSON-RPC, not MCP), and `claude mcp serve` exposes only Claude Code's tools, not a reviewing model, so neither first-party MCP path yields a review.

### Inferences
- The only first-party, supported way to get a *review from the other model* today is the other harness's headless CLI; MCP gets you tools or a thread, not a verdict. The project's `reviewer.sh` design (CLI-to-CLI) is therefore the mainstream shape, and the hyperskills runner independently arrived at the same two safeguards the project uses (tree fingerprint before/after, restricted tool set).
- Nearly all bridges let the reviewer discover the diff itself via git rather than inlining it; the exception (OJamals) inlines the diff only because its reviewer runs with `dontAsk` and no Bash allow rule, so it cannot run git. Inlining becomes necessary exactly when you take Bash away.
- PAL/zen's value for this project is mostly its *prompt design* (severity taxonomy, `files_required_to_continue`, confidence ladder with "certain" short-circuit) rather than its runtime, which relaxes permissions (`--dangerously-bypass-approvals-and-sandbox`, `acceptEdits`) and had its last push in December 2025.
- Several wrappers still reference `codex mcp-server`; anything built on it is broken on 0.160.1.

## Q2. Built-in review features: `codex review` / `codex exec review`, Codex's bundled code-review plugin, Codex cloud GitHub reviews, Claude Code `/code-review` (effort levels, `--fix`, `--comment`, ultra), `/security-review`, `/simplify`, GitHub Action review; default severity thresholds and formats; comparison with a hand-rolled prompt

### Takeaway
Both vendors ship a fixed review rubric that is stricter and more structured than most hand-rolled prompts: Codex's rubric demands a JSON object with per-finding `confidence_score`, `priority` 0–3 ([P0]–[P3] title tags), short `code_location` ranges overlapping the diff, an `overall_correctness` verdict, and "prefer outputting no findings" unless the author would fix it; Claude Code's `/code-review` runs effort-dependent recipes (low: one diff pass, no verify; medium: 8 finder angles x up to 6 candidates then a 1-vote CONFIRMED/PLAUSIBLE/REFUTED verify pass, ≤8 findings, precision-biased; high: same but recall-biased, ≤10; xhigh/max ≤15) and outputs `{file, line, summary, failure_scenario}`. Codex's custom review instructions *replace* the user message and cannot be combined with `--uncommitted/--base/--commit` (clap conflict), but the rubric always stays as the system prompt. Only `codex exec review` (not top-level `codex review`) accepts `-o`/`--json`; `--worktree` is rejected for reviews.

## Q3. Headless mechanics for Codex (`codex exec`): output options, exit codes, sandbox modes and what read-only forbids, `--worktree`, `--add-dir`, images, stdin hang, reasoning effort, approvals

### Takeaway
`codex exec` prints only the final message to stdout, progress to stderr, writes the last message with `-o`, and emits JSONL with `--json` (`--experimental-json` survives only as a hidden alias). It never asks for approval (headless default `never`) and defaults to `read-only`, which — measured locally — denies every write (cwd, `/tmp`, `$TMPDIR`, `.git`, `__pycache__`, `~/.cache`), so read-only cannot run test suites that write caches; `workspace-write` allows cwd, `/tmp`, `$TMPDIR` and cache dirs inside the workspace but still denies `.git`, `~/.cache` and network. The stdin hang is real and deterministic: with a prompt argument and a non-TTY stdin, Codex prints "Reading additional input from stdin..." and blocks in `read_to_end` until EOF, so `< /dev/null` (or a closing pipe) is mandatory. Exit code is 1 on setup errors or when any error event was seen, else 0; exit codes are not officially documented.

### Inferences
- `-s workspace-write` is the minimum sandbox for a reviewer that must run the project's checks; the project's choice is therefore justified by measurement, and `.git` stays protected even there, so the reviewer cannot commit or rewrite history through git (it can still edit tracked files — hence the fingerprint check).

## Q4. Headless mechanics for Claude Code (`claude -p`): tool restriction, permission modes, output formats, structured output, limits, system prompt, images, nested-session behaviour

### Takeaway
On 2.1.292 a nested `claude -p` launched from inside a Claude Code session works (verified live, and the old "Claude Code cannot be launched inside another Claude Code session" string is absent from the binary); the current env markers only affect session persistence. `claude --help` hides several working flags (`--max-turns`, `--append-system-prompt-file`, `--system-prompt-file`, `--permission-prompt-tool`), and the docs say so explicitly. - The project's `--allowedTools "Bash,Read,Grep,Glob"` happens to be what restores Glob/Grep on macOS (naming either restores both), so that part is sound; but the bare `Bash` entry means any shell command runs unprompted in `default` mode, so "don't change the work" is enforced only by the prompt and detected only by the fingerprint. Swapping the bare `Bash` for prefix rules (`Bash(git diff *)`, `Bash(git status *)`, the project's check commands) plus `--permission-mode dontAsk` (or plan mode) would make edits via shell impossible rather than merely detectable.
- If the user's org/plan ever puts `-p` into `auto` mode (third-party provider or telemetry off on ≥2.1.285), the bare `Bash` allow is silently dropped and the classifier decides each command — the reviewer would keep working but behave differently; pinning `--permission-mode` removes that variability.
- The ~$0.59 fixed cost per nested `-p` launch is mostly context (CLAUDE.md, skill listings, MCP tool schemas) being cached; `--safe-mode` keeps OAuth and strips all of that, `--bare` strips more but needs an API key. Either would make each review round cheaper and faster.
- Because `-p` executes project hooks and `.mcp.json` servers with no trust prompt, a reviewer run against an untrusted checkout is a code-execution vector; `--settings '{"disableAllHooks":true}' --strict-mcp-config` is the minimal hardening that keeps subscription auth.

- Whether `--json-schema` structured output coexists with a reviewer that must also run tools for many turns was not tested (docs say it validates "after the agent completes its workflow").

## Q5. Commercial PR reviewers (CodeRabbit, Greptile, Cursor Bugbot, GitHub Copilot, Graphite Diamond, Qodo, plus Codex cloud and Claude Code Review): noise filtering, confidence, memory of accepted/dismissed feedback, finding format, published statistics

### Takeaway
The commercial tools converge on four noise controls: (1) a severity label per finding with a posting threshold (Codex P0/P1 only on GitHub; Qodo `inline_comments_severity_threshold`; CodeRabbit profiles quiet/chill/assertive; Claude Code Review Important/Nit/Pre-existing with a REVIEW.md nit cap), (2) multi-pass generation plus a validator/verification pass (Bugbot's 8 randomized passes + majority vote + validator; Claude's finder agents + verification step; Copilot suppresses low-confidence output per secondary sources), (3) repository-level natural-language rules (CodeRabbit path instructions, Greptile greptile.json/strictness/commentTypes, Cursor BUGBOT.md, Graphite dashboard rules, Codex AGENTS.md "Code Review Rules", Claude REVIEW.md), and (4) feedback memory keyed on 👍/👎 and replies (Greptile learns only from 👍/👎; CodeRabbit stores "Learnings" from replies with a dashboard; Graphite and Claude collect reaction rates to tune). Published numbers: Bugbot resolution rate 52%→70%+ (v1→v11); an independent 146-PR study found CodeRabbit 2.3% FP, Bugbot 4.8%, Greptile 0% (of 120 findings), and 93.4% of findings caught by exactly one tool.

We Ran 4 in Parallel for 3 Weeks (146 PRs, 679 Findings)" (2026-05-12; PHP/React SaaS, default configs): CodeRabbit 281 findings / 82 PRs / 3.4 per PR / 2.3% FP / 68.3% ship a diff or suggestion block / 9.5 min mean latency; Sentry Seer 149 / 62 / 2.4 / 12.5% FP (15.0% at "high" tier, 6/6 at "critical") / 3.7 min; Greptile 120 / 55 / 2.2 / 0% FP ("~92% bug-shaped") / 32.5% with suggestion blocks / 4.9 min; Cursor BugBot 128 / 50 / 2.6 / 4.8% FP / prose-only / 6.1 min; "93.4%" of findings were caught by exactly one reviewer and "all four reviewers never once converged on the same line"; author's lean: Greptile — [Source](https://dev.to/_vjk/best-ai-code-reviewer-in-2026-we-ran-4-in-parallel-for-3-weeks-146-prs-679-findings-1c0f)

### Inferences
- The field has settled on "severity + confidence + evidence" per finding and on a *posting threshold* separate from the *finding list*: Qodo and Claude Code Review both keep sub-threshold findings in a summary rather than dropping them. The project's binary must-fix/not-must-fix split is the stricter end of that spectrum; a "below-threshold, mentioned in a count" tail would preserve information without reopening noise.
- Memory of accepted/rejected feedback is implemented everywhere as a *reviewer-side* store (learnings, memories, rules) consulted on every run, with reactions as the cheapest training signal. The project's `.local/decisions.md` "Settled choices" is a builder-side equivalent; the vendors' lesson is to show the reviewer the rejected finding *and the reason*, and to let a factually wrong reason be challenged once — which the project already does.
- Majority voting across randomized passes (Bugbot) and explicit verify-or-refute votes (Claude) are the two cheap ways to buy precision without a second model; both are reproducible with the harnesses on hand (e.g., run the reviewer twice with shuffled file order and keep intersecting findings, or ask the same reviewer to refute its own list in a second turn).
- The near-zero overlap between tools (93.4% unique findings) is the empirical argument for cross-model review itself: a second reviewer from a different family finds mostly different things.

## Q6. Concrete ideas the project could adopt

### Takeaway
The highest-value changes are mechanical and verified: make the Claude reviewer genuinely read-only with prefix allow rules plus `dontAsk` (or the Bash sandbox), run the Codex reviewer through `codex exec review` to inherit the JSON rubric or keep `codex exec` but borrow the rubric's "author would fix it / provably affected / not pre-existing" tests, add a per-finding confidence field and a verify-or-refute second turn, and harden/cheapen both launches (`--safe-mode`, `--settings '{"disableAllHooks":true}'`, `--max-turns`/`--max-budget-usd`, unique absolute `-o` paths, `--permission-prompts none`).

### Cited Findings
- `--disallowedTools "Edit"` removes the tool from context; scoped `Bash(...)` rules deny only matching calls; `dontAsk` denies anything that would prompt while read-only Bash and `--allowedTools` entries still run — [Source](https://code.claude.com/docs/en/cli-reference); [Source](https://code.claude.com/docs/en/permission-modes)
- Claude's Bash sandbox can be enabled per run via `--settings` and restricts writes to cwd/temp/added dirs with OS enforcement — [Source](https://code.claude.com/docs/en/sandboxing)
- Codex read-only denies all writes; workspace-write protects `.git`; `codex exec review` writes rendered findings to `-o` and accepts a custom prompt that replaces only the user message — [Source](https://learn.chatgpt.com/docs/agent-approvals-security); [Source](https://github.com/openai/codex/blob/main/codex-rs/prompts/src/review_request.rs)
- Codex rubric rules 4, 6, 7 and the ≤1-paragraph/≤3-lines comment limits — [Source](https://github.com/openai/codex/blob/main/codex-rs/prompts/templates/review/rubric.md)
- Claude's CONFIRMED/PLAUSIBLE/REFUTED verify vote and `{file,line,summary,failure_scenario}` output — strings from the 2.1.292 binary; `ReportFindings` documented at [Source](https://code.claude.com/docs/en/tools-reference)
- REVIEW.md patterns: verification bar, re-review convergence, summary tally — [Source](https://code.claude.com/docs/en/code-review)
- hyperskills: findings ledger carried verbatim across rounds; "Two reviewers agreeing... does not promote a candidate to confirmed"; don't pipe through head/tail; strip `ANTHROPIC_API_KEY` for subscription billing — [Source](https://github.com/hyperb1iss/hyperskills/blob/main/skills/cross-model-review/SKILL.md)
- turbo: unique absolute `-o` paths; resume a timed-out Codex session with `codex exec -o <fresh> resume <id> "Reply now with your complete findings..."` — [Source](https://github.com/tobihagemann/turbo/blob/main/claude/skills/codex-exec/SKILL.md)
- Measured cost of a nested `-p` launch here: $0.59 with 73,500 cache-creation tokens for a one-word answer; `--safe-mode` keeps OAuth while dropping CLAUDE.md/skills/MCP — [Source](https://code.claude.com/docs/en/cli-reference)
- Bugbot's majority vote over randomized passes and validator model — [Source](https://cursor.com/blog/building-bugbot)

### Inferences
1. **Make the Claude reviewer unable to edit, not just told not to.** Replace `--allowedTools "Bash,Read,Grep,Glob"` with `--permission-mode dontAsk --permission-prompts none --allowedTools "Read" "Grep" "Glob" "Bash(git status *)" "Bash(git diff *)" "Bash(git log *)" "Bash(git show *)" "Bash(<project check commands> *)" "Bash(mkdir -p .local/scratch*)" --disallowedTools "Edit" "Write" "NotebookEdit" "mcp__*"`. Read-only shell builtins (`ls`, `cat`, `grep`, `find`, ...) still work without rules; anything else is denied instead of running. Keep the fingerprint check as the backstop. Optionally add `--settings '{"sandbox":{"enabled":true,"allowUnsandboxedCommands":false,"filesystem":{"denyWrite":["."],"allowWrite":[".local/scratch"]}}}'` so even an allowed check command cannot write outside `.local/scratch` (test first: some test runners need `/tmp`, which the sandbox allows by default).
2. **Pin the permission mode and harden the launch.** Always pass `--permission-mode` (so an org/plan flip to `auto` cannot silently drop the bare `Bash` allow), `--settings '{"disableAllHooks":true}' --strict-mcp-config` (a `-p` run otherwise executes the repo's hooks and `.mcp.json` servers with no trust prompt), `--no-session-persistence`, and consider `--safe-mode` to cut the ~73k-token context load per round while keeping subscription auth (use `--bare` only if an `ANTHROPIC_API_KEY` is acceptable). Add `--max-turns` and `--max-budget-usd` as circuit breakers and `--output-format json` so the builder can read `result`, `permission_denials`, and `total_cost_usd`.
3. **Let Codex run its own rubric.** For round 1 (full review) call `codex exec review -s workspace-write -c model_reasoning_effort=high -o out.md "<project reviewer prompt>" < /dev/null` instead of `codex exec`: the custom prompt replaces only the user message, Codex's rubric stays as the system prompt, and `-o` receives `[Pn] title — path:start-end` findings with bodies. Treat P0/P1 as must-fix and P2/P3 as the "mentioned, not fixed" tail. Caveat: `--worktree` and `-i/--image` are not available on `exec review`, so keep plain `codex exec` for the design (screenshot) review and for "Fixes to check" rounds where the project's narrower scope matters.
4. **Borrow three rubric tests into the hand-rolled prompt** (they target exactly the false positives a loop suffers from): "The bug was introduced in this change (pre-existing bugs should not be flagged)"; "It is not enough to speculate that a change may disrupt another part of the codebase — identify the other parts of the code that are provably affected"; "Do not rely on unstated assumptions about the author's intent". Add the comment limits: body ≤1 paragraph, no code chunk longer than 3 lines, state the inputs/environment needed for the failure.
5. **Add a confidence field and a refute pass.** Ask for `confidence: confirmed-by-running | confirmed-by-reading | plausible` (the project already distinguishes run vs read; make "plausible" explicit) and, after the list, run one more reviewer turn whose only job is to REFUTE each finding by quoting the line that disproves it (Claude's verify vote); drop REFUTED items before the builder sees them. For precision rounds, a cheap majority vote is to run the reviewer twice with the file list in shuffled order and keep only findings reported both times (Bugbot's trick), at 2x cost.
6. **Terminal verdict as structured output.** Keep `NO MUST-FIX FINDINGS` but also request an `overall_correctness`-style line (`VERDICT: PASS|NEEDS_CHANGES`) and a one-line tally (`2 must-fix, 3 below threshold`) at the top — the REVIEW.md "summary shape" idea — so `review-loop` can parse without reading the body. With Claude, `--json-schema '{"type":"object","properties":{"verdict":{"enum":["PASS","NEEDS_CHANGES"]},"findings":{"type":"array"}},"required":["verdict","findings"]}'` gives this for free in `structured_output`.
7. **Carry the ledger, not just the settled choices.** Following hyperskills and REVIEW.md "re-review convergence": in rounds ≥2 pass the previous round's findings verbatim with their disposition (fixed / rejected + reason / disputed) and instruct the reviewer to check closure of those first and only then look for new must-fix items; this is what the project's "Fixes to check" does, made explicit per finding.
8. **Operational hygiene for Codex runs.** Use a unique absolute `-o` path per round (the current `.local/review-round-N.md` already is per round; make it absolute via `$(git rev-parse --show-toplevel)`), capture the `session id:` line from the log, and on a 10-minute timeout resume with `codex exec -o <fresh> resume <id> "Reply now with your complete findings as your final message." < /dev/null` instead of re-running from scratch. In `--json` mode, treat `item.type=="error"` as warnings unless the exit code is 1 (the Superset wrapper's hook-trust warning appears there). Tell the reviewer prompt that `.git` and `$HOME` are write-protected so it does not misreport a denied cache write as a project bug.
9. **Decide effort deliberately.** The user's Codex default is `xhigh`; `-c model_reasoning_effort=high` lowers it. Either drop the override to inherit the user's default (the README says the reviewer runs on each harness's default model) or expose it as a knob mirroring `/code-review low|medium|high` (precision vs recall).
10. **Billing route.** When Codex is the builder and launches `claude -p`, strip an inherited `ANTHROPIC_API_KEY`/`ANTHROPIC_AUTH_TOKEN` if the intent is subscription billing (hyperskills' rule); when Claude launches Codex, `CODEX_HOME` is already handled by the Superset wrapper.

### Gaps
- Items 1 and 5 need a local test of `dontAsk` + prefix allow rules against the project's actual check commands (e.g. whether `npm test` spawns subcommands the rule does not cover) before adopting.
- Whether `codex exec review` honours `-s workspace-write` placed after `review` was not tested (it is listed in `codex exec --help` as a global option of `exec`, and inherited by the top-level `review`), and `--add-dir` was not tested with reviews.
- The cost comparison `--safe-mode` vs current launch was not measured; the $0.59 figure is a single sample in this repository.
