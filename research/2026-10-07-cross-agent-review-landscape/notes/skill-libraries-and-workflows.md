## Key question 1: Which libraries define a full workflow (brainstorm or plan, plan review, build, code review, finish or ship), and what do the awesome lists rank highly in 2026?

### Takeaway
Seven libraries define a genuinely end-to-end loop with a plan artifact, a review stage and a finishing step: obra/superpowers, garrytan/gstack, EveryInc/compound-engineering-plugin, bmad-code-org/BMAD-METHOD, Yeachan-Heo/oh-my-claudecode, affaan-m/everything-claude-code and mattpocock/skills. The spec-driven tools (github/spec-kit, Fission-AI/OpenSpec, Kiro-style) define plan→implement→verify but no code-review or ship step; Taskmaster and ccpm are task/PM layers without review or ship; anthropics/skills, openai/skills and davila7/claude-code-templates are catalogs, not workflows; OneRedOak/claude-code-workflows covers only the three review workflows (code, security, design).

### Inferences
- The field has split into three layers: (a) opinionated "process" bundles that own the whole loop (superpowers, gstack, compound-engineering, BMAD, OMC), (b) composable small skill sets that deliberately do not own the process (mattpocock/skills, this project), and (c) spec/PM layers (spec-kit, OpenSpec, Kiro, Taskmaster, ccpm) that stop at "implement" and leave review and shipping to the host or to another tool.
- Every full-loop library except spec-kit and OpenSpec now puts a fresh-context or other-model review between build and finish; this is the one phase this project shares with the whole top tier.

### Gaps
- The awesome lists do not rank entries; "ranked highly" could only be approximated by inclusion and by star counts (see KQ4).
- jcputney/agent-peer-review, ching-kuo/claude-codex, skills-directory/skill-codex, Plannotator, Claude CodePro and AB Method were not read; only their list descriptions are cited.

## Key question 2: For each library, how do the plan phase, code review, finish/ship step and memory of decisions work concretely?

### Takeaway
Plans are almost always committed Markdown files with a date or number prefix (superpowers `docs/superpowers/plans/YYYY-MM-DD-<feature>.md`, compound `docs/plans/`, OpenSpec `openspec/changes/<name>/`, spec-kit `specs/NNN-<name>/`, BMAD `_bmad-output/`, OMC `.omc/plans/ralplan-*.md`), and the human gate is "approve the written plan before any code" everywhere; code review is done by a fresh subagent with a three-level severity scale and, increasingly, a confidence floor and an explicit "zero findings is valid" rule; finishing stops at "push and open a PR" in nearly every library (only gstack `/land-and-deploy` and this project's `ship` merge); decisions are remembered via ledgers/plan sections (superpowers `progress.md` "Ruling:" lines, BMAD `## Code Review` blocks with recorded dismissals, compound `docs/solutions/`, ECC instincts, gstack `/learn`).

#### obra/superpowers (v6.4.2, 2026-09-25)
- Plan phase: brainstorming classifies every request as Spike / Bounded / Architectural "before your first question" and says it out loud; "When in doubt between two paths, take the heavier one"; architectural work writes a design doc to `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md` and then invokes writing-plans — [brainstorming/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md)
- Human gate is explicit and staged: "<HARD-GATE> Before taking any implementation action ... Spike: the human partner approves the question and probe. Bounded: the human partner approves the short in-chat design. Architectural: the human partner reviews and approves the written spec, then reviews the written implementation plan and selects its execution method. Conversational design approval only permits writing the spec; written-spec approval only permits invoking writing-plans." and "A reply approves the stage actually presented. Approval of an idea or feature scope does not approve artifacts that do not exist yet." — [brainstorming/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md)
- Plan file: "Save plans to: `docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md` (User preferences for plan location override this default)"; mandatory header with Goal, Architecture, Tech Stack, Spec path, "## Global Constraints", "## Review Focus" (up to five inputs or failure modes the spec implies but no task tests); tasks carry "Files", "Interfaces: Consumes/Produces" and checkbox steps (write failing test, run to fail, implement signature, run to pass, commit); self-review is "a checklist you run yourself — not a subagent dispatch" — [writing-plans/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/writing-plans/SKILL.md)
- v6.4.2 release notes: "A plan records decisions. - Plan review by whom: no separate plan-review skill; the plan's self-review plus the user's review of the saved plan; a `plan-document-reviewer-prompt.md` was removed in v6.4.2 ("Nothing referenced it") — [RELEASE-NOTES.md](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md)
- Code review: `requesting-code-review` dispatches "a `general-purpose` subagent" with a template; "The reviewer gets precisely crafted context for evaluation — never your session's history"; mandatory "After each task in subagent-driven development, After completing major feature, Before merge to main"; findings are "Critical (Must Fix) / Important (Should Fix) / Minor (Nice to Have)", each with "File:line reference, What's wrong, Why it matters, How to fix", plus "Ready to merge? [Yes | No | With fixes]"; the reviewer is told "Your review is read-only on this checkout. Do not mutate the working tree, the index, HEAD, or branch state in any way" and "You Do Not Dispatch Subagents"; it must list a "Declined to judge" section: "list every behavior you considered and set aside as outside the plan or spec, one line each, with the reason. - Builder's handling of findings: "Fix Critical issues immediately, Fix Important issues before proceeding, Note Minor issues for later, Push back if reviewer is wrong (with reasoning)"; receiving-code-review forbids "You're absolutely right!" and requires "READ → UNDERSTAND → VERIFY → EVALUATE → RESPOND → IMPLEMENT"; "IF conflicts with your human partner's prior decisions: Stop and discuss with your human partner first" — [receiving-code-review/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/receiving-code-review/SKILL.md)

Park findings in ledger with rulings"; the final whole-branch review gets "ONE fix dispatch, one scoped re-review, adjudicate residuals" — [subagent-driven-development/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md)

## Key question 3: Which patterns are widely copied or considered best practice in 2026, and which have been criticised?

### Takeaway
Copied everywhere: written plan before code with a hard approval gate, fresh-context reviewer that never sees the author's history, three-level severity with a confidence floor and "no findings is valid", bounded fix/re-review rounds, and "never push/merge without being asked"; criticised: token cost and ceremony on small tasks (Superpowers), skill libraries crowding the description budget, mandatory TDD/verification theatre, rigid phase gates (spec-kit, via OpenSpec), and persona-heavy prompt packs that are "just prompts" (gstack).

Chasing every finding leads to over-engineering" — [best-practices](https://code.claude.com/docs/en/best-practices)

## Key question 5: Which libraries pair Claude Code with Codex (or another agent) as builder and reviewer?

### Takeaway

### Inferences
- The consensus mechanics for a cross-model reviewer in 2026 are: `codex exec` with `read-only` sandbox (or `--disallowedTools Edit,Write` on the Claude side), a JSON schema for findings (`--output-schema` / `--json-schema`), a severity+confidence gate, a bounded number of rounds, and the builder re-verifying each finding before acting; this project matches all but the schema and the read-only sandbox (it uses `workspace-write` plus a post-hoc fingerprint check).
- Nobody else combines "the loop stops when accepted findings stop falling" with a diff-growth cap; the closest guards are antonmd's verify-only later rounds and compound's "repair budget".

### Gaps
- Whether `codex exec -o out.md` works under `-s read-only` was not tested; the community tools write results from their wrapper scripts, not from inside the sandbox.
- jcputney/agent-peer-review and ching-kuo/claude-codex may be close analogues to this project but were not read.

## Key question 6 (from the objective): What could this project borrow, and what does it already do that the others do not?

### Takeaway

### Inferences
- Ideas to borrow, in rough order of value for cost: (1) add a "declined to judge / out of scope" section to `.local/review.md` and the "Ruling: what — why — cost if wrong" line format to `.local/decisions.md`; (2) put ECC/Anthropic-style calibration text (confidence floor, proof for must-fix, zero findings valid, false-positive list) into the reviewer prompt; (3) make later review-loop rounds verify-only against the previous findings; (4) request schema-conforming JSON from both `codex exec --output-schema` and `claude -p --json-schema` and render Markdown from it; (5) run the Codex reviewer with `-s read-only` and keep the fingerprint check as a second line of defence; (6) classify tasks Spike/Bounded/Architectural in the default instruction block so trivial changes skip review-plan; (7) extend review-design with a 768px pass, console-error capture and the Blocker/High/Medium/Nit taxonomy; (8) offer `npx skills add` or plugin manifests alongside the bash installer.
- Already distinctive in this project and not seen elsewhere in this research: the symmetric pairing where either harness can build and the other reviews via one shell script; a content fingerprint proving the reviewer did not edit files (others rely on sandbox flags alone); a loop stop rule based on the count of accepted findings and on diff growth (>50% or >200 lines); the plan file starting with the user's request verbatim; and `apply-review`/`save-review` as an explicit hand-off pair via `.local/review.md`.
- One divergence to weigh: most libraries commit plans and review blocks (superpowers `docs/superpowers/`, compound `docs/plans/`, OpenSpec change folders, BMAD plan `## Code Review`), while this project keeps them in `.local/`; the committed approach gives PR reviewers the intent, the local approach avoids repository noise — OpenSpec's team workflow shows a middle path (plan in the PR, archived after merge).

### Gaps
- None of the libraries publish measured data on how often reviewers re-raise rejected findings, so the benefit of `.local/decisions.md` versus verify-only rounds cannot be quantified from sources.
- Whether `claude -p --json-schema` is documented by Anthropic was not verified (seen only in the taupe.site practitioner post); the Claude Code headless docs page was not read.
