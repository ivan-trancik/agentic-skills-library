# How coding agents take and review screenshots for design review (macOS, as of 2026-10-07)

Scope note: the project under comparison is the `review-design` skill in the agentic-skills-library repo (builder runs the app, a shell script drives headless Chrome `--headless=new --disable-gpu --hide-scrollbars --window-size=WxH --virtual-time-budget=8000 --screenshot=out.png URL` at 1440x900, 1440x4000 and 390x844 plus one per task-relevant state; the builder writes `.local/design-context.md`; the other agent reviews headlessly via `codex exec --image=...` or `claude -p` reading PNGs; the reviewer prompt asks for must-fix findings or `NO MUST-FIX DESIGN FINDINGS`, then at most five suggestions). "Project" below means that skill. All comparisons are in the Inferences subsections.

## Key question 1: Browser tooling available to agents (capture interactive states, multiple viewports, dark mode, full page, no display on macOS; setup cost and reliability)

### Takeaway
Every mainstream agent browser tool except the bare `chrome --screenshot` CLI can click, resize, emulate devices and dark mode, and capture full pages headlessly on macOS; the two best-documented options for a Claude Code + Codex pair are Playwright MCP (`@playwright/mcp`, accessibility-tree first, one-line install in both CLIs) and Chrome DevTools MCP (`chrome-devtools-mcp`, Puppeteer-based, also ships `emulate` with `colorScheme`, `lighthouse_audit`, and screenshot downscaling flags). The headless CLI's `--virtual-time-budget` is a real "wait for network, then fast-forward timers" mechanism, but the CLI cannot click, emulate `prefers-color-scheme`, or capture beyond the window size.

### Cited Findings

Headless Chrome CLI (the project's current capture path)
- Chromium's headless command switches define `--screenshot` as "Save a screenshot of the loaded page."; `--dump-dom` as "Print the serialized DOM (doctype + document.documentElement.outerHTML) to stdout."; `--print-to-pdf` as "Save a PDF file of the loaded page."; `--default-background-color` as "The background color to be used if the page doesn't specify one. Provided as RGB or RGBA integer value in hex, e.g. 'ff0000ff' for red or '00000000' for transparent."; `--timeout` as "Issues a stop after the specified number of milliseconds. This cancels all navigation and causes the DOMContentLoaded event to fire." — [Chromium source: components/headless/command_handler/headless_command_switches.cc](https://chromium.googlesource.com/chromium/src/+/main/components/headless/command_handler/headless_command_switches.cc)
- `--virtual-time-budget`: "If set the system waits the specified number of virtual milliseconds before deeming the page to be ready. For determinism virtual time does not advance while there are pending network fetches (i.e no timers will fire). Once all network fetches have completed, timers fire and if the system runs out of virtual time is fastforwarded so the next timer fires immediately, until the specified virtual time budget is exhausted." — [Chromium source: headless_command_switches.cc](https://chromium.googlesource.com/chromium/src/+/main/components/headless/command_handler/headless_command_switches.cc)
- Google's "Getting started with Headless Chrome" shows `--screenshot` sized by `--window-size`: `chrome --headless --disable-gpu --screenshot --window-size=1280,1696 https://www.chromestatus.com/` ("the size of a standard letterhead") and `--window-size=412,732` ("Nexus 5x"); `--disable-gpu` is described as needed only on Windows; `--dump-dom` "prints `document.body.innerHTML` to stdout"; the post recommends Puppeteer or the DevTools protocol for anything beyond one-off tasks — [developer.chrome.com blog](https://developer.chrome.com/blog/headless-chrome/)
- "In Chrome 112, the Headless mode was updated so that Chrome creates, but doesn't display, any platform windows"; "Since Chrome 132.0.6793.0 the old Headless mode is only available as a standalone binary named `chrome-headless-shell`"; Puppeteer `headless: true` is new headless and `headless: 'shell'` is the old shell — [developer.chrome.com Headless docs](https://developer.chrome.com/docs/chromium/headless)
- Chromium's headless README: "As of M132, headless shell functionality is no longer part of the Chrome binary, so --headless=old has no effect"; programmatic control should use the DevTools remote-debugging protocol or Node packages like Puppeteer and chrome-remote-interface — [Chromium headless/README.md](https://chromium.googlesource.com/chromium/src/+/main/headless/README.md)
- Dark mode via CLI: Chromium's `--force-dark-mode` applies Chrome's filter-based auto-darkening to any site, which "differs from simulating the `prefers-color-scheme: dark` media query that respects sites' native dark mode implementations"; emulating the media query requires the DevTools Protocol before load — [fullpage-screenshot.ai.studio article (secondary)](https://fullpage-screenshot.ai.studio/articles/screenshot-dark-mode-wrong-theme); same distinction made for Cypress/Chromium launches — [Cypress blog (secondary)](https://www.cypress.io/blog/test-your-web-app-in-dark-mode)

Playwright library API (what MCP/CLI/shot-scraper build on)
- `page.screenshot` options: `fullPage` ("When true, takes a screenshot of the whole scrollable page", default false), `clip`, `mask` (locators overlaid with a solid color), `maskColor` (default `#F0F`), `omitBackground`, `animations` (`"disabled"` or `"allow"`), `caret` (`"hide"` default, `"initial"`), `scale` (`"css"` one pixel per CSS pixel, `"device"` default), `style` (inject CSS during capture), `type` png/jpeg, `quality`, `timeout`, `path` — [playwright.dev page.screenshot](https://playwright.dev/docs/api/class-page#page-screenshot)
- `page.goto` `waitUntil`: `"load"`, `"domcontentloaded"`, `"networkidle"` (waits for at least 500 ms with no network activity), `"commit"`; `networkidle` is discouraged: "Don't use this method for testing, rely on web assertions to assess readiness instead" — [playwright.dev page API](https://playwright.dev/docs/api/class-page#page-screenshot)
- `page.emulateMedia`: `colorScheme` `"light"`/`"dark"`/null, `reducedMotion` `"reduce"`/`"no-preference"`, `forcedColors` `"active"`/`"none"` — [playwright.dev page API](https://playwright.dev/docs/api/class-page#page-screenshot)
- Device descriptors via `playwright.devices` (e.g. `'iPhone 13'`, `'Desktop Chrome'`, `'Pixel 5'`) set `userAgent`, `screenSize`, `viewport`, `hasTouch`, `deviceScaleFactor`, `isMobile`; `colorScheme`, `locale`, `timezoneId`, `geolocation`, `offline`, `permissions` are context options; usage `use: { ...devices['iPhone 13'] }` and `test.use({ colorScheme: 'dark' })` — [playwright.dev emulation](https://playwright.dev/docs/emulation)
- Full-page height ceiling: "past roughly 16,384 pixels of height it hits a hard browser limit on how large a single image can be"; taller pages must be tiled — [fullpage-screenshot.ai.studio (secondary)](https://fullpage-screenshot.ai.studio/long-webpage-screenshot); Chromium out-of-memory crashes on very tall full-page captures described at [dev.to (secondary)](https://dev.to/allscreenshots/debugging-chromium-crashes-when-taking-full-page-screenshots-with-playwright-43k1)

### Inferences
- The project's headless CLI path already has the best readiness heuristic the CLI offers: `--virtual-time-budget=8000` pauses virtual time while fetches are pending and then fast-forwards timers, so it approximates "network idle plus settled timers" without a wall-clock sleep. What it cannot do is click, hover, focus, emulate `prefers-color-scheme`, set `deviceScaleFactor` independently of the window, or capture beyond `--window-size` (the 1440x4000 "full page" is really a 4000 px tall viewport, which also changes how `100vh` layouts and sticky elements render compared with a true `fullPage` capture).
- A Playwright-based script (Node `playwright` or Python `playwright` as in Anthropic's `webapp-testing` skill) replaces the Chrome-finding shell script with roughly the same install cost (`npx playwright install chromium`) and gains `fullPage`, `devices['iPhone 14']` (correct `deviceScaleFactor`/`isMobile`), `emulateMedia({ colorScheme: 'dark' })`, `mask`, `animations: 'disabled'`, `scale: 'css'`, and scripted clicks for states. It keeps the project's "screenshots on disk, reviewer runs headless" architecture.
- shot-scraper `multi` is the closest existing analogue of the project's shell script: a declarative YAML of shots with `width`/`height`/`wait_for`/`javascript`/`selector`, including a `server:` key that starts the app and kills it afterwards. Its gaps are no first-class dark-mode flag (would need `--javascript` or `--browser-arg`) and Python/pip as a dependency.
- Playwright MCP and Chrome DevTools MCP both install into Claude Code and Codex with one command and run headless (`--headless`), so the builder could use them for clickable states and keep the shell script for the three static shots. Chrome DevTools MCP's `emulate` tool covers dark mode and DPR directly, and its `--screenshotMaxWidth/--screenshotMaxHeight` flags downscale images before they reach the model, which matters for the resolution limits in question 4. Both default to headed mode, so headless must be passed explicitly.
- First-party agent browsers (Claude in Chrome, Codex for Chrome, Claude Code computer use) are interactive-only or app-only (computer use explicitly excludes `-p`; Codex's extension excludes the CLI), so they fit the builder's "use its own browser tools for states that need clicks" step but not the headless reviewer step.
- Default-headed MCP servers and the archived Puppeteer MCP are reliability risks for an unattended loop: the former pops windows unless `--headless` is set, the latter gets no fixes.

### Gaps
- I could not fetch a primary definition for `--hide-scrollbars`, `--force-device-scale-factor`, or `--run-all-compositor-stages-before-draw` (the developer.chrome.com headless CLI reference returned 404 and the peter.sh switch list was too long to read at the right offset); whether `--force-device-scale-factor=2` combines with `--screenshot` remains unverified here.
- Whether Playwright MCP exposes a `--color-scheme` flag or a `contextOptions` block in its `--config` file was not visible in the README extracts; dark mode through Playwright MCP may require `browser_run_code_unsafe` calling `page.emulateMedia`.
- browser-use's headless behaviour and default screenshot sizes were not documented in the pages fetched.
- The Codex browser-use facts come from one third-party blog; OpenAI's own docs for the Chrome plugin were not fetched.

## Key question 2: Existing design-review skills and agents (structure of must-fix vs suggestion, checklists, how screenshots reach the model)

### Takeaway
The most complete public design-review agent (OneRedOak's `design-review`) runs a seven-phase live-browser audit through Playwright MCP at 1440/768/375 px and reports a four-level triage (Blocker, High-Priority, Medium-Priority, Nitpick) with "problems over prescriptions"; Vercel's web-interface-guidelines skill is code-only with a terse `file:line - [guideline] fix` format and 100+ rules; Anthropic's `frontend-design` skill is a build skill that only tells the builder to screenshot and self-critique. None of them separates "stated user goal not met" from aesthetic findings the way the project does, and all MCP-based ones feed screenshots to the model inline as tool results rather than as files read later.

## Key question 3: Visual regression tooling as objective checks (BackstopJS, Playwright toHaveScreenshot, Chromatic, Percy, Argos, Lost Pixel, reg-suit) and fit as a cheap gate in an agent loop

### Takeaway
Pixel diffing is cheap to add locally (Playwright's `toHaveScreenshot`, BackstopJS, or bare `pixelmatch` on two PNGs) but only answers "did unchanged areas change?", and all tools warn that rendering differs across OS, headless mode and even power source; the SaaS options (Chromatic, Argos, Percy) move diffing to the cloud, Lost Pixel was archived in April 2026, and Argos's ARIA-snapshot diffing is the one idea that extends "objective diff" beyond pixels.

### Cited Findings
- Playwright `toHaveScreenshot`: on first run the runner "took a bunch of screenshots until two consecutive screenshots matched, and saved the last screenshot to file system"; files are named `{test-name}-{browser}-{platform}.{extension}` (e.g. `example-test-1-chromium-darwin.png`); update with `npx playwright test --update-snapshots`; warning: "Browser rendering can vary based on the host OS, version, settings, hardware, power source (battery vs. power adapter), headless mode, and other factors."; `stylePath` injects CSS to hide dynamic elements — [playwright.dev test-snapshots](https://playwright.dev/docs/test-snapshots)
- Options: `maxDiffPixels` ("An acceptable amount of pixels that could be different"), `maxDiffPixelRatio` (0–1), `threshold` ("An acceptable perceived color difference in the YIQ color space ... Defaults to `0.2`"), `animations: "disabled"` ("stops CSS animations, CSS transitions and Web Animations"), `caret`, `clip`, `fullPage`, `mask` ("Masked elements will be overlaid with a pink box"), `maskColor` default `#FF00FF`, `omitBackground`, `scale`, `stylePath`, `timeout`; the assertion "will wait until two consecutive page screenshots yield the same result"; "screenshot assertions only work with Playwright test runner" — [playwright.dev PageAssertions](https://playwright.dev/docs/api/class-pageassertions#page-assertions-to-have-screenshot-1)
- pixelmatch (the library Playwright uses): "A small, simple and fast JavaScript pixel-level image comparison library, originally created to compare screenshots in tests."; `pixelmatch(img1, img2, output, width, height[, options])` "returns the number of mismatched pixels"; `threshold` default 0.1; `includeAA` ("If true, disables detecting and ignoring anti-aliased pixels"); `diffMask`; `windowSize`; "All three images need to have the same dimensions."; CLI `pixelmatch image1.png image2.png [diff.png] [threshold] [includeAA]` — [mapbox/pixelmatch](https://github.com/mapbox/pixelmatch)
- BackstopJS: `backstop init` / `backstop test` / `backstop approve`; `viewports` with `label`, `width`, `height`; scenario keys `selectors`, `hideSelectors`, `removeSelectors`, `misMatchThreshold` (percentage 0.00–100.00), `delay`, `readyEvent`, `readySelector`, `clickSelector`, `hoverSelector`, `postInteractionWait`, `requireSameDimensions`; `engine` `puppeteer` (default) or `playwright` (chromium/firefox/webkit); reports `browser`, `CI` (JUnit), `json`; `--docker` to eliminate cross-platform rendering variation; comparison via Resemble.js — [garris/BackstopJS](https://github.com/garris/BackstopJS); latest version 6.3.25, MIT, "Pixel-based via Resemble.js", Docker flakiness tracked in issues #1156 and #1303 — [cloudzy comparison (2026-07-08, secondary)](https://cloudzy.com/blog/argos-vs-lost-pixel-vs-backstopjs-compared/)
- Lost Pixel: archived 22 April 2026 when the team joined Figma; "No migration guidance accompanied the sunset." — [cloudzy (secondary)](https://cloudzy.com/blog/argos-vs-lost-pixel-vs-backstopjs-compared/)
- Argos: "MIT code, managed SaaS product"; maintainer "Provides no support or documentation for running it outside of the managed service" (September 2025); ARIA snapshot diffing added 4 November 2025 "compares the accessibility tree (roles, labels, and structure) alongside the pixel screenshot"; snapshot-based pricing — [cloudzy (secondary)](https://cloudzy.com/blog/argos-vs-lost-pixel-vs-backstopjs-compared/)
- Chromatic with Playwright: "Chromatic captures full-page archives (including DOM, styling, and assets) of your test cases"; archives are uploaded and "Chromatic generates snapshots and performs pixel diffing"; install `chromatic` and `@chromatic-com/playwright`, swap the test import, run `npx playwright test`, then `npx chromatic --playwright -t=<TOKEN>`; review by approving each diff, which "updates the baselines"; cloud-only — [chromatic.com/docs/playwright](https://www.chromatic.com/docs/playwright/)
- reg-suit (per a 2026 roundup surfaced in search, page not fetched): bring-your-own images diffed against Git-keyed baselines, reports to S3/GCS, notifications to GitHub/GitLab/Slack, MIT, v0.14.6 released March 2026 — [21st.dev roundup (secondary, snippet only)](https://21st.dev/blog/lost-pixel-alternatives)

### Inferences
- A cheap gate for the project's loop is "re-capture the same three viewports before and after the change on pages the task did not touch, run `pixelmatch` with a small `maxDiffPixels`, and treat any diff as a must-fix candidate for the reviewer to look at". It needs identical dimensions (so fixed `--window-size` captures, not `fullPage`, or `requireSameDimensions`-style handling), `animations` disabled, and masking of clocks/avatars; all of that is simpler in Playwright than in the headless CLI.
- Within the changed page a pixel diff is not a pass/fail signal, since the change is supposed to alter pixels; its value there is as a reviewer aid (a diff mask image highlights exactly what moved, which helps a vision model that is weak at spotting small shifts).
- Baselines generated on macOS headless Chrome should be compared only against captures from the same machine and mode, per Playwright's rendering warning; the project's single-machine, same-session before/after comparison satisfies this, whereas committing baselines to the repo would not.
- Argos's ARIA-snapshot diff suggests a non-pixel objective check the project could do for free: `browser_snapshot`/`take_snapshot` (or Playwright `ariaSnapshot`) before and after, diffed as text, catches "information no longer reachable" and label changes with zero rendering noise.
- SaaS tools (Chromatic, Argos, Percy) add accounts, tokens and uploads, which conflicts with the project's local, two-agent loop; BackstopJS and bare pixelmatch do not.

## Key question 4: Feeding images to reviewers (`codex exec --image`, Claude Code reading PNGs in `-p` mode, resolution guidance, whether 1440x4000 should be tiled)

### Takeaway
Codex accepts `--image`/`-i` with comma-separated or repeated paths and no documented count or size limit; Claude Code's `Read` tool is documented as presenting images visually, but a February 2026 issue reports that in `-p` mode the model fabricated image content 100% of the time when the image did not actually arrive, so the project should verify delivery with a canary. Anthropic's documented resize rule means a 1440x4000 capture shrinks to about 564x1568 on standard-tier models (16 px text becomes about 6 px) and about 927x2576 on high-resolution-tier models, so full-page captures should be tiled into viewport-height slices or cropped to components.

The edge limit takes over only for elongated images such as panoramas or tall phone screenshots."; images are padded to multiples of 28 on bottom/right; `"transformations": { "oversized_image": "error" }` rejects instead of resizing; "Small elements lose precision when an image is downscaled: for fine targets, crop the region of interest and send the crop" — [platform.claude.com vision-coordinates](https://platform.claude.com/docs/en/build-with-claude/vision-coordinates)
- Computer-use guidance: "For general desktop tasks, use 1024x768 or 1280x720; for web applications, use 1280x800 or 1366x768."; "Avoid resolutions above 1920x1080 to prevent performance issues."; `zoom` action for "small text or specific UI elements that aren't legible at the screenshot's default resolution"; troubleshooting "Accuracy consistently poor → Resolution too low → Try 1280x720 as a baseline" — [computer use tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)

OpenAI vision guidance (page as fetched 2026-10-07)
- Formats "PNG (`.png`), JPEG (`.jpeg` or `.jpg`), WEBP (`.webp`), and non-animated GIF (`.gif`)"; stated limits "Up to 1,500 images per request", 512 MB total payload, "up to 30,000 patches per image"; `detail` values `low` ("Coarse image understanding"), `high` ("Standard high-fidelity image understanding"), `original` ("Large, dense, spatially sensitive, or computer-use images"); low detail "fits within 512 × 512 pixels"; high detail on gpt-5.1/4o-class models scales to fit 2048×2048 then shortest side to 768 px and tokenises in 512 px tiles; patch models use "32px x 32px patches" with `ceil(width/32)×ceil(height/32)` and a patch budget; the page also lists a high-detail cap of "up to 2,500 patches and a 65,535-pixel maximum dimension" for a newer model — [developers.openai.com images-vision](https://developers.openai.com/api/docs/guides/images-vision)
- Limitations: "Small text" without enlargement, "Rotated or upside-down text", "Images with text of non-Latin alphabets", graphs where colors or styles vary, precise spatial localisation, panoramic/fisheye, approximate counting, CAPTCHAs blocked, metadata ignored — [developers.openai.com images-vision](https://developers.openai.com/api/docs/guides/images-vision)

Tool-level image controls
- Playwright MCP `--image-responses allow|omit|only` controls whether screenshots are returned to the model inline — [playwright-mcp README](https://github.com/microsoft/playwright-mcp); Chrome DevTools MCP `--screenshotMaxWidth`/`--screenshotMaxHeight` "Downscale images before return" — [configuration.md](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/configuration.md)
- A practitioner post states Playwright MCP gained `scale=device` on 25 June 2026 and gives GPT-5.4/5.5 "high" detail as 2048 px / 2,500 patches and "original" as 6000 px / ~10,000 patches — [Digital Applied (secondary, partly unsourced)](https://www.digitalapplied.com/blog/screenshot-driven-ui-development-vision-models-2026); the 6000 px / 10,000-patch figure conflicts with the OpenAI page's "65,535-pixel maximum dimension" wording and is unverified.

### Inferences
- Applying Anthropic's documented rule to the project's three sizes (my computation from the published formula): 1440x900 costs 52×33 = 1716 tokens, so on standard-tier models it is scaled slightly to about 1372x857 (49×31 = 1519 tokens), and on high-res models it is sent unchanged; 390x844 (14×31 = 434 tokens) is never resized; 1440x4000 hits the edge limit, shrinking to about 564x1568 on standard tier (scale 0.39, so 16 px UI text renders at about 6 px) and about 927x2576 on high-res tier (scale 0.64, 16 px to about 10 px). A tall full-page PNG is therefore the one capture most likely to produce "content cut off / too small" false findings or missed findings. Tiling it into 1440x900 slices (or `fullPage` cropped into ≤1568 px tall tiles with a small overlap) keeps text legible on both tiers.
- For Codex the same logic holds under its tile/patch schemes: a 512 px low-detail path would make 1440-wide text unreadable, so the reviewer prompt should not rely on defaults; the project cannot set `detail` from `codex exec --image`, so pre-sizing is the only lever.
- The `-p` hallucination report is directly relevant: if `Read` fails to return pixels (transparent PNGs, API media rejections) the headless reviewer may invent findings. A cheap guard is a canary: include a tiny PNG containing a random word and require the reviewer to transcribe it first, or ask it to state the pixel dimensions of each screenshot; mismatches mean the images did not arrive. Using `--output-format json` plus `--json-schema` lets the builder parse a `must_fix` array and the canary field mechanically.
- Anthropic's "images before text" and "Image 1:" labelling guidance maps onto the project's `design-context.md`: the reviewer prompt should reference screenshots by the same names as the file list and put the context after the images where the tool allows ordering.
- Because Claude Code's `-p` run kills background Bash about five seconds after the final result, the builder must keep the app running in its own session (as the project does) rather than letting the reviewer start it.

### Gaps
- No official Codex documentation of count, byte-size or pixel limits for `--image` was found; the "20 MiB decoded per item" figure that surfaced in search belongs to OpenCode, not Codex, and should not be reused.
- Whether Claude Code's `-p` mode can take images via `--input-format stream-json` user messages was not covered by the headless page I fetched.
- The exact current Claude Code behaviour of `Read` on PNGs in `-p` (fixed, regressed, or model-dependent) is unknown; the issues are closed as duplicates without visible resolution.
- The OpenAI page's limit figures (1,500 images, 512 MB, 30,000 patches) differ from older widely quoted values (500 images, 50 MB); I report the page as fetched and flag the discrepancy.

## Key question 5: Best-practice checklists for judging UI from screenshots, and documented weaknesses of vision models at this task

### Takeaway
Published checklists converge on the same screenshot-checkable items (overflow/clipping/overlap, horizontal scroll at phone width, contrast and minimum text size, focus visibility, empty/loading/error states, realistic data, dark mode, 8-pt spacing rhythm), while the research record shows general vision-language models score near chance on holistic "which design is better" judgments (GPT-4V 51.58% on UIClip's pairwise test) and produce plausible but wrong critiques unless grounded with bounding boxes and explicit guidelines; vendors themselves document weak counting, approximate localisation and small-text failures.

### Cited Findings

Checklists
- OneRedOak phases cover interactive states (hover, active, disabled), destructive-action confirmations, three viewports with "no horizontal scrolling or element overlap", alignment/spacing/typography/colour consistency, keyboard order and visible focus, form labels, alt text, "color contrast ratios (4.5:1 minimum)", invalid-input and overflow stress tests, "loading, empty, and error states", design-token use, copy clarity and console errors — [design-review-agent.md](https://raw.githubusercontent.com/OneRedOak/claude-code-workflows/main/design-review/design-review-agent.md)
- OneRedOak principles: 8 px base spacing, 150–300 ms motion, states default/hover/active/focus/disabled/loading/error/empty, 44x44 px touch targets, WCAG AA contrast, dark palette required — [design-principles-example.md](https://raw.githubusercontent.com/OneRedOak/claude-code-workflows/main/design-review/design-principles-example.md)
- Vercel rules usable from screenshots: ≥16 px mobile input text, ≥24 px hit targets (44 px mobile), visible focus ring, truncation/line-clamp/`min-w-0` for overflow, spinner timing, `color-scheme: dark`, safe-area insets, no unwanted scrollbars, `text-wrap: balance`, tabular numerals, destructive confirmation — [web-interface-guidelines](https://github.com/vercel-labs/web-interface-guidelines), [command.md](https://raw.githubusercontent.com/vercel-labs/web-interface-guidelines/main/command.md)
- web-design-reviewer rubric: Element Overflow, Element Overlap, Alignment, Inconsistent Spacing, Text Clipping, Non-mobile Friendly, Breakpoint Issues, Touch Targets, Insufficient Contrast, No Focus State, Missing alt, Font/Color/Spacing inconsistency, at 375/768/1280/1920 — [claudeskills.info](https://claudeskills.info/skills/galaxy-dawn/claude-scholar/web-design-reviewer/)
- Anthropic `frontend-design` tells that double as review heuristics: identical rounded cards with the same grey shadow, ALL-CAPS eyebrow labels on every heading, "A · B · C" meta strings, "→" on every button, accenting a single word in a headline, line length over 80 characters, scattered fade-and-slide entrances — [frontend-design SKILL.md](https://github.com/anthropics/skills/blob/main/skills/frontend-design/SKILL.md)
- Practitioner heuristics for critique prompts: 8-point spacing scale, WCAG 2.2 AA 4.5:1 for normal text, line-heights on a 4 px grid, "Internal padding ≤ external margins for visual grouping"; the same post lists what single frames cannot show: "Hover, focus, active, and disabled require triggering; the frame shows only the state captured", motion ("the model sees a single frame, not a timeline"), below-fold content, cross-browser variance, alternate data states — [Digital Applied (secondary)](https://www.digitalapplied.com/blog/screenshot-driven-ui-development-vision-models-2026)
- Anthropic image-quality guidance: ensure text is "legible and not too small", pre-resize or crop, avoid heavy compression — [Vision](https://platform.claude.com/docs/en/build-with-claude/vision)

Documented weaknesses of vision models at UI judgment
- UIClip (Wu et al., 2024): "all LVLMs performed very poorly on design quality assessment, often around the level of random guessing"; "GPT-4V (overall 51.58%)"; LLaVA 54.59% "since LLaVA was not trained to refuse requests"; test sets of 201 pairs each (BetterApp rated by 12 designers, JitterWeb synthetic); "GPT-4V erroneously associated certain types of jitters (e.g., dark, unreadable backgrounds) with better design", producing "realistic-sounding but inaccurate reasoning"; the specialised UIClip model reached 75.12% — [arXiv 2404.12500 (HTML)](https://arxiv.org/html/2404.12500v1)
- Duan, Cheng, Hartmann, Li (2024, rev. 2025): multimodal LLMs "often struggle with generating high-quality design critiques -- a complex task that requires producing detailed design comments that are visually grounded in a given design's image"; their pipeline takes "UI screenshots and design guidelines as input" and emits comments paired with bounding boxes via "iterative refinement of text output and bounding boxes using few-shot samples tailored for each step"; with Gemini-1.5-pro and GPT-4o "human experts generally preferred the design critiques generated by our pipeline over those by the baseline, with the pipeline reducing the gap from human performance by 50% for one rating metric" — [arXiv 2412.16829](https://arxiv.org/abs/2412.16829)
- Anthropic: approximate counting ("especially with large numbers of small objects"), approximate localisation, errors on "low-quality, rotated, or very small images under 200 pixels" — [Vision](https://platform.claude.com/docs/en/build-with-claude/vision); "Always carefully review and verify Claude's image interpretations, especially for high-stakes use cases." — [Vision](https://platform.claude.com/docs/en/build-with-claude/vision)
- OpenAI: unreliable on "Small text", rotated text, non-Latin scripts, graphs with varying colours/styles, precise spatial tasks, approximate counting — [images-vision](https://developers.openai.com/api/docs/guides/images-vision)
- Claude Code's own fix for small text on screen is zoom, not resolution: the computer-use `zoom` action exists "when asked about small text or specific UI elements that aren't legible at the screenshot's default resolution, such as file names in a sidebar, tab titles, status-bar text, line numbers, or button labels" — [computer use tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)
- A third-party evaluation cited by a blog reports a frontier model at "30% precise object counting (3/10 prompts)" versus 78.9% spatial understanding — [Digital Applied citing Roboflow (secondary, unverified)](https://www.digitalapplied.com/blog/screenshot-driven-ui-development-vision-models-2026)
- Failure mode when images do not arrive: 100% fabricated descriptions in `claude -p` per the bug report in question 4 — [anthropics/claude-code #25960](https://github.com/anthropics/claude-code/issues/25960)

### Inferences
- The evidence favours the project's reviewer prompt design: it asks for concrete, verifiable defects (goal not met, cut-off, overlap, unreachable information, broken phone layout, unknown-as-zero) first and caps aesthetic suggestions at five. The UIClip result argues against ever asking the reviewer "is this good design?" as a gate.
- Counting is explicitly weak in both vendors' docs, yet the project's must-fix list says "counting where countable". Mitigations: have the builder state expected counts in `design-context.md` (so the reviewer verifies rather than counts freely), keep countable items large in the frame (crop to the list or table), and treat count disagreements as "verify" rather than automatic must-fix.
- Grounding improves critiques (Duan et al.), so requiring each finding to name the screenshot and a location, as the project already does, is supported; going further, asking for a bounding box or the nearest visible label of the defect would make findings checkable by the builder and discourage generic complaints.
- Single frames cannot show hover, focus, motion or below-fold content; the project's per-task state screenshot should default to including focus (a Tab press) and the empty/loading/error states when the task touches them, and the builder should say in `design-context.md` which states were not captured so the reviewer does not report their absence as a defect.
- Dark mode is absent from the project's capture set while two of the surveyed checklists require it; with Playwright or Chrome DevTools MCP it is one extra `colorScheme` capture per viewport.
- Realistic data, which the project already requires, matters more for a vision reviewer than for a code reviewer because placeholder text hides truncation and zero-state bugs that only appear with long names and large numbers.

### Gaps
- No peer-reviewed study was found that benchmarks current (2026) frontier models on defect-finding in UI screenshots (truncation, overlap, contrast) as opposed to holistic quality ranking; the UIClip and Duan et al. results are from 2024-model generations.
- The "OverlayQA" practitioner taxonomy and the Roboflow counting figure were only available second-hand via a blog.
- WCAG/APCA numeric checks cannot be done reliably from a screenshot by a vision model; the sources treat contrast as something to measure with a tool (axe, Lighthouse, a contrast checker), and no source quantified how accurately a model estimates contrast ratios from pixels.
