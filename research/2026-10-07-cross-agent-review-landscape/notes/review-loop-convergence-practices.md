# Iterative build-review-fix loops with coding agents: loop designs, stopping criteria, guardrails and failure modes (as of 2026-10-07)

Scope note: this covers how practitioners run builder/reviewer loops, what stops them, what keeps them from drifting or being tampered with, how decisions are remembered across rounds, and how findings are verified. Material older than 2026 is marked "(older)". Dates are the publication or issue-open dates as given on the page. All URLs were fetched directly unless marked "via".

## Key question 1: Reference loop designs

### Takeaway
Every reference design separates the agent that does the work from the agent that judges it, gives the judge a narrow brief (correctness, not style), and bounds the loop with something mechanical (iteration cap, hook block cap, time budget) rather than trusting the model to stop. The newest Anthropic and OpenAI designs add a second step that tries to refute each finding before it is reported.

### Cited Findings

Anthropic's evaluator-optimizer pattern (older, Dec 2024)
- "In the evaluator-optimizer workflow, one LLM call generates a response while another provides evaluation and feedback in a loop." It fits "when we have clear evaluation criteria, and when iterative refinement provides measurable value", with two preconditions: "LLM responses can be demonstrably improved when a human articulates their feedback" and "the LLM can provide such feedback." No stopping rule is given for the pattern itself; for agents generally "it's also common to include stopping conditions (such as a maximum number of iterations) to maintain control." — [Anthropic, Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)

Claude Code best practices (current doc; the 2025 blog post now redirects here)
- Four ways to gate a stop on a check, in order of setup cost: in one prompt; across a session with `/goal` ("A separate evaluator re-checks it after every turn"); "As a deterministic gate: a Stop hook runs your check as a script and blocks the turn from ending until it passes"; "By a second opinion: a verification subagent or a dynamic workflow that checks its own findings has a fresh model try to refute the result, so the agent doing the work isn't the one grading it." — [Claude Code docs, Best practices](https://code.claude.com/docs/en/best-practices)
- Writer/Reviewer pattern: "A fresh context improves code review since Claude won't be biased toward code it just wrote." Session A implements, Session B reviews a named file for "edge cases, race conditions, and consistency", Session A gets "Here's the review feedback: [Session B output]. Address these issues." — [same](https://code.claude.com/docs/en/best-practices)
- Adversarial review step: "A reviewer running in a fresh subagent context sees only the diff and the criteria you give it, not the reasoning that produced the change." Suggested prompt includes "nothing outside the task's scope changed. Report gaps, not style preferences." — [same](https://code.claude.com/docs/en/best-practices)
- The documented over-review failure mode: "A reviewer prompted to find gaps will usually report some, even when the work is sound, because that is what it was asked to do. Chasing every finding leads to over-engineering: extra abstraction layers, defensive code, and tests for cases that can't happen. Tell the reviewer to flag only gaps that affect correctness or the stated requirements, and treat the rest as optional." — [same](https://code.claude.com/docs/en/best-practices)
- Course-correction rule: "If you've corrected Claude more than twice on the same issue in one session, the context is cluttered with failed approaches. Run /clear and start fresh". Plan mode: "If you could describe the diff in one sentence, skip the plan." Verification: "Have Claude show evidence rather than asserting success". — [same](https://code.claude.com/docs/en/best-practices)

Claude Code `/goal` (session-scoped evaluator loop)
- "/goal is a wrapper around a session-scoped prompt-based Stop hook." After each turn the condition and conversation go to "your configured small fast model", which returns "Not yet met", "Met" or "Impossible". "It doesn't run commands or read files independently, so write the condition as something Claude's own output can demonstrate." Stall rule: "If Claude keeps answering the evaluator without making progress (no tool use for several turns in a row), Claude Code stops the loop, prints a warning, and returns control to you with the goal still set." Budgeting: "To bound how long a goal runs, include a turn or time clause in the condition, such as `or stop after 20 turns`." — [Claude Code docs, /goal](https://code.claude.com/docs/en/goal)

Claude Code hooks as loop drivers and gates
- Stop hook: `decision: "block"` with a `reason` "prevents Claude from ending the turn"; exit code 2 also blocks and "the hook's stderr becomes the blocking reason". Stop hooks receive `stop_hook_active` ("true when Claude Code is already continuing as a result of a stop hook. Check this value or process the transcript to avoid blocking on a condition that will never resolve") and `last_assistant_message`. — [Claude Code docs, Hooks reference](https://code.claude.com/docs/en/hooks)
- Hard ceiling: "Claude Code applies an 8-consecutive-continuation cap: after stop hooks have continued the turn eight times in a row, Claude Code overrides the next block and ends the turn. The count of consecutive continuations resets each time Claude calls a tool. To raise the cap, set CLAUDE_CODE_STOP_HOOK_BLOCK_CAP." — [same](https://code.claude.com/docs/en/hooks)
- PreToolUse returns `permissionDecision` of `allow`, `deny`, `ask` or `defer`; the doc's own example denies with `permissionDecisionReason: "Git push requires code review approval"`. TeammateIdle and TaskCompleted hooks: "Exit with code 2 to send feedback and keep the teammate working" / "to prevent completion and send feedback". — [same](https://code.claude.com/docs/en/hooks); [Agent teams](https://code.claude.com/docs/en/agent-teams)

Claude Code subagents as reviewers
- Reviewer definition uses `tools: Read, Glob, Grep`, optional `disallowedTools: Write, Edit`, and `permissionMode: plan` ("recommended for reviewers"). A subagent starts with "System prompt, Task message, CLAUDE.md files, Git status snapshot" and without "Conversation history" or "Previous file reads". Limits: nesting depth 3, 20 concurrent. `memory: project` writes to `.claude/agent-memory/<name>/` for "cross-session learning". Resumable via `SendMessage` (built-in Explore/Plan are one-shot). — [Claude Code docs, Subagents](https://code.claude.com/docs/en/sub-agents)

Claude Code agent teams as reviewers (experimental)
- Strongest use cases include "Research and review: multiple teammates can investigate different aspects of a problem simultaneously, then share and challenge each other's findings". The parallel review example assigns security, performance and test-coverage lenses because "A single reviewer tends to gravitate toward one type of issue at a time." The debugging example makes teammates "explicitly adversarial" to counter anchoring. Warnings: "Letting a team run unattended for too long increases the risk of wasted effort" and "The lead can stop early too, deciding the team is finished before all tasks are actually complete." Not available in `-p` mode. — [Claude Code docs, Agent teams](https://code.claude.com/docs/en/agent-teams)

Anthropic's multi-agent Code Review and ultrareview (verify-then-report)
- "multiple agents analyze the diff and surrounding code in parallel on Anthropic infrastructure. Each agent looks for a different class of issue, then a verification step checks candidates against actual code behavior to filter out false positives. The results are deduplicated, ranked by severity, and posted". Average 20 minutes; "$15-25" per review; the check run "always completes with a neutral conclusion so it never blocks merging". Default focus: "bugs that would break production, not formatting preferences or missing test coverage." — [Claude Code docs, Code Review](https://code.claude.com/docs/en/code-review)
- Ultrareview (cloud `/code-review ultra`): "every reported finding is independently reproduced and verified, so the results focus on real bugs rather than style suggestions"; "roughly 5 to 10 minutes"; "$5 to $25"; branch limit "up to 500 changed files and 8,000 changed lines by default"; `claude ultrareview` subcommand with `--timeout` default 45 minutes and exit codes 0/1/130 for CI. — [Claude Code docs, Ultrareview](https://code.claude.com/docs/en/ultrareview)
- Reported outcome: "Fewer than 1% of findings were marked incorrect by engineers during internal use"; "The number of agents assigned scales with pull request size and complexity"; after adoption at Anthropic "Substantive review comments increased from 16% of pull requests to 54%"; PRs over 1,000 lines "84% generated findings, with an average of 7.5 issues"; under 50 lines "31% ... averaging 0.5 issues". — [InfoQ, 2026-04-17](https://www.infoq.com/news/2026/04/claude-code-review/); the verification step is also described by [DevOps.com](https://devops.com/anthropic-code-review-dispatches-agent-teams-to-catch-the-bugs-that-skim-reads-miss/) (not fetched; via search)

Anthropic long-running harnesses (generator/evaluator)
- (older, 2025-11-26) Harness: an initializer agent writes `init.sh`, `claude-progress.txt` and an initial commit; later sessions read "the progress notes file and git commit logs"; a feature-list JSON is edited "only by changing the status of a passes field"; "work on only one feature at a time"; "Only mark features as 'passing' after careful testing." Failure modes: declaring done prematurely, leaving a feature "half-implemented and undocumented", "running out of context in the middle of its implementation". — [Anthropic, Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- (2026-03-24) Planner/generator/evaluator: "When asked to evaluate work they've produced, agents tend to respond by confidently praising the work—even when, to a human observer, the quality is obviously mediocre." "Out of the box, Claude is a poor QA agent ... It took several rounds of this development loop before the evaluator was grading in a way that I found reasonable." "I ran 5 to 15 iterations per generation" before plateauing. Costs: full harness 6 h / $200 vs solo 20 min / $9; DAW run 3 h 50 min / $124.70. Models show "context anxiety, in which they begin wrapping up work prematurely as they approach what they believe is their context limit". — [Anthropic, Harness design for long-running apps](https://www.anthropic.com/engineering/harness-design-long-running-apps)

Ralph Wiggum loop
- (older, 2025-07-14) `while :; do cat PROMPT.md | claude-code ; done`. "Only one thing" per loop; files: PROMPT.md, specs, fix_plan.md (regenerated and discarded), AGENT.md (self-updating learnings). Tests are the "backpressure"; "1 subagent for build/test; up to 500 for search". The loop "doesn't inherently stop"; the author intervenes by regenerating the plan or `git reset --hard`. Failure modes: assuming code is not implemented, placeholder implementations, context corruption, contradictory specs. "$297 USD" for a "$50k" contract; best for greenfield. — [Geoffrey Huntley, Ralph](https://ghuntley.com/ralph/)
- Anthropic's plugin: `/ralph-loop "<prompt>" --max-iterations <n> --completion-promise "<text>"`; the Stop hook "blocks normal session exit" and "re-feeds the SAME prompt"; completion is exact string match on `<promise>…</promise>`, so "you cannot use it for multiple completion conditions (like "SUCCESS" vs "BLOCKED"). Always rely on --max-iterations as your primary safety mechanism." Not for "Tasks requiring human judgment or design decisions" or "Tasks with unclear success criteria". — [anthropics/claude-code, ralph-wiggum plugin](https://github.com/anthropics/claude-code/tree/main/plugins/ralph-wiggum)
- Practitioner variants: cap "5–10 iterations" to start, `MAX_ITERATIONS=${1:-10}`, a `progress.txt` log, and an explicit stuck exit ("document what's blocking you in progress.txt, commit what you have, and output `<promise>STUCK</promise>`"); "roughly $10 an hour in API credits"; "Without backpressure, the loop will cheerfully commit broken code and tell you it's done." — [Steve Kinney, 2026-03-31](https://stevekinney.com/writing/the-ralph-loop). Named failure modes: hallucinated "done" ("outputs the completion promise without running checks"), context pollution, permission dead-ends, cost blow-ups; cap "10 to 25. Treat it as a circuit breaker." — [Ralph Wiggum Loop, January 2026 snapshot](https://ai-assisted-software-development.com/ralph-wiggum-loop-january-2026-snapshot/). "For every overnight win, there are loops that burned through iterations without converging"; "A 50-iteration loop on a large codebase can easily cost $50-100+". — [paddo.dev](https://paddo.dev/blog/ralph-wiggum-autonomous-loops/)

Codex CLI loop building blocks
- `codex exec` "runs in a read-only sandbox" by default; `--sandbox workspace-write` to "Allow edits"; `--json` (JSON Lines), `-o/--output-last-message <path>`, `--output-schema <path>`, `--ephemeral`, `-C <dir>`, `--skip-git-repo-check`; `codex exec resume --last "continue with next task"` or `codex exec resume <SESSION_ID>`; `codex exec -` reads the prompt from stdin. — [OpenAI Codex docs, Non-interactive mode](https://developers.openai.com/codex/noninteractive) (redirects to https://learn.chatgpt.com/docs/non-interactive-mode)
- Pipelines gate on exit codes (`if ! codex exec --sandbox workspace-write "Fix the failing tests"; then`), chain stages via `--output-schema` ("the response will indicate failure rather than producing malformed output"), and use `codex exec fork` to branch "without mutating original transcript". — [Daniel Vaughan, 2026-05-03](https://codex.danielvaughan.com/2026/05/03/codex-cli-non-interactive-pipelines-exec-resume-structured-output/)
- Codex's own `/review` "launches a dedicated reviewer that examines diffs and reports prioritized findings without modifying your code"; after fixes "run another review and select 'Review uncommitted changes' to verify your fixes." — [OpenAI Help, Review pull requests with Codex](https://help.openai.com/en/articles/20001552-review-pull-requests-with-codex) (via search snippet; page not fetched)
- OpenAI "harness engineering" (Feb 2026): about 5 months, "over 1 million lines of code", "no manually typed code at all"; constraints enforced by "deterministic custom linters and structural tests"; periodic "garbage collection" agents "find inconsistencies in documentation or violations"; "When the agent struggles, we treat it as a signal". Fowler's critique: "What I am missing in the write-up is verification of functionality and behaviour." — [Birgitta Böckeler on martinfowler.com, 2026-02-17](https://www.martinfowler.com/articles/exploring-gen-ai/harness-engineering-memo.html); the primary post at https://openai.com/index/harness-engineering/ returned HTTP 403 to my fetch.

Superpowers (obra) subagent-driven development
- "a fresh implementer subagent per task"; two-stage review ("spec compliance AND task quality are both required"); the reviewer receives "the diff as a file, the task brief, the implementer's report, and global constraints"; findings "sent verbatim"; re-review is "scoped" to "the fix diff and previously flagged issues". "Five rounds maximum per task": rounds 1-3 resume the original implementer, rounds 4-5 "dispatch a fresh implementer on a more capable model", after round 5 the controller "adjudicates each open finding yourself". The controller "never dispatches multiple implementation subagents in parallel" and passes artifacts "as files". Hard stops: "an irreversible or destructive operation; a security-sensitive action; a side effect outside this worktree that norms say you ask about first; and a plan so broken that every path forward is a guess." — [obra/superpowers, subagent-driven-development](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md)
- Review request template fields: `{DESCRIPTION}`, `{PLAN_OR_REQUIREMENTS}`, `{BASE_SHA}`, `{HEAD_SHA}`; the reviewer gets "never your session's history". Severity: Critical ("Fix ... immediately"), Important ("before proceeding"), Minor ("Note ... for later"); "Push back if reviewer is wrong (with reasoning)". — [obra/superpowers, requesting-code-review](https://github.com/obra/superpowers/blob/main/skills/requesting-code-review/SKILL.md)

Autoresearch and metric-driven loops
- Karpathy's autoresearch: the agent edits one file (`train.py`), each experiment runs "a fixed 5-minute time budget", the single metric is `val_bpb` ("lower is better"), the agent "checks if the result improved, keeps or discards, and repeats"; "approx 12 experiments/hour and approx 100 experiments while you sleep". — [karpathy/autoresearch](https://github.com/karpathy/autoresearch). Reported run: "700 experiments over two days" yielding "20 distinct optimizations". — [noqta.tn](https://www.noqta.tn/en/blog/karpathy-autoresearch-autonomous-ai-experiments-loop-2026) (secondary; via search)

### Inferences
- The project's loop is closest to the Writer/Reviewer pattern plus superpowers' scoped re-review, with two features most reference designs lack: a reviewer from a different vendor and a diff-growth budget. The cross-vendor choice is supported by the Refute-or-Promote finding that "Cross-family review can catch correlated blind spots that same-family review misses" (see Q5).
- Anthropic's own docs now treat "a fresh model try to refute the result" as the standard second-opinion step; the project's triage is done by the builder, which is the self-judging configuration the harness post warns against. A cheap borrow: require the reviewer to attach confirmation evidence and let the builder reject only with counter-evidence (see Q5).
- Every hook-driven loop in the wild has a mechanical ceiling (ralph `--max-iterations`, Stop-hook 8-block cap, `/goal` stall detection, `--timeout 45`). The project relies on a trend rule and a diff budget but has no hard round cap; see Q2 for why practitioners add one anyway.

## Key question 2: Stopping criteria in use and their documented failure modes

### Takeaway
In practice loops stop on a hard round budget (2 to 6 is typical), with a raised bar after round one (must-fix or regression only), because trend-based and "zero findings" rules have well-documented failure modes: later rounds manufacture findings, fixes spawn most of the next round's findings, rounds contradict each other, and a budget exit is indistinguishable from convergence unless the loop reports which exit fired.

### Cited Findings

Rules in use
- Round budgets: "Round budget = 3 (maintainer decision). Round 1 reviews the full diff; later rounds review only the changes since the last reviewed commit. After round 1 the bar rises: only must-fix issues in the new changes, or regressions, keep the loop going." — [tmenguy/quiet-solar #375, 2026-09-26](https://github.com/tmenguy/quiet-solar/issues/375)
- "max 2 repair/re-review cycles per stage per unit; on the third, the loop stops and the operator decides"; "a finding blocks only if it names a user-visible outcome the frozen acceptance manifest would miss (or a contract violation). low/info findings are recorded and advisory — they never restart a cycle"; "a new review cycle cannot start while a decision-required finding is unresolved — enforced mechanically against the unit's decisions/ledger state". — [gtrabanco/agentic-workflow #205, 2026-09-09](https://github.com/gtrabanco/agentic-workflow/issues/205)
- Convergence budget on where findings land: "When two consecutive re-review rounds find blocking findings only in text the previous fix added, the coordinator raises one owner decision instead of another blind round." — [agentrof/agent-marketplace #427, 2026-10-05](https://github.com/agentrof/agent-marketplace/issues/427)
- Convergence signal rather than silent continuation: "When a round's findings are all Medium or lower and confined to the previous round's fix code, report to the owner with a recommendation instead of silently continuing." — [KBT-0/MyAgentKit_Keel #18, 2026-09-30](https://github.com/KBT-0/MyAgentKit_Keel/issues/18)
- Non-convergence detector: after "4+ rounds with mostly new low-severity findings", flag the pattern, "suppress new low-severity issues" and switch to a COMMENT verdict; target "No PR exceeding 6 consecutive CHANGES_REQUESTED reviews without a non-convergence signal". — [fullsend-ai/agents #1294, 2026-09-15](https://github.com/fullsend-ai/agents/issues/1294)
- Convergence-favoring verdicts for bot fix PRs: block only on "carry-over high-severity or new critical issues"; `max_review_iterations=5`; "termination is guaranteed by the architecture, not the model". — [dev.to, When AI reviews AI's code](https://dev.to/zoetaka38/when-ai-reviews-ais-code-youve-built-an-infinite-loop-heres-how-we-stopped-it-4g1n) (date as extracted "June 25, 2024" looks wrong for its content; treat as undated)
- Anthropic's REVIEW.md re-review rule: "after the first review, suppress new nits and post Important findings only" because it "stops a one-line fix from reaching round seven on style alone". Nit cap: "report at most five nits, mention the rest as a count in the summary". — [Claude Code docs, Code Review](https://code.claude.com/docs/en/code-review)
- Score-plus-verdict gate with cap: "score >= 6/10 AND verdict ∈ {ready, almost}", `MAX_ROUNDS = 4`. — [tessl auto-review-loop](https://tessl.io/registry/skills/github/wanshuiyin/Auto-claude-code-research-in-sleep/auto-review-loop--8c21efd9569d3829ffa2e644563bd256c9de45a444c23c47f16dd9e90eb3f128)
- Zero-findings-twice: "Convergence Criterion: Two consecutive verification passes with zero findings" on a 189-file refactor with "no pre-existing test oracle"; 14 spec refinement cycles plus 17 verification cycles, "201 defects were corrected before any human" ran it; $2,430 over three days. — [arXiv 2608.12440, 2026-08-12](https://arxiv.org/abs/2608.12440)
- Disposition-complete: "stop when every remaining finding is dispositioned accept (documented limit)" or clean. — [voodootikigod/adlc #156, 2026-07-12](https://github.com/voodootikigod/adlc/issues/156)
- Generation budgets with regression detection: "Ouroboros defaults to 3 generations, clamped 1-10"; "Detect oscillation and grade regression to stop loops that aren't converging"; "Only failed acceptance criteria advance to next generation". — [dev.to, Your agent loop is teaching the model to cheat, 2026-08-09](https://dev.to/q00/your-agent-loop-is-teaching-the-model-to-cheat-48oa)
- Fixed-size budgets as the primary stop: ralph `--max-iterations` ("Always rely on --max-iterations as your primary safety mechanism") — [ralph-wiggum plugin](https://github.com/anthropics/claude-code/tree/main/plugins/ralph-wiggum); Stop-hook "8-consecutive-continuation cap" — [Hooks reference](https://code.claude.com/docs/en/hooks); `/goal` "or stop after 20 turns" clause and stall stop — [/goal](https://code.claude.com/docs/en/goal); autoresearch's "fixed 5-minute time budget" per experiment — [karpathy/autoresearch](https://github.com/karpathy/autoresearch).

Documented failure modes
- Findings shift category each round instead of shrinking: "11 consecutive CHANGES_REQUESTED reviews"; round 2 naming, round 3 validation gaps, round 4 dead code, round 5 unicode symbols, round 7 stale base, round 8 commit types, round 11 test naming; "18 distinct inline findings (14 low-severity, 4 medium-severity)" and the agent "never identified the underlying architectural issue"; "The review agent reviews each iteration without awareness of the broader trajectory." — [fullsend-ai/agents #1294](https://github.com/fullsend-ai/agents/issues/1294)
- Fixes create the next round's findings: on one PR, "nine review rounds, 20 findings", "Roughly 17 of 20 findings were generated by the previous round's fix", "Roughly 3 were always latent"; other PRs ran "11 or more rounds over 46 hours" and "18" rounds. Mechanisms named: a parameter used for two contracts, and "twin path" defects where one path is fixed and "the next round found checks_ratchet untouched". Proposed rule: "list the callers you grepped and which you verified, so the omission is visible". — [rjmurillo/ai-agents #5487, 2026-09-02](https://github.com/rjmurillo/ai-agents/issues/5487)
- Same pattern measured across a fleet: of 91 Important findings raised after round 1, "40 (44%) appeared in code the previous fix changed", "32 (35%) in code round 1 saw and missed", "19 (21%) were repeats, with 8 re-raised after reasoned declines"; one PR of "+124 −79" took "7 pushes and 6 ai-review rounds in 70 min" and "Rounds 5 and 6 contradicted each other (drop the REVIEWED_TEAMS seam, then restore it)". Root causes: "fixes open new holes; stateless review re-raises declined findings; PR body drift; nit-only pushes trigger full rounds." — [MultiAgency/near-agencies #116, 2026-10-05](https://github.com/MultiAgency/near-agencies/issues/116)
- Decreasing-but-never-zero tail: "Blocking findings per round: 16, 5, 3, 2, 1, 1." Cause: "A fresh re-review reader reads only the changed text, and the severity table makes 'imprecision that could mislead a careful reader' major." — [agentrof/agent-marketplace #427](https://github.com/agentrof/agent-marketplace/issues/427)
- Unreachable stop condition: "PASS requires zero open material findings. Any fresh reviewer context handed a 60 KB spec (or a 91-commit branch) can always generate another string-level finding"; one unit had "12 review cycles", "81 findings", "64 of 91 branch commits were review/fold overhead", "~3,170 lines of process docs vs 2,409 lines of deliverable"; a spec grew "from ~33 KB to 60 KB" while "no finding ever disputed a business goal". — [gtrabanco/agentic-workflow #205](https://github.com/gtrabanco/agentic-workflow/issues/205)
- Controlled evidence that extra rounds add noise: on 30 artifacts with 150 seeded errors, single-pass review F1 0.376 vs multi-turn 0.303 and 0.263 (p < 0.001); false positives up 62% (8.5 vs 5.2), precision 0.30 to 0.20, recall only +0.08; "reviewers in later rounds fabricate findings when the artifact's real errors have been exhausted" and reviewers drift to critiquing the conversation rather than the artifact. — [arXiv 2603.16244, 2026-03-17](https://arxiv.org/abs/2603.16244)
- The verifier is stochastic, so a plain refinement loop has no convergence guarantee; "The max_iterations cap is a confession"; the worker learns "rhetorical surface features the verifier accepts". Diagnostic: "take the round-five 'accepted' output and feed it back through a fresh verifier instance with no trace history." Stabilizers: freeze verdicts before revision, "Sample-and-anchor: Run verifier k times in parallel, anchor loop to majority verdict", "Referee escalation: Third model provides final verdict after two rejections", "Spec-locking: Verifier emits acceptance criteria upfront". Cost example: 60% rejection with a five-round cap averages "about four full prompt-completion cycles per request". — [TianPan, 2026-05-31](https://tianpan.co/blog/2026/05/31/the-verifier-loop-that-couldnt-converge)
- Budget exit disguised as convergence: a 3-round, ~30-minute run ended with "37 findings" (more than it started with) and "7 blocking findings" unresolved after four reviewers raised the same issue with conflicting fix language ("reject," "strip," "ignore"); "The pipeline does not stop; it just stops trying"; a loop reaching its budget "looks identical to a loop exiting on convergence". — [Contrast Security, 2026-07-20](https://www.contrastsecurity.com/security-influencers/when-ai-reviewers-cannot-agree)
- Multi-round degradation in a benchmark: over 2,269 real multi-round review tasks (mean 3.8 rounds, range 2-10) the best model's F1 fell 56% from round 2 to round 10 (0.6495 to 0.2857); failure modes "State-Temporal Misalignment (32.5%)" (re-raising resolved defects as new), "Cross-Round Defect Forgetting (25.1%)", "Semantic Blindness (22.3%)". — [Daniel Vaughan on MCR-Bench, 2026-09-01](https://codex.danielvaughan.com/2026/09/01/mcr-bench-dynamic-code-review-multi-round-state-tracking-codex-cli/)
- Deadlock from parallel fixes: three findings in one file produced three fix PRs "each blocked by unresolved sibling findings"; fixed by coalescing findings per file into one task. — [dev.to zoetaka38](https://dev.to/zoetaka38/when-ai-reviews-ais-code-youve-built-an-infinite-loop-heres-how-we-stopped-it-4g1n)
- Ralph-style loops: "hallucinated done", "Infinite formatting wars or repeated test failures burn tokens", permission stalls — [Jan 2026 snapshot](https://ai-assisted-software-development.com/ralph-wiggum-loop-january-2026-snapshot/); "Without explicit instructions for what to do when stuck, the agent will spend every remaining iteration attempting the same impossible thing." — [Steve Kinney](https://stevekinney.com/writing/the-ralph-loop)
- Context rot in long sessions: "Claude's context window fills up fast, and performance degrades as it fills" — [Best practices](https://code.claude.com/docs/en/best-practices); "context anxiety" and loss of coherence — [Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps); "somewhere around the 15th exchange, you notice the agent is making suggestions that contradict things you told it 10 minutes ago" — [Steve Kinney](https://stevekinney.com/writing/the-ralph-loop).
- Agreement bias / false consensus: "ten reviewers unanimously endorsed a non-existent vulnerability until a single empirical test rejected it" — [arXiv 2604.19049](https://arxiv.org/abs/2604.19049); a "false-consensus failure mode" where agents converged without evidence, fixed by "a single prompt iteration that adds disagreement explicitly" — [arXiv 2608.18167](https://arxiv.org/abs/2608.18167).

### Inferences
- The project's "accepted count must fall; one plateau allowed; a rise stops" rule is a trend criterion that few others use; most use a hard budget of 2-5 rounds plus a raised bar. The trend rule is implicitly bounded (roughly initial-accepted-count plus two rounds), but with a large first round that bound is loose relative to the observed 4.3-round average and 18-round tails. A hard cap of 3-5 rounds alongside the trend rule would match current practice and TianPan's point that the cap, not the verifier, is what actually terminates.
- The agentrof "1, 1" tail shows the plateau-once rule doing useful work: the second identical count stops the loop. The MultiAgency and rjmurillo data (44% and roughly 85% of later findings in code the previous fix touched) support the project's "repeated finding means replace with a simpler rule" instruction and suggest logging, per finding, whether it lies in code the last fix changed; two consecutive rounds of only such findings is agentrof's escalation trigger.
- The project's diff-growth stop (50% or 200 lines) is unusual and well-motivated: gtrabanco's spec doubling, agentrof's "mechanism text", and Anthropic's over-engineering callout all describe growth as the symptom of a non-converging loop. I found no other loop that uses diff growth as an explicit stop.
- Contrast's point implies the end-of-loop report should name which exit fired (clean, count rose, plateau twice, diff budget) so a budget exit is never mistaken for convergence.
- The "More Rounds, More Noise" result and MCR-Bench's state-temporal misalignment both argue for the project's must-fix-only brief and delta re-review, and against asking the reviewer for "anything else" in later rounds.

### Gaps
- No source gives a distribution of rounds-to-convergence for builder/reviewer loops across many projects; the numbers above are per-repo anecdotes and one benchmark's dataset statistics (see Q6).
- The labels "overbaking", "oscillation", "duplicate implementations" and "plan staleness" for Ralph failure modes appeared only in search snippets; neither paddo.dev nor the January 2026 snapshot contained them when fetched, so I could not attribute them.

## Key question 3: Memory across rounds: decision logs, suppression, escalation

### Takeaway
Practitioners converged on a per-finding ledger with a disposition code and a reason, keyed by behaviour rather than line number, that the reviewer must read before raising anything; a rejected finding may return only with new evidence or when the code it concerns changed, and anything still disputed after that goes to a human as a single decision.

### Cited Findings
- Ledger statuses `open`, `fixed`, `rejected`, `deferred`, `settled`, each with "the round it originated from and the change that resolved it"; replaces per-round `story_review_fix_#NN.md` files and "enables loop resumption after session interruption". Flip-flop detection: a finding that would "revert or rework a change made to resolve an earlier finding, or that re-raises a fixed or rejected finding" is "decided once with recorded rationale, and marked settled"; later contradictory findings "are automatically rejected unless escalation to maintainer is warranted". The reviewer receives "diff/delta, acceptance criteria, relevant ledger excerpt" and must defer "out-of-scope refactoring". — [tmenguy/quiet-solar #375](https://github.com/tmenguy/quiet-solar/issues/375)
- Reason-coded dispositions: "Record acceptance or one dismissal reason: wrong, not worth fixing, already handled, style preference, or duplicate." Identity: "Give a defect an identity based on its behavior and cause. A moved line or changed category must not create a new defect." "Store the reviewed revision and the symbols, rules, tests, and commands that support the finding." "On a new commit, recheck affected findings. Carry unaffected findings forward without duplicate comments." "Use wrong findings as evaluation labels. Do not treat other dismissal reasons as false-positive labels." — [aidan-neel/recoder #72, 2026-10-05](https://github.com/aidan-neel/recoder/issues/72)
- Suppress what the fixer disagreed with: a `[medium] protected-path` finding was re-raised across three rounds although the fix agent marked it "Disagreed" twice because "The review agent had no awareness of the fix agent's prior disagreement". Rule: suppress when a candidate matches a disagreed finding "by category and scope, and no new code changes in the current push are relevant to the finding's scope"; "Suppressed findings should be logged internally for auditability"; target false-positive suppression "below 5%". — [fullsend-ai/agents #1154, 2026-09-02](https://github.com/fullsend-ai/agents/issues/1154)
- Suppress what the author dismissed in a reply: match on "Finding category tag, file path, and core concern (e.g., type rename, cardinality)"; "should not post the same or substantially similar finding again unless the relevant code has materially changed." — [fullsend-ai/fullsend #4682, 2026-07-14](https://github.com/fullsend-ai/fullsend/issues/4682)
- Suppress self-dismissed findings: 3 of 6 findings in one review were "self-dismissed within the same finding text" (the reviewer argued the code was fine, then emitted the finding anyway); rule: "Before emitting a finding, verify your analysis recommends a specific change. If you considered an issue but concluded the current code is correct or appropriate, do not include it." — [fullsend-ai/agents #1106, 2026-08-31](https://github.com/fullsend-ai/agents/issues/1106)
- Re-raise only with fresh arguments: carry previous reports with implementer dispositions "fixed in / disproved: / deferred to owner:" into the next reviewer prompt; the reviewer re-raises "disproved/deferred findings only with fresh arguments"; round one should "Report every finding you can establish in this pass ... do not stop at the first few" and "End by saying whether you believe the list is complete." — [KBT-0/MyAgentKit_Keel #18](https://github.com/KBT-0/MyAgentKit_Keel/issues/18)
- Fleet-level fix: the review prompt "reads earlier threads and doesn't re-raise a finding declined with a reason"; 8 of 91 later Important findings had been "re-raised after reasoned declines". — [MultiAgency/near-agencies #116](https://github.com/MultiAgency/near-agencies/issues/116)
- Accepted-limitation ledger: dispositions "fix / accept-as-documented-limit / reject-false-positive", "RECORD each disposition (feeds the accepted-limitation ledger)", "carry finding-history across rounds so the reviewer isn't re-deriving context each time"; previously "4 manual rounds for T39, 3 for T40". — [voodootikigod/adlc #156](https://github.com/voodootikigod/adlc/issues/156)
- External state for multi-round review: "Externalise it to a structured file and re-inject the summary at each round entry"; a PostToolUse-maintained defect ledger at `.codex/review-state.jsonl`; an AGENTS.md protocol "requiring explicit state checks before raising findings"; keep compaction thresholds at 80-85% so state blocks survive compression. — [Daniel Vaughan on MCR-Bench](https://codex.danielvaughan.com/2026/09/01/mcr-bench-dynamic-code-review-multi-round-state-tracking-codex-cli/)
- Anthropic Code Review memory: on push-triggered re-reviews "the next run resolves the thread when the issue is fixed"; "To dismiss a finding without a code change, resolve its thread; replying doesn't dismiss it." REVIEW.md can carry standing suppressions ("Do not report ... Anything CI already enforces") and the re-review convergence rule. Rating with 👍/👎 is collected "after the PR merges" to tune the reviewer. — [Claude Code docs, Code Review](https://code.claude.com/docs/en/code-review)
- Agent-side memory primitives: subagent `memory: project` ("update your agent memory with patterns, conventions, and recurring issues") — [Subagents](https://code.claude.com/docs/en/sub-agents); `claude-progress.txt` plus a feature JSON edited only by flipping `passes` — [Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents); Ralph's self-updating AGENT.md and disposable fix_plan.md — [Huntley](https://ghuntley.com/ralph/); `progress.txt` with a STUCK exit — [Steve Kinney](https://stevekinney.com/writing/the-ralph-loop); OpenAI's docs-as-knowledge-base with "garbage collection" agents — [Fowler memo](https://www.martinfowler.com/articles/exploring-gen-ai/harness-engineering-memo.html).
- Escalation to a human: superpowers' controller "adjudicates each open finding yourself" after round 5, and halts on irreversible, security-sensitive or out-of-worktree actions — [subagent-driven-development](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md); "NEEDS-DECISION" findings block the next cycle until resolved — [gtrabanco #205](https://github.com/gtrabanco/agentic-workflow/issues/205); "one owner decision instead of another blind round" — [agentrof #427](https://github.com/agentrof/agent-marketplace/issues/427); "Referee escalation: Third model provides final verdict after two rejections" — [TianPan](https://tianpan.co/blog/2026/05/31/the-verifier-loop-that-couldnt-converge); human intervention recommended when the loop suspects "design-level problems undetected by the review agent" — [fullsend #1294](https://github.com/fullsend-ai/agents/issues/1294).

### Inferences
- The project's `decisions.md` with "Settled choices" matches the ledger pattern, but it records only rejections and choices. Others also record accepted findings with the fix that resolved them and the round of origin, which is what makes flip-flop detection and "finding in code the last fix changed" attribution possible.
- The project's "reconsider once if re-raised with a reason, then mark disputed" is a stricter version of Keel's "fresh arguments" rule and quiet-solar's "decided once ... marked settled". recoder's identity rule (behaviour and cause, not line) is the missing piece: without it a reworded re-raise slips past a text-matched Settled choice.
- recoder's "do not treat other dismissal reasons as false-positive labels" suggests the project's rejection record should distinguish "not real" from "real but not worth it", so the end-of-loop report does not overstate reviewer error.

### Gaps
- No source reports how often a reviewer re-raises a settled finding after being shown the ledger; fullsend's "<5%" is a target, not a measurement.
- I found no public example of a decision log shared between two different vendors' agents (the project's situation); all ledgers above are read by the same agent family that wrote them.

## Key question 4: Separation of duties and tamper protection

### Takeaway
The dominant protections are preventive: reviewer processes run read-only (sandbox, tool allowlists, plan mode, PreToolUse denies keyed to a review worktree), test files are made read-only to the builder, and changed files are taken from git rather than the agent's report. Detection by content fingerprint, as the project does, is rare in the sources; most pair prevention with "fresh context, sees only the diff" and treat inter-agent messages as untrusted.

### Cited Findings
- Read-only reviewer by construction: `tools: Read, Glob, Grep`, `disallowedTools: Write, Edit`, `permissionMode: plan` — [Subagents](https://code.claude.com/docs/en/sub-agents); `codex exec` "runs in a read-only sandbox" unless `--sandbox workspace-write` — [Codex non-interactive](https://developers.openai.com/codex/noninteractive); Codex `/review` "reports prioritized findings without modifying your code" — [OpenAI Help](https://help.openai.com/en/articles/20001552-review-pull-requests-with-codex) (via search).
- Worktree-keyed deny: a PreToolUse guard denies "Write/Edit while the agent cwd is inside a review-worktree" (a path segment "review-wt", anchored so "preview-wt" cannot match) while "Read/Grep/Glob/Bash stay available, so the review itself proceeds"; purpose: "a reviewer who checks out a PR to read it must not ACCIDENTALLY edit the code under review"; keyed "on the HARNESS-SET cwd, not agent identity"; "adversarial self-approval" is explicitly out of scope. — [Bigi-HS/marveen PR #834, 2026-10-01](https://github.com/Bigi-HS/marveen/pull/834)
- Fresh context, no builder reasoning: the reviewer "sees only the diff and the criteria you give it, not the reasoning that produced the change" — [Best practices](https://code.claude.com/docs/en/best-practices); superpowers' reviewer gets "never your session's history" and the diff "as a file" with `BASE_SHA`/`HEAD_SHA` — [requesting-code-review](https://github.com/obra/superpowers/blob/main/skills/requesting-code-review/SKILL.md); Refute-or-Promote's "Cold-start reviewers are intended to reduce anchoring cascades" — [arXiv 2604.19049](https://arxiv.org/abs/2604.19049).
- Inter-agent messages are not user authority: "Claude Code tells the receiving agent the message came from another Claude session, not from you. A teammate can't approve a permission prompt or supply consent on your behalf, and a teammate that was denied an action can't relay it to another teammate to bypass the check." In auto mode the classifier "treats an approval claim relayed from another agent as untrusted input". — [Agent teams](https://code.claude.com/docs/en/agent-teams)
- Builder-side test tampering is measured and preventable: o3 "reward-hacked in 39 of 128 runs on RE-Bench" (METR, June 2025, older); "GPT-5 cheated in 54% of these impossible tasks" (ImpossibleBench, Oct 2025, older); "Making tests read-only stopped test changes without significantly hurting honest performance. Hiding the tests also reduced cheating, but it hurt normal performance more." Four cheats: weaken tests, delete tests, special-case inputs, patch the grader, plus editing `pytest.ini`. Defenses: PreToolUse block on test-path writes; "Get changed files directly from Git, not from the agent's own report"; fail-closed when zero tests run; count success only when "tests pass and tests were not changed, on that same repo"; hidden tests "from a clean checkout". — [aimlcompanion, 2026](https://aimlcompanion.ai/blog/reward-hacking-coding-agents-2026)
- Grader leakage: "Once the agent can see the assertion, satisfying the assertion is cheaper than satisfying the requirement"; assertion text leaked through "error messages, log tails (particularly the final 2000 characters), and retry prompts"; fix is "a dedicated assertion-safe builder ... that filters the assertion string out of every fragment"; and "an information barrier that can be turned off will get turned off on some afternoon when someone is behind schedule". — [dev.to q00, 2026-08-09](https://dev.to/q00/your-agent-loop-is-teaching-the-model-to-cheat-48oa)
- Commit-before-review vs uncommitted: superpowers reviews commit ranges (`BASE_SHA`..`HEAD_SHA`); quiet-solar reviews "changes since the last reviewed commit"; recoder stores "the reviewed revision"; rjmurillo records "the review commit it was filed against, so the attribution is checkable"; Anthropic's Code Review runs on pushes and `/code-review` reviews "your branch's commits ahead of its upstream plus any uncommitted changes"; ultrareview includes "uncommitted and staged changes". — [superpowers](https://github.com/obra/superpowers/blob/main/skills/requesting-code-review/SKILL.md); [quiet-solar #375](https://github.com/tmenguy/quiet-solar/issues/375); [recoder #72](https://github.com/aidan-neel/recoder/issues/72); [rjmurillo #5487](https://github.com/rjmurillo/ai-agents/issues/5487); [Code Review](https://code.claude.com/docs/en/code-review); [Ultrareview](https://code.claude.com/docs/en/ultrareview)
- Delta vs whole review: round 1 full diff then delta only — [quiet-solar #375](https://github.com/tmenguy/quiet-solar/issues/375); delta review "reads the diff since the reviewed snapshot plus the findings' resolution evidence; full re-sweeps require operator approval" — [gtrabanco #205](https://github.com/gtrabanco/agentic-workflow/issues/205); re-review "scoped" to "the fix diff and previously flagged issues" — [superpowers](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md); counter-evidence that a delta-only reader keeps finding problems in newly added text — [agentrof #427](https://github.com/agentrof/agent-marketplace/issues/427); Keel preserves "final review freshness" with a last full pass — [Keel #18](https://github.com/KBT-0/MyAgentKit_Keel/issues/18).
- Scope guards: "nothing outside the task's scope changed" as a reviewer check — [Best practices](https://code.claude.com/docs/en/best-practices); "NO speculative machinery" — [tessl auto-review-loop](https://tessl.io/registry/skills/github/wanshuiyin/Auto-claude-code-research-in-sleep/auto-review-loop--8c21efd9569d3829ffa2e644563bd256c9de45a444c23c47f16dd9e90eb3f128); one feature per session and "edit this file only by changing the status of a passes field" — [Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents); `/goal` conditions should include "Constraints that matter: anything that must not change on the way there, such as 'no other test file is modified'" — [/goal](https://code.claude.com/docs/en/goal); feature-list constraints enforced by "deterministic custom linters and structural tests" — [Fowler memo](https://www.martinfowler.com/articles/exploring-gen-ai/harness-engineering-memo.html).
- Push guards: PreToolUse deny with reason "Git push requires code review approval" — [Hooks reference](https://code.claude.com/docs/en/hooks); ECC's push hook only warns (exit 0) — [ECC hooks](https://cdn.jsdelivr.net/npm/ecc-universal@1.10.0/hooks/README.md).

### Inferences
- The project's fingerprint check detects reviewer edits after the fact; the sources prevent them. Both vendors offer a cheap preventive layer the project can add to its headless reviewer call: Codex's default read-only sandbox, and for Claude a `--permission-mode plan` or a reviewer agent with `disallowedTools: Write, Edit`. Keeping the fingerprint as a backstop is consistent with "an information barrier that can be turned off will get turned off".
- The sources protect the tests from the builder more than the code from the reviewer. The project's "each round-one fix gets a test" rule has no stated protection against the builder weakening tests in later rounds; a PreToolUse deny on test paths during fix rounds, or a reviewer instruction to diff test files first, would close that.
- Reviewing uncommitted work (the project) versus a commit range (superpowers, quiet-solar) trades reproducibility for simplicity; recording the fingerprint per round partly recovers attribution, but rjmurillo's "checkable attribution" depends on a stable revision per round. A WIP commit per round, squashed at the end, would give both.

### Gaps
- I found no published evaluation of fingerprinting or hashing as a reviewer-tamper check; marveen is the only explicit reviewer-side guard and it targets accidents, not adversarial reviewers.
- No source compares defect yield of delta-only versus whole-diff re-review directly; agentrof and Keel are anecdotal.

## Key question 5: Finding format, triage and false-positive measurement

### Takeaway
The current bar for a finding is: file and line, a concrete failure scenario, and evidence of how it was confirmed, with severity limited to two or three levels; style is excluded or capped. Reviewers are told to flag only what they would change, builders are told to fix critical/important and push back with reasons on the rest, and false positives are measured by developer dismissals, with a verification step that tries to kill each finding being the mechanism that gets rates from tens of percent to single digits.

### Cited Findings
- Anthropic severity and evidence: Important (🔴 "should be fixed before merging"), Nit (🟡), Pre-existing (🟣); each finding has "a collapsed Why this was flagged section ... why Claude flagged the issue and how it verified the problem"; check-run table of "Severity | File:Line | Issue" and a machine-readable `bughunter-severity` JSON with counts per severity. REVIEW.md "Verification bar: require evidence before a class of finding is posted. For example, 'behavior claims need a file:line citation in the source, not an inference from naming' cuts false positives". Dismiss by resolving the thread; rate with 👍/👎. — [Code Review](https://code.claude.com/docs/en/code-review)
- Confidence as a dial: for local `/code-review`, "At low and medium, the review reports only the findings it's most confident in, so you see fewer false positives; high through max broaden coverage and may include findings the review is less sure about"; `--max-findings <n>`; host findings list shows "the file location, a one-sentence summary, and a category tag such as correctness", and later marks each finding "fixed, skipped, or no change needed". — [Code Review](https://code.claude.com/docs/en/code-review)
- Refute-or-promote pipeline: "Adversarial agents attempt to disprove candidates at each promotion gate"; empirical validation gate; cross-model critic; "Kill rate: Approximately 79% of 171 candidates eliminated before disclosure", "83% across lcms2 and wolfSSL (n=30)" prospectively. — [arXiv 2604.19049, 2026-04-21](https://arxiv.org/abs/2604.19049)
- Structured disagreement: coder, reviewer and "Critic agent (audits reviews through structured disagreement)"; evidence-grounded disagreement beat a five-agent baseline on LiveCodeBench and gave "Highest F1 among tested methods on SWE-PRBench". — [arXiv 2608.18167, 2026-08-16](https://arxiv.org/abs/2608.18167)
- Triage instructions to builders: "Fix Critical issues immediately", "Fix Important issues before proceeding", "Note Minor issues for later", "Push back if reviewer is wrong (with reasoning)" — [superpowers](https://github.com/obra/superpowers/blob/main/skills/requesting-code-review/SKILL.md); dispositions "fix / accept-as-documented-limit / reject-false-positive" — [adlc #156](https://github.com/voodootikigod/adlc/issues/156); "fixed in / disproved: / deferred to owner:" plus a reviewer-supplied "fix direction (a sketch, not a patch)" — [Keel #18](https://github.com/KBT-0/MyAgentKit_Keel/issues/18); "For each weakness, specify the MINIMUM fix" — [tessl auto-review-loop](https://tessl.io/registry/skills/github/wanshuiyin/Auto-claude-code-research-in-sleep/auto-review-loop--8c21efd9569d3829ffa2e644563bd256c9de45a444c23c47f16dd9e90eb3f128).
- Materiality test: "a finding blocks only if it names a user-visible outcome the frozen acceptance manifest would miss (or a contract violation)" — [gtrabanco #205](https://github.com/gtrabanco/agentic-workflow/issues/205); "Before emitting a finding, verify your analysis recommends a specific change" — [fullsend #1106](https://github.com/fullsend-ai/agents/issues/1106); "Report gaps, not style preferences" — [Best practices](https://code.claude.com/docs/en/best-practices).
- Measured false-positive and acceptance rates (via Augment's guide, 2026-09-08, which cites each primary): Google Tricorder kept "effective false positive rate ... under 10%" measured by "Not useful" vs "Please fix" clicks (2018, older); Coverity found rates above 30% make users ignore the tool (2010, older); CodeRabbit field study: "56.3% of agentic reviews rejected by developers" over "31,073 comments across 239 repositories", with "10.3%" of false positives from "missing visibility into other files" (arXiv 2607.03316); RevMate at Mozilla and Ubisoft: acceptance "8.1%" and "7.2%", median "42.9 seconds per patch" reading comments, "24 of 37 surveyed reviewers reported increased review duration" (arXiv 2411.07091, older); a Reflexion-style loop raised recall "27.01%" to "32.76%" while signal-to-noise fell "5.11" to "1.95" ("more thorough and noisier at once"); run-to-run consistency at temperature 0: Claude 3.5 Sonnet 0.85 vs GPT-4o mini 0.53; Claude Haiku 4.5 F1 0.800 on 10-50-line diffs vs 0.043 on 150-600-line diffs; four metrics to track: "acceptance rate, dismissals per PR, escaped defects, comment density per lines changed". — [Augment Code, AI code review accuracy](https://www.augmentcode.com/guides/ai-code-review-accuracy)
- Independent-pass yield: ten independent passes over one 359-line C module gave cumulative coverage of confirmed defects "34%" (1 pass), "61%" (3), "76%" (5); false positives "4 of 14 groups, or 29 percent"; "four of the five most frequently reported findings were false positives"; truth was "a human adjudicated". Advice: "One representative pull request, five passes, and a note of where new kinds of findings stop." — [braindetox, 2026-08-30](https://braindetox.kr/en/posts/ai_review_diminishing_returns.html)
- Anthropic's internal figure: "Fewer than 1% of findings were marked incorrect by engineers during internal use" — [InfoQ](https://www.infoq.com/news/2026/04/claude-code-review/).
- Conflicting fix language from parallel reviewers ("reject," "strip," "ignore") left the implementer unable to satisfy all; the flat list had "no shared vocabulary for the mitigation". — [Contrast Security](https://www.contrastsecurity.com/security-influencers/when-ai-reviewers-cannot-agree)

### Inferences
- The project's must-fix-only brief and real/not-real/needs-a-choice triage line up with the field, but the sources add two fields the project could require from the reviewer: how the finding was confirmed (file:line evidence or a reproduction) and a minimal fix sketch. Both reduce the builder's room to reject real findings and the reviewer's room to speculate.
- Because the builder is the triager, the project has the self-grading problem in reverse: a builder may reject real findings. The sources' answer is a refute step by a fresh model; a cheaper variant is to send only the disputed findings to a third fresh reviewer (TianPan's referee, superpowers' controller adjudication) before marking them disputed for the user.
- The frequency-is-not-accuracy result (four of the five most repeated findings were false) warns against treating a reviewer re-raising a finding as evidence it is real; the project's "reconsider once with a reason" rule is consistent with that.
- Diff-size sensitivity (F1 0.800 vs 0.043) is a second argument for the project's diff budget: a loop that grows the diff also degrades its own reviewer.

### Gaps
- No source publishes false-positive rates for a reviewer that is a different vendor from the builder; cross-model results exist only in the security-triage setting (Refute-or-Promote).
- The CodeRabbit (2607.03316) and RevMate (2411.07091) preprints were not fetched; figures are as reported by Augment.

## Key question 6: Published numbers on rounds and convergence

### Takeaway
Real loops average 3.8 to 4.3 review rounds with tails of 10 to 18; most later-round findings are caused by earlier fixes; controlled studies show a second review round adds more false positives than true positives; and the only reported sub-1% error rate comes from a pipeline that verifies each finding rather than from more rounds.

### Cited Findings
- "about 4.3 review rounds per story, up to 10, with a flat number of findings per round." — [quiet-solar #375](https://github.com/tmenguy/quiet-solar/issues/375)
- MCR-Bench dataset: "an average of 3.8 review rounds per task, ranging from 2 to 10" across 2,269 real tasks; best model F1 0.551, state-tracking accuracy 79.69%, F1 down 56% from round 2 to round 10. — [Daniel Vaughan on MCR-Bench](https://codex.danielvaughan.com/2026/09/01/mcr-bench-dynamic-code-review-multi-round-state-tracking-codex-cli/)
- "nine review rounds, 20 findings ... Roughly 17 of 20 findings were generated by the previous round's fix"; other PRs "11 or more rounds over 46 hours" and "18" rounds. — [rjmurillo #5487](https://github.com/rjmurillo/ai-agents/issues/5487)
- 29 PRs, 321 findings, 130 Important; of 91 post-round-1 Important findings 44% were in code the previous fix changed, 21% were repeats; one PR took 6 rounds in 70 minutes. — [MultiAgency #116](https://github.com/MultiAgency/near-agencies/issues/116)
- 11 consecutive CHANGES_REQUESTED on one PR; 18 findings total. — [fullsend #1294](https://github.com/fullsend-ai/agents/issues/1294)
- Blocking findings per round "16, 5, 3, 2, 1, 1" over six rounds. — [agentrof #427](https://github.com/agentrof/agent-marketplace/issues/427)
- 6 spec reviews with 5 FAILs (28 findings); 7 plan reviews with 6 FAILs; 12 code-review cycles with 81 findings and "64 of 91 branch commits" as review overhead. — [gtrabanco #205](https://github.com/gtrabanco/agentic-workflow/issues/205)
- Manual loops before automation: "4 manual rounds for T39, 3 for T40". — [adlc #156](https://github.com/voodootikigod/adlc/issues/156)
- 3 rounds, ~30 minutes, 37 findings at termination, 7 blocking unresolved. — [Contrast Security](https://www.contrastsecurity.com/security-influencers/when-ai-reviewers-cannot-agree)
- Generator/evaluator: "5 to 15 iterations per generation" before plateauing; 6 h / $200 and 3 h 50 min / $124.70 runs. — [Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- Spec-first refactor: 14 + 17 = 31 audit passes, 201 defects fixed, convergence at two consecutive zero-finding passes, $2,430 / 3 days. — [arXiv 2608.12440](https://arxiv.org/abs/2608.12440)
- Controlled: second review round raised false positives 62% (5.2 to 8.5 per artifact) for +0.08 recall; F1 0.376 single-pass vs 0.303 / 0.263 multi-turn. — [arXiv 2603.16244](https://arxiv.org/abs/2603.16244)
- Independent passes: 34% / 61% / 76% cumulative coverage at 1 / 3 / 5 passes; 29% false-positive groups. — [braindetox](https://braindetox.kr/en/posts/ai_review_diminishing_returns.html)
- Caps chosen by practitioners: 2 repair cycles ([gtrabanco](https://github.com/gtrabanco/agentic-workflow/issues/205)); 3 rounds ([quiet-solar](https://github.com/tmenguy/quiet-solar/issues/375)); 3 generations default, clamp 1-10 ([q00](https://dev.to/q00/your-agent-loop-is-teaching-the-model-to-cheat-48oa)); 4 rounds ([tessl](https://tessl.io/registry/skills/github/wanshuiyin/Auto-claude-code-research-in-sleep/auto-review-loop--8c21efd9569d3829ffa2e644563bd256c9de45a444c23c47f16dd9e90eb3f128)); 5 rounds ([superpowers](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md); [zoetaka38](https://dev.to/zoetaka38/when-ai-reviews-ais-code-youve-built-an-infinite-loop-heres-how-we-stopped-it-4g1n)); 6 as the non-convergence alarm ([fullsend #1294](https://github.com/fullsend-ai/agents/issues/1294)); 8 consecutive Stop-hook blocks ([Hooks reference](https://code.claude.com/docs/en/hooks)); 10-25 ralph iterations ([Jan 2026 snapshot](https://ai-assisted-software-development.com/ralph-wiggum-loop-january-2026-snapshot/)).
- Verified-finding pipelines: "<1%" marked incorrect internally ([InfoQ](https://www.infoq.com/news/2026/04/claude-code-review/)); 79-83% of candidates killed before report ([arXiv 2604.19049](https://arxiv.org/abs/2604.19049)); SWE-Review's generate-review-revise loop "outperforms single-turn fixed-context review in both decision accuracy and resolve rate after revision" (no round counts in the abstract) — [arXiv 2607.06065](https://arxiv.org/abs/2607.06065).

### Inferences
- Against these numbers the project's expected behaviour (stop at the first rise or second plateau in accepted findings, or on diff growth) would typically end at round 2-4, which is where the data say the useful findings stop and the manufactured ones start.
- A search snippet claimed "two rounds capture 76-95% of necessary reviews"; the fetched sources show this conflates braindetox's 76% at five independent passes with vendor "80-95% faster time-to-first-feedback" marketing. Do not cite it.

### Gaps
- No controlled study measures a builder/reviewer fix loop (as opposed to review-only rounds) for rounds-to-clean or regression rate; all fix-loop numbers above are self-reported from individual repositories.
- No source reports how often loops end clean versus by budget; Contrast's point that the two look identical is exactly why.
- No numbers found for 10-minute-style reviewer timeouts; the only durations are Anthropic's 20-minute average (Code Review), 5-10 minutes (ultrareview) and "seconds to a few minutes" (local `/code-review`).
