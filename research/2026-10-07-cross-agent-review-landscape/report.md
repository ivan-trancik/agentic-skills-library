# Cross-vendor review is right; harden its mechanics

The project's core bet — a different vendor's harness reviews each stage, the reviewer reports only must-fix findings, and the loop stops when accepted findings stop falling or the diff outgrows the task — is the configuration the research record supports best, and none of the roughly twenty libraries surveyed combines its symmetric two-way pairing, content-fingerprint tamper check, diff-growth stop and settled-decisions ledger. What it lacks is enforcement and calibration rather than design. The Claude reviewer's bare `Bash` allow rule lets it run any shell command, so edits are detected afterwards rather than prevented; `-c model_reasoning_effort=high` lowers Codex below the user's configured `xhigh`; the loop has no hard round cap although controlled and field data put the useful rounds at one to two and show a second review round adding 62% more false positives; the 1440x4000 screenshot is downscaled to roughly 564x1568 pixels on standard-tier Claude models, turning 16 px text into about 6 px; and `claude -p` executes a repository's hooks and MCP servers with no trust prompt while costing about $0.59 of cached context per launch (measured on Claude Code 2.1.292 and Codex CLI 0.160.1 on 7 October 2026). Both CLIs now ship review rubrics stricter than the project's prompt — Codex's P0–P3 JSON schema with per-finding `confidence_score` and an "author would fix it" test, Claude Code's CONFIRMED/PLAUSIBLE/REFUTED verify vote — and `codex exec review "<prompt>"` lets the project inherit Codex's rubric while keeping its own scope. Vision-language models match expert designers on aesthetics (agreement KBP ≥ 0.81) but average 58% on trivial geometric tasks, so screenshot review should generate candidates over structured inputs rather than deliver verdicts. The installer's layout is exactly what both harnesses need today (a probe confirmed Claude Code does not read `~/.agents/skills`); the remaining distribution gaps are that `ship` is auto-invocable, that absolute script paths break plugin packaging, and that nothing checks for updates. The prioritised list at the end turns each finding into a concrete change tagged as verified fact, inference or vendor claim.

## The project sits in a thin cross-vendor tier that larger bundles only gesture at

Twenty-odd libraries now claim to define a development workflow for Claude Code or Codex, and they split into three layers. Process bundles own the whole loop: obra/superpowers (296,303 stars, v6.4.2 on 2026-09-25) runs brainstorming → worktree → writing-plans → subagent-driven development → requesting-code-review → finishing-a-development-branch ([superpowers](https://github.com/obra/superpowers)); garrytan/gstack (135,665 stars) runs "Think → Plan → Build → Review → Test → Ship → Reflect" across 35 commands ([gstack](https://github.com/garrytan/gstack)); EveryInc/compound-engineering-plugin, bmad-code-org/BMAD-METHOD, Yeachan-Heo/oh-my-claudecode and affaan-m/everything-claude-code (274,736 stars, "68 agents", "293 skills") do the same with their own vocabularies ([compound-engineering](https://github.com/EveryInc/compound-engineering-plugin); [BMAD](https://docs.bmad-method.org/); [OMC](https://github.com/Yeachan-Heo/oh-my-claudecode); [ECC](https://github.com/affaan-m/everything-claude-code)). Composable small sets refuse to own the process: mattpocock/skills (279,211 stars) argues that "GSD, BMAD, and Spec-Kit try to help by owning the process. But while doing so, they take away your control and make bugs in the process hard to resolve" ([mattpocock/skills](https://github.com/mattpocock/skills)). Spec and PM layers (github/spec-kit at 140,510 stars, Fission-AI/OpenSpec at 71,254, Taskmaster, ccpm) stop at "implement" and leave review and shipping to the host ([spec-kit](https://github.com/github/spec-kit); [OpenSpec](https://github.com/Fission-AI/OpenSpec)). Star counts across the category are inflated — several repos gained over 100,000 stars within a year of creation — so last-push dates are the better maintenance signal: Taskmaster's last push was 2026-04-28, ccpm's 2026-03-18, and OpenAI's own Codex plugin for Claude Code has not been pushed since 2026-07-08 ([codex-plugin-cc](https://github.com/openai/codex-plugin-cc)).

The project belongs to the composable layer and to a far thinner cross-vendor niche. The official pairing is openai/codex-plugin-cc (33,927 stars): a read-only `/codex:review` that "is not steerable", a steerable `/codex:adversarial-review`, and an optional Stop-hook "review gate" whose README warns that it "can create a long-running Claude/Codex loop and may drain usage limits quickly" ([codex-plugin-cc](https://github.com/openai/codex-plugin-cc)). gstack embeds the other CLI as an "outside voice" that blocks a spec below 7/10 and hides installed skills during nested Codex reviews with `-c skills.include_instructions=false` ([gstack README](https://github.com/garrytan/gstack)); OMC's `ralplan` accepts `--critic codex` ([OMC ralplan](https://github.com/Yeachan-Heo/oh-my-claudecode/blob/main/skills/ralplan/SKILL.md)). The community tools that do what this project does are tiny — rocket-review has 1 star, claude-codex-bridge and claude-code-cross-review have 0 — and only rocket-review and gstack run the pairing in both directions ([rocket-review](https://github.com/ledger-rocket/rocket-review); [claude-codex-bridge](https://github.com/vasilievyakov/claude-codex-bridge)). The niche matters more than its stars suggest: a 2026 synthesis of 3,100 practitioner documents finds agent-authored PRs "reviewed less often, merged several times faster, and discussed less than human-authored ones" and concludes that "review is the control point through which a coding agent's effect on software is decided" ([arXiv 2607.07980](https://arxiv.org/abs/2607.07980)).

Five features of the project appeared nowhere else in the survey. The **symmetric pairing** through one `reviewer.sh` that runs `codex exec` when Claude Code builds and `claude -p` when Codex builds. A **content fingerprint** (`git diff HEAD` plus hashes of untracked files) checked before and after each review, where every other tool relies on sandbox flags alone and the one explicit reviewer-side guard found — a PreToolUse deny keyed to a review worktree — targets accidents, not an unsandboxed reviewer ([marveen PR #834](https://github.com/Bigi-HS/marveen/pull/834)). A **stop rule driven by the trend in accepted findings plus a diff-growth budget** of 50% or 200 lines, where no other loop uses diff growth as an explicit stop. A **decisions file** that forbids the reviewer from re-raising settled choices unless the recorded reason is factually wrong. And a **plan that opens with the user's request verbatim**, which no surveyed plan template does. The `save-review`/`apply-review` hand-off pair and a `ship` that squash-merges are also rare: nearly every library hands the merge to the human — superpowers presents a menu, compound-engineering "does not merge unless you grant that", OpenSpec "never commits, branches, pushes, or pulls", BMAD stops at `built` — and only gstack's `/land-and-deploy` also merges ([superpowers finishing](https://github.com/obra/superpowers/blob/main/skills/finishing-a-development-branch/SKILL.md); [compound README](https://github.com/EveryInc/compound-engineering-plugin); [OpenSpec team workflow](https://github.com/Fission-AI/OpenSpec/blob/main/docs/team-workflow.md); [BMAD autonomous loops](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/docs/build/autonomous-development-loops.md); [gstack README](https://github.com/garrytan/gstack)).

The main 2026 criticism of the process bundles is cost. A Hacker News thread on Superpowers 6 called it "a large and growing artifice" and "tokenmaxxing for marginal improvements" ([HN 48739459](https://news.ycombinator.com/item?id=48739459)); a one-month gstack review reported "stable usage after four weeks: six commands out of 35" ([claude-codex.fr](https://claude-codex.fr/en/content/garry-tan-stack-claude-code/)); Anthropic's own docs say "Plan mode is useful, but also adds overhead ... If you could describe the diff in one sentence, skip the plan" ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)). The bundles answered with right-sizing rather than by dropping review: superpowers classifies every request as Spike, Bounded or Architectural "before your first question" ([brainstorming](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md)), and BMAD sizes a session at "about 500 lines of code added or changed (not counting tests)" and says "For a trivial edit you are willing to review yourself, skip the process" ([BMAD build-a-change](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/docs/build/build-a-change.md)). The project's default instruction block has no escape hatch beyond "Questions, explanations and tasks that only run commands don't need a plan".

## Peer workflows converge on hard gates, three severities and human-held merges

Plans everywhere are Markdown files and the human gate is "approve the written plan before any code", but the libraries are stricter than the project about what approval means. Superpowers' brainstorming skill carries a literal `<HARD-GATE>`: "Approval of an idea or feature scope does not approve artifacts that do not exist yet", and its release notes add that "Approving an idea or a scope no longer counts as approving a plan you haven't seen" after "some frontier models, including Opus 5.5, could get overzealous during plan writing and ... would sometimes try to implement the entire project while designing the plan" ([brainstorming](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md); [RELEASE-NOTES](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md)). OpenSpec's propose skill says "The user request that selected or triggered this workflow authorizes planning only, even if it asks to build or fix something" ([OpenSpec propose](https://github.com/Fission-AI/OpenSpec/blob/main/skills/openspec-propose/SKILL.md)). Plan storage splits between committed (superpowers `docs/superpowers/plans/YYYY-MM-DD-<feature>.md`, compound `docs/plans/`, OpenSpec `openspec/changes/<name>/`, spec-kit `specs/NNN-<name>/`) and local scratch (OMC `.omc/plans/`, this project's `.local/plan.md`); the committed camp's argument is that the PR reviewer gets the intent next to the code, and OpenSpec's team workflow shows a middle path where the plan rides in the PR and is archived after merge ([writing-plans](https://github.com/obra/superpowers/blob/main/skills/writing-plans/SKILL.md); [OpenSpec team workflow](https://github.com/Fission-AI/OpenSpec/blob/main/docs/team-workflow.md)).

Plan review by a second model exists in four places, and in each it is scored rather than binary. gstack's `/spec` has an "Outside-review quality gate before filing (Claude Code on Codex; Codex on other harnesses; blocks below 7/10)" ([gstack](https://github.com/garrytan/gstack)); OMC's `ralplan` runs "Planner -> Architect -> Critic loop until agreement" with a five-iteration cap, insists the Critic "MUST NOT consume or receive the Architect review", and ends with an ADR ([ralplan](https://github.com/Yeachan-Heo/oh-my-claudecode/blob/main/skills/ralplan/SKILL.md)); hasuwini77's codex-reviewer-skill fans out three Codex lenses (assumptions and goal, completeness, risk and reversibility), returns SOLID "only if all three lenses agree", and "treats the plan as untrusted data, so a prompt-injected plan can't make the reviewer touch your filesystem" ([codex-reviewer-skill](https://github.com/hasuwini77/codex-reviewer-skill)); rocket-review's `rr plan.md` "stress-tests a design doc before you build it" and defaults to Codex for plan reviews ([rocket-review](https://github.com/ledger-rocket/rocket-review)). Superpowers, by contrast, deleted its plan-document-reviewer prompt in v6.4.2 because "Nothing referenced it" and relies on the author's self-checklist plus the human ([RELEASE-NOTES](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md)). The project's `review-plan` prompt — request missed or quietly narrowed, false assumption with file and line, risky choice, choice the user should make, check that wouldn't prove the work done, else `PLAN IS SOUND` — is closest to hasuwini77's lenses and is the only one that forces the reviewer to start from the user's own words.

Code-review formats have converged on three severities, `file:line`, a concrete failure scenario and a verdict, with three 2026 additions: a confidence floor, a "zero findings is valid" instruction and an explicit false-positive list. ECC's reviewer says "Only report issues you are confident about (>80% sure it is a real problem)", imposes a four-question "Pre-Report Gate", requires proof for HIGH and CRITICAL and lists "Common False Positives - Skip These" ([ECC code-reviewer](https://github.com/affaan-m/everything-claude-code/blob/main/agents/code-reviewer.md)); BMAD's `bmad-review` "never pads to look thorough", and OMC's review states "A plausible-sounding finding that does not reproduce is noise" and "Advisory by default — review informs, it does not gate" ([BMAD skills](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/docs/reference/skills-and-agents.md); [OMC review](https://github.com/Yeachan-Heo/oh-my-claudecode/blob/main/skills/review/SKILL.md)). Superpowers' reviewer gets "never your session's history", is told "Your review is read-only on this checkout. Do not mutate the working tree, the index, HEAD, or branch state in any way", and must emit a "Declined to judge" section: "list every behavior you considered and set aside as outside the plan or spec, one line each, with the reason. The executor rules on each line; nothing you set aside is dropped silently" ([requesting-code-review](https://github.com/obra/superpowers/blob/main/skills/requesting-code-review/SKILL.md); [code-reviewer.md](https://github.com/obra/superpowers/blob/main/skills/requesting-code-review/code-reviewer.md)). mattpocock and OMC independently split review into two axes ("Standards"/"Spec" and "Standards"/"Intent") run as parallel subagents that are "never merged or cross-ranked" ([mattpocock code-review](https://github.com/mattpocock/skills/blob/main/skills/engineering/code-review/SKILL.md)). BMAD's triage is the closest published analogue of the project's real/not-real/needs-a-choice sort — "Verify the claimed consequence at the named location ... Dismiss noise, refuted claims, and unsubstantiated claims, with a recorded reason — never silently; Route survivors to patch, defer, or decision needed" — and it names a stopping heuristic the project could borrow verbatim: "Non-trivial findings on a third pass of agentic review usually mean something is wrong upstream of this change" ([BMAD review-a-change](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/docs/build/review-a-change.md)).

On the receiving side, superpowers forbids "You're absolutely right!" and prescribes READ → UNDERSTAND → VERIFY → EVALUATE → RESPOND → IMPLEMENT, with "IF conflicts with your human partner's prior decisions: Stop and discuss with your human partner first" ([receiving-code-review](https://github.com/obra/superpowers/blob/main/skills/receiving-code-review/SKILL.md)). Its ledger records every deviation as "`Ruling: <what you decided> — <why> — <what it costs if wrong>`" because "Deviating from the plan without a ledgered ruling is a decision made in secret", and after compaction the agent is told to "trust the ledger and `git log` over your own recollection" ([executing-plans](https://github.com/obra/superpowers/blob/main/skills/executing-plans/SKILL.md)). The project's "Settled choices" lines carry the what but not the why-and-cost, which is exactly the information a reviewer needs to exercise the one exception the project's prompt allows — challenging a recorded reason that is factually wrong.

Finishing is where the libraries are most conservative. mattpocock's git-guardrails hook blocks `git push` in all variants plus `reset --hard`, `clean -f`, `branch -D` and `checkout .` ([git-guardrails](https://github.com/mattpocock/skills/blob/main/skills/misc/git-guardrails-claude-code/SKILL.md)); gstack's `/careful` returns `permissionDecision: "ask"` for `rm -rf`, `DROP TABLE`, `git push --force` and `git reset --hard`, and hard-denies two shapes — `rm -r` of `/`, `~` or `$HOME`, and force-push to the default branch ([careful](https://github.com/garrytan/gstack/blob/main/careful/SKILL.md)); superpowers requires the user to type 'discard' before discarding a branch and confirms the base branch because "merging into the wrong base is expensive to undo" ([finishing](https://github.com/obra/superpowers/blob/main/skills/finishing-a-development-branch/SKILL.md)). The project's `ship` already says "never force a push or a merge" and stops on a real conflict; what it lacks is a hook that makes the rule mechanical and an invocation guard that stops a model from selecting it on its own (see the distribution section).

## Both CLIs now ship review rubrics stricter than any hand-rolled prompt

### Codex: a JSON rubric with an "author would fix it" test

Every Codex review — TUI `/review`, `codex review`, `codex exec review`, the app-server `review/start` — runs as a sub-agent thread whose system prompt is a fixed rubric, with approvals forced to `never` and web search disabled ([codex review task](https://github.com/openai/codex/blob/main/codex-rs/core/src/tasks/review.rs)). The rubric defines a reportable bug by eight tests, four of which target exactly the false positives a loop suffers from: "The bug was introduced in the commit (pre-existing bugs should not be flagged)", "The author of the original PR would likely fix the issue if they were made aware of it", "The bug does not rely on unstated assumptions about the codebase or author's intent", and "It is not enough to speculate that a change may disrupt another part of the codebase, to be considered a bug, one must identify the other parts of the code that are provably affected". Volume is governed by "If there is no finding that a person would definitely love to see and fix, prefer outputting no findings. Do not stop at the first qualifying finding." Comments are capped at "at most 1 paragraph" with no code chunk "longer than 3 lines" and must "clearly and explicitly communicate the scenarios, environments, or inputs that are necessary for the bug to arise". Each finding carries a `confidence_score` from 0 to 1, a `priority` 0–3 rendered as `[P0]`–`[P3]` ("[P0] – Drop everything to fix ... Only use for universal issues that do not depend on any assumptions about the inputs"), and a `code_location` that "should overlap with the diff" in a range of at most "5–10 lines"; the object ends with `overall_correctness` ("patch is correct" or "patch is incorrect") and `overall_confidence_score` ([rubric.md](https://github.com/openai/codex/blob/main/codex-rs/prompts/templates/review/rubric.md)). Findings render as `- [Pn] title — path:start-end` with an indented body ([review_format.rs](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/review_format.rs)). On GitHub, "Codex flags only P0 and P1 issues so review comments stay focused on high-priority risks", and repositories tune it through an `AGENTS.md` "## Code Review Rules" section ([Codex GitHub docs](https://learn.chatgpt.com/docs/third-party/github)).

The mechanics matter because the custom prompt replaces only the user message, so `codex exec review "<project prompt>"` yields the project's scope instructions plus Codex's rubric and JSON for free. Verified on 0.160.1: top-level `codex review` has no `-o`, `--json`, `-m` or `--worktree`; `codex exec review` adds `-o/--output-last-message`, `--json`, `-m`, `--output-schema` and `--ephemeral` but bails on `--worktree` ("--worktree is not supported with `codex exec review`"); each target flag is declared with `conflicts_with_all` including `prompt`, so `codex review --uncommitted "custom"` fails in clap before any model call ([Codex CLI reference](https://learn.chatgpt.com/docs/developer-commands?surface=cli); [exec cli.rs](https://github.com/openai/codex/blob/main/codex-rs/exec/src/cli.rs); [exec lib.rs](https://github.com/openai/codex/blob/main/codex-rs/exec/src/lib.rs)). A local run of `codex exec review --uncommitted --json -o out.md < /dev/null` on a two-function Python diff wrote an overall explanation and "- [P2] Average the two middle values for even-length inputs — /abs/path/stats.py:10-10" with a `median([1, 2, 3, 4])` example and exit 0, but `turn.completed.usage` was all zeros, so token accounting is unavailable for review runs ([Codex non-interactive docs](https://learn.chatgpt.com/docs/non-interactive-mode)). The model is `review_model` if set, otherwise the session model ([config reference](https://learn.chatgpt.com/docs/config-file/config-reference)).

### Claude Code: effort-dependent recipes with a verify vote

`/code-review [low|medium|high|xhigh|max|ultra] [--fix] [--comment] [--max-findings n]` reviews "your branch's commits ahead of its upstream plus any uncommitted changes", runs in the foreground in `-p` (except `ultra`), reuses the last typed effort level, and "doesn't read `REVIEW.md`" ([code-review docs](https://code.claude.com/docs/en/code-review); [commands](https://code.claude.com/docs/en/commands)). Strings extracted from the 2.1.292 binary show what the levels do (a local observation; the docs describe the behaviour, not the recipe text): `low` is one diff pass with no verify step and at most min(files, 4) findings — "Flag runtime-correctness bugs visible from the hunk alone" and "Do **not** flag style, naming, perf, missing tests, or anything outside the hunk"; `medium` runs "8 independent finder angles", each surfacing up to six candidates with `file`, `line`, `summary` and `failure_scenario`, then "one verifier" that returns **CONFIRMED** ("can name the inputs/state that trigger it and the wrong output or crash. Quote the line"), **PLAUSIBLE** or **REFUTED**, capped at eight findings and tuned for precision; `high` flips to recall ("**PLAUSIBLE by default** — do not refute a candidate for being 'speculative'") with ten findings; `xhigh` and `max` add a gap sweep and cap at fifteen. Output is a severity-ranked JSON array of `{file, line, summary, failure_scenario}` or a `ReportFindings` tool call with a `category` slug ([tools reference](https://code.claude.com/docs/en/tools-reference)). The docs state the trade-off plainly: "At `low` and `medium`, the review reports only the findings it's most confident in, so you see fewer false positives; `high` through `max` broaden coverage and may include findings the review is less sure about" ([code-review docs](https://code.claude.com/docs/en/code-review)). `/security-review` applies the same philosophy to exploits — "Only flag issues where you're >80% confident of actual exploitability", a confidence scale where "Below 0.7: Don't report", a 17-item hard-exclusion list and a sub-task that filters false positives out of each candidate ([commands](https://code.claude.com/docs/en/commands)). Cloud `ultrareview` promises that "every reported finding is independently reproduced and verified", takes 5–10 minutes and $5–25 after three free runs, and is callable as `claude ultrareview --json --timeout <minutes>` with exit codes 0/1/130, but `claude -p '/code-review ultra'` "launches the cloud review and exits without waiting" ([ultrareview](https://code.claude.com/docs/en/ultrareview)). Anthropic's managed Code Review runs "multiple agents ... Each agent looks for a different class of issue, then a verification step checks candidates against actual code behavior to filter out false positives", posts Important/Nit/Pre-existing comments with a collapsed "Why this was flagged", averages $15–25 and 20 minutes, and is tuned by a `REVIEW.md` whose documented patterns include a verification bar ("behavior claims need a `file:line` citation in the source, not an inference from naming"), a re-review rule ("after the first review, suppress new nits and post Important findings only") and a summary tally ("open with a one-line tally such as `2 factual, 4 style`") ([code-review docs](https://code.claude.com/docs/en/code-review)). InfoQ relays Anthropic's internal numbers — "Fewer than 1% of findings were marked incorrect by engineers" and substantive review comments rising "from 16% of pull requests to 54%" — which are vendor figures reported second-hand ([InfoQ](https://www.infoq.com/news/2026/04/claude-code-review/)).

### Commercial reviewers add thresholds, validators and reaction memory

The commercial PR bots converge on four controls the project has only in part. First, a severity label with a posting threshold that keeps sub-threshold findings visible: Qodo's `inline_comments_severity_threshold` ("A finding below the threshold still appears in the summary, it's never dropped entirely") and CodeRabbit's `quiet`/`chill`/`assertive` profiles ([Qodo](https://docs.qodo.ai/code-review/severity-thresholds.md); [CodeRabbit config](https://docs.coderabbit.ai/reference/configuration)). Second, multi-pass generation plus a validator: Cursor's Bugbot runs "eight parallel passes with randomized diff order", applies "Majority voting to filter out bugs found during only one pass", then "a validator model to catch false positives", and reports resolution rising "from 52% to over 70%" between v1 and v11 while bugs flagged per run rose from 0.4 to 0.7 — a vendor series, but the only published one ([Cursor blog](https://cursor.com/blog/building-bugbot)). Third, repository rules in natural language: CodeRabbit `path_instructions`, Greptile `greptile.json`, Cursor `.cursor/BUGBOT.md`, Codex `## Code Review Rules`, Claude `REVIEW.md`. Fourth, reviewer-side memory keyed on reactions: Greptile trains only on 👍/👎 ("Other emojis ... are treated as neutral"), CodeRabbit stores "Learnings" from replies with a dashboard and `local`/`global` scope, and Graphite tracks per-rule acceptance so teams can "Refine or remove rules with low acceptance rates" ([Greptile](https://www.greptile.com/docs/code-review/training-the-learning-system); [CodeRabbit learnings](https://docs.coderabbit.ai/guides/learnings); [Graphite](https://graphite.com/docs/ai-review-customization)). GitHub's Copilot added High/Medium/Low severity in May 2026 and titled findings in September ([GitHub changelog, May](https://github.blog/changelog/2026-05-12-copilot-code-review-comment-experience-improvements); [September](https://github.blog/changelog/2026-09-18-copilot-code-review-an-improved-review-experience)), while its responsible-use page concedes the tool "may highlight problems in reviewed code that do not exist" ([GitHub docs](https://docs.github.com/en/copilot/responsible-use/code-review)). The one independent head-to-head — 146 PRs, 679 findings, four tools on one PHP/React codebase — found CodeRabbit at 2.3% false positives, Bugbot 4.8%, Greptile 0% of 120, and that "93.4%" of findings were raised by exactly one reviewer with none shared by all four; weak as a single-codebase sample, it is the clearest empirical hint that a second reviewer from a different family finds different things ([dev.to comparison](https://dev.to/_vjk/best-ai-code-reviewer-in-2026-we-ran-4-in-parallel-for-3-weeks-146-prs-679-findings-1c0f)).

### Bridges all spawn the other CLI, and the headless flags have traps

Every working Claude↔Codex bridge reduces to spawning the other harness's headless CLI or wrapping that CLI in an MCP server; neither first-party MCP route yields a review. The Codex docs state that `codex mcp-server` "have been removed. Use the Codex app server instead" — a JSON-RPC interface whose `review/start` takes `uncommittedChanges`, `baseBranch`, `commit` or `custom` targets ([CLI reference](https://learn.chatgpt.com/docs/developer-commands?surface=cli); [app-server](https://learn.chatgpt.com/docs/app-server)) — and `claude mcp serve` "only exposes Claude Code's tools to your MCP client", not a reviewing model ([Claude MCP docs](https://code.claude.com/docs/en/mcp)). The project's CLI-to-CLI `reviewer.sh` is therefore the mainstream shape, and the most careful community runner, hyperskills' `cross-model-review`, independently landed on the same two safeguards — a tree fingerprint at launch and completion and a restricted tool set — while going further: `--safe-mode --permission-mode dontAsk --tools <Read,Glob,Grep>`, stripping `ANTHROPIC_API_KEY`/`ANTHROPIC_AUTH_TOKEN` to keep subscription billing, and rules such as "A finding is a claim until its cited path and trigger survive a disproof attempt", "Two reviewers agreeing increases investigation priority; it does not promote a candidate to confirmed", "Do not pipe a live review through `head` or `tail` as the sole capture", and the named anti-pattern "Treating `--allowedTools` as a sandbox" ([hyperskills SKILL.md](https://github.com/hyperb1iss/hyperskills/blob/main/skills/cross-model-review/SKILL.md); [run_claude_review.py](https://github.com/hyperb1iss/hyperskills/blob/main/skills/cross-model-review/scripts/run_claude_review.py)). Other bridges contribute single ideas: polyakov's `codex-review` writes a one-word `APPROVED`/`CHANGES_REQUESTED` verdict file where only a `## Blocking` section sets the verdict, and a PreToolUse hook denies `ExitPlanMode` without an approved plan ([polyakov](https://github.com/artwist-polyakov/polyakov-claude-skills/tree/main/plugins/codex-review)); turbo's `codex-exec` skill codifies `< /dev/null` (the project already does this), a unique absolute `-o` path per run because a relative path "can fail ... when the working directory drifts", and timeout recovery via `codex exec -o <fresh> resume <session-id> "Reply now with your complete findings..."` ([turbo codex-exec](https://github.com/tobihagemann/turbo/blob/main/claude/skills/codex-exec/SKILL.md)); PAL (formerly zen, 11,772 stars, last push 2025-12-15) is worth mining for prompt design — `[SEVERITY] File:Line – Description → Fix`, a confidence ladder where "certain" skips external validation, and a `files_required_to_continue` escape hatch — but not for its runtime, whose `clink` runs Codex with `--dangerously-bypass-approvals-and-sandbox` ([PAL codereview](https://github.com/BeehiveInnovations/pal-mcp-server/blob/main/docs/tools/codereview.md); [clink](https://github.com/BeehiveInnovations/pal-mcp-server/blob/main/docs/tools/clink.md)).

The headless facts that bear directly on `reviewer.sh` were verified on the installed versions. On the Codex side, `codex exec` defaults to `read-only`, which a `codex sandbox` probe showed denies every write — cwd, `/tmp`, `$TMPDIR`, `.git`, `__pycache__`, `~/.cache` — so a read-only reviewer cannot run pytest or node test suites that write caches; `workspace-write` allows cwd, `/tmp`, `$TMPDIR` and in-repo caches but still denies `.git`, `~/.cache` and the network, which justifies the project's `-s workspace-write` and means the reviewer cannot commit but can edit tracked files, hence the fingerprint ([Codex sandbox docs](https://learn.chatgpt.com/docs/agent-approvals-security)). The stdin hang is deterministic — with a prompt argument and a non-TTY stdin Codex prints "Reading additional input from stdin..." and blocks in `read_to_end` until EOF — so `< /dev/null` is mandatory ([exec lib.rs](https://github.com/openai/codex/blob/main/codex-rs/exec/src/lib.rs)). There is no `--reasoning-effort` flag and `-c model_reasoning_effort=<level>` is the correct form, but the user's `~/.codex/config.toml` sets `gpt-6-astra` at `xhigh`, so the project's `high` lowers the reviewer's effort below the README's promised "each harness's own default model" ([config reference](https://learn.chatgpt.com/docs/config-file/config-reference)). The Superset `codex` wrapper appends `--enable hooks --dangerously-bypass-hook-trust`, which in `--json` mode surfaces three `item.completed` events of type `error` while the exit code stays 0, so error items must be treated as warnings unless the exit code is 1. Running Codex from inside Claude Code's Bash sandbox needs `dangerouslyDisableSandbox: true`; otherwise it panics in the `system-configuration` crate before the model runs ([turbo](https://github.com/tobihagemann/turbo/blob/main/claude/skills/codex-exec/SKILL.md); [polyakov](https://github.com/artwist-polyakov/polyakov-claude-skills/tree/main/plugins/codex-review)).

On the Claude side, a nested `claude -p` works on 2.1.292 — the old "Claude Code cannot be launched inside another Claude Code session" string is absent from the binary and a local run from inside this session returned `end_turn` — but it cost **$0.59 and 73,500 cache-creation tokens for a one-word answer**, because CLAUDE.md, skill listings and MCP schemas load on every launch ([env vars](https://code.claude.com/docs/en/env-vars); [issue #32618](https://github.com/anthropics/claude-code/issues/32618)). The project's `--allowedTools "Bash,Read,Grep,Glob"` is right about one thing almost by accident — on macOS "the default set leaves out `Glob` and `Grep`" and "naming either tool in `--allowedTools` restores both" ([tools reference](https://code.claude.com/docs/en/tools-reference)) — but a bare `Bash` entry means "Tools that execute without prompting for permission", so `sed -i` or `git checkout .` run unprompted and "don't change the work" rests on the prompt alone ([CLI reference](https://code.claude.com/docs/en/cli-reference)). Worse, if the session starts in `auto` mode (a third-party provider, or telemetry off on 2.1.285 or later), "Claude Code drops a bare `Bash` entry as a broad allow rule and auto mode evaluates each command instead", silently changing the reviewer's behaviour ([headless](https://code.claude.com/docs/en/headless); [permission modes](https://code.claude.com/docs/en/permission-modes)). The documented remedy is `--permission-mode dontAsk` ("auto-denies every tool call that would otherwise prompt you" while read-only Bash and allow-listed commands still run), prefix rules such as `Bash(git diff *)` ("The space before `*` is important"), `--permission-prompts none`, and optionally the per-run Bash sandbox via `--settings '{"sandbox": {...}}'` ([permission modes](https://code.claude.com/docs/en/permission-modes); [sandboxing](https://code.claude.com/docs/en/sandboxing)). Two further traps: "Without `--bare`, a `-p` session runs the hooks in a project's `.claude/settings.json` and connects the servers in its `.mcp.json`, even in a folder you've never trusted", mitigated by `--settings '{"disableAllHooks":true}'` and `--strict-mcp-config` ([permissions](https://code.claude.com/docs/en/permissions)); and `--bare` is "the recommended mode for scripted and SDK calls" but "never reads OAuth credentials", which is why two independent wrappers use `--safe-mode` instead to keep subscription auth while dropping CLAUDE.md, skills and MCP ([headless](https://code.claude.com/docs/en/headless); [daron4ever](https://github.com/daron4ever/claude-mcp-for-codex)). `--max-turns` and `--max-budget-usd` work in print mode as circuit breakers, and `--output-format json` with `--json-schema` returns validated `structured_output` ([CLI reference](https://code.claude.com/docs/en/cli-reference); [headless](https://code.claude.com/docs/en/headless)).

## The evidence favours a fresh, different-family reviewer and two rounds, not more

### Self-review degrades; cross-family judges accept fewer wrong answers

Intrinsic self-correction — the same model critiquing and revising its own output with no external signal — does not reliably help and often hurts. Huang et al. (ICLR 2024) found GPT-4 falling on GSM8K from 95.5% to 91.5% after one self-correction round and 89.0% after two, GPT-3.5 "more likely to modify a correct answer to an incorrect one than to revise an incorrect answer", and same-model debate underperforming plain self-consistency at equal cost ([arXiv 2310.01798](https://arxiv.org/abs/2310.01798)). Kamoi et al.'s TACL survey concludes that "no prior work demonstrates successful self-correction with feedback from prompted LLMs" outside tasks exceptionally suited to it ([arXiv 2406.01297](https://arxiv.org/abs/2406.01297)). For code, Olausson et al. found self-repair gains "often modest, vary a lot between subsets of the data, and are sometimes not present at all", that at fixed budgets more initial samples beat repair — and that when GPT-4 wrote the feedback for GPT-3.5's programs, GPT-3.5 could "break through the performance barrier", which its own feedback never achieved: the clearest controlled result that a different, stronger reviewer finds more actionable faults than the author ([arXiv 2306.09896](https://arxiv.org/abs/2306.09896)). Sharma et al. supply the mechanism by which an author capitulates to a wrong finding: humans and preference models "prefer convincingly-written sycophantic responses over correct ones a non-negligible fraction of the time" ([arXiv 2310.13548](https://arxiv.org/abs/2310.13548)). Anthropic's own docs now say "A fresh context improves code review since Claude won't be biased toward code it just wrote" and describe a verification subagent that "has a fresh model try to refute the result, so the agent doing the work isn't the one grading it" ([best practices](https://code.claude.com/docs/en/best-practices)).

Self-preference bias makes the vendor of the reviewer matter, not just its context. Panickssery, Bowman and Feng showed GPT-4 recognising its own summaries with 73.5% pairwise accuracy and that "the strength of self-preference bias is linearly correlated with the LLM's self-recognition capability" ([arXiv 2404.13076](https://arxiv.org/abs/2404.13076)). A 2026 study on programmatically verifiable rubrics (IFEval, LiveCodeBench) found judges "more than 50% more likely to incorrectly mark [failed rubrics] as satisfied when the output is their own" and that they "favor outputs produced by themselves or by models from their own family" ([arXiv 2604.06996](https://arxiv.org/abs/2604.06996)); across 37 models from seven families, "the more similar the solver and verifier distributions, the more likely the verifier is to accept incorrect answers", and cross-family verification "substantially outperforms" self-verification ([arXiv 2512.02304](https://arxiv.org/html/2512.02304v2)). Self-consistent errors are model-specific — even Qwen2.5-7B and Qwen2.5-14B share only 28.7% of them ([arXiv 2505.17656](https://arxiv.org/abs/2505.17656)) — and heterogeneity is "a universal antidote" that consistently improves multi-agent debate ([arXiv 2502.08788](https://arxiv.org/abs/2502.08788)). The one industrial cross-vendor data point agrees: Uber's uReview found the best F1 by pairing "Anthropic Claude-4-Sonnet as the primary comment generator with OpenAI o4-mini-high as the review grader", with 75% of posted comments marked useful across more than 90% of about 65,000 weekly diffs — vendor-reported, with no public precision table ([uber.com](https://www.uber.com/en-GB/blog/ureview/)). Independence of context matters separately: separating production and review into independent sessions scored F1 0.376 against 0.303 and 0.263 for multi-turn variants, because "reviewers in later rounds fabricate findings when the artifact's real errors have been exhausted" and drift to "critiquing the conversation instead of the artifact" ([arXiv 2603.16244](https://arxiv.org/abs/2603.16244)). The project's architecture — a different vendor, a fresh process, sees only the diff and the ledger — is the configuration this literature most supports, and a Claude model reviewing Claude's code would retain the family-level bias. No controlled study measures a frontier model reviewing another frontier model's repository-scale diff, so the project's own logs would be the first such dataset.

### Acceptance is a filtering policy; recall is low

Field acceptance of AI review comments spans an order of magnitude and tracks filtering, not model quality. Mozilla and Ubisoft accepted 8.1% and 7.2% of lightly filtered RevMate comments, with functional findings accepted at only 4.8% and 5.2% against about 18% for refactoring ([arXiv 2411.07091](https://arxiv.org/abs/2411.07091)); Google's AutoCommenter required an 80% "useful" ratio before wider rollout, plateaued near 54% and reached 80% only after suppressing 22 problematic practice URLs ([arXiv 2405.13565](https://arxiv.org/abs/2405.13565)); Beko's Qodo deployment saw 73.8% of comments resolved but PR closure time rising from 5h52m to 8h20m, with ignored comments that "fix code blocks that are not in the scope of the task" ([arXiv 2412.18531](https://arxiv.org/abs/2412.18531)); Uber reaches 75% useful by suppressing whole low-reception categories because "when they encounter many false-positive comments, they start to tune out" ([uber.com](https://www.uber.com/en-GB/blog/ureview/)). Recall is the other half: eight frontier models detected only 15–31% of human-flagged issues on SWE-PRBench, the top four were statistically indistinguishable, and adding repository context "degraded every model monotonically" ([arXiv 2603.26130](https://arxiv.org/abs/2603.26130)); OpenAI's CriticGPT catches more bugs than contractors but with hallucination and nitpick rates "much higher" than humans ([arXiv 2407.00215](https://arxiv.org/abs/2407.00215)). Two implications follow. The project's must-fix-only brief is the policy every surviving deployment converged on, and few findings per round is the expected, healthy outcome. And `NO MUST-FIX FINDINGS` is necessary but not sufficient — at 15–31% recall, tests, builds and behavioural checks remain the primary gate, as Anthropic's docs warn that "A reviewer prompted to find gaps will usually report some, even when the work is sound" ([best practices](https://code.claude.com/docs/en/best-practices)).

### Gains concentrate in rounds one and two while diffs inflate

Across self-refinement, self-repair and UI-critique studies, most benefit arrives in the first one or two rounds and later rounds add cost and noise. Self-Refine's code-optimisation curve ran 22.0 → 27.0 → 27.9 → 28.8 ([arXiv 2303.17651](https://arxiv.org/abs/2303.17651)); a 2026 study of seven models found "most gains concentrate in the first two rounds" of repair and that logic errors repair at only about 45% ([arXiv 2604.10508](https://arxiv.org/abs/2604.10508)); the multi-turn review study's extra rounds bought +0.08 recall for 62% more false positives and precision falling from 0.30 to 0.20 ([arXiv 2603.16244](https://arxiv.org/abs/2603.16244)); GPT-4's UI-feedback accuracy fell from 52% to 39% once designers applied its edits ([arXiv 2403.13139](https://arxiv.org/abs/2403.13139)). Iteration also inflates patches: across 28 SWE-bench approaches, successful patches exceeded gold patches by a median +121.78% in total changes and +43.99% in cyclomatic complexity, with iterative-refinement systems far worse than non-iterative ones, while a post-hoc refinement step cut the excess from +242% to +4% without losing resolutions ([arXiv 2608.13292](https://arxiv.org/abs/2608.13292)). Passing tests is weak evidence of correctness: 7.8% of SWE-bench patches counted correct fail the developer-written tests and 29.6% of plausible patches "behave differently from the ground truth" ([arXiv 2503.15223](https://arxiv.org/abs/2503.15223)). The project's "stop when accepted findings stop falling" rule points the right way, and its diff-growth budget is the only explicit guard in the field against the inflation these papers measure; what the evidence adds is that the finding count does not fall to zero on its own ("false positive pressure"), so a hard cap belongs alongside the trend rule.

### Plans help when reviewed; a bad plan hurts more than none

Planning before coding gave up to 25.4% relative Pass@1 improvement over direct generation in Jiang et al. ([arXiv 2303.06689](https://arxiv.org/abs/2303.06689)) and +5.0 pp on SWE-bench Verified when coupled with memory in PMCoder ([arXiv 2608.06811](https://arxiv.org/abs/2608.06811)), but a 2026 harness-ablation study finds that "planning shifts from an accuracy scaffold for weaker models to a cost saver for stronger models, with little change in accuracy" ([arXiv 2609.20804](https://arxiv.org/abs/2609.20804)). The result that most justifies `review-plan` is asymmetric: over 21,120 SWE-agent trajectories, "providing the standard plan improves issue resolution" and "periodic plan reminders can mitigate plan violations", but "a subpar plan hurts performance even more than no plan at all" ([arXiv 2604.12147](https://arxiv.org/abs/2604.12147)). A cross-harness plan review is cheap insurance against the expensive failure mode, and it should hunt for a wrong plan — wrong files, false assumptions, missing verification, a quietly narrowed request — rather than polish a good one, which is what the project's prompt already asks. Vendor guidance to skip the plan for one-sentence diffs matches the cost-saver finding ([best practices](https://code.claude.com/docs/en/best-practices)). Claims of "3-10x higher first-pass success" from spec-driven development appear only in consultancy blogs with no methodology ([devtoollab](https://devtoollab.com/blog/spec-driven-development-ai-agents)); METR's randomised trial found experienced developers 19% slower with AI in early 2025 and its 2026 follow-up offers "only very weak evidence" of a reversal ([arXiv 2507.09089](https://arxiv.org/abs/2507.09089); [METR update](https://metr.org/blog/2026-02-24-uplift-update/)).

### Vision models judge goals well and geometry badly

Frontier VLMs are now reliable for coarse visual judgments and unreliable for exactly the primitives layout review needs. On 1,000 UICrit screens, GPT-5, Claude 4 Sonnet and Gemini 2.5 Pro reached "almost perfect" agreement with expert ratings (KBP ≥ 0.81) on Aesthetics and Design Quality zero-shot, but over-estimated Usability, Learnability and Efficiency by 1–3 points, and few-shot prompting "generally worsened agreement" ([HCI International 2026](https://2026.hci.international/MOBILE-best-paper-award.html)); a separate study found strong rank correlation for aesthetics (Claude r = 0.62) and near-zero for ease of use, recommending "supplemental use" only ([arXiv 2510.08783](https://arxiv.org/html/2510.08783v1)). On geometric primitives, "Vision language models are blind" reports an average of 58.07% on seven trivial tasks, with GPT-4o at 72.69% on whether two circles overlap or touch and 42.50% on counting overlapping circles, and notes that models "struggle with ... geometric primitives that overlap or are close together" ([arXiv 2407.06581](https://arxiv.org/abs/2407.06581)); GUI grounding on high-resolution professional apps reached 18.9% ([arXiv 2504.07981](https://arxiv.org/abs/2504.07981)). Unaided critique precision has been low — 13.1% of Gemini Pro Vision's zero-shot UI critiques were valid in UICrit ([arXiv 2407.08850](https://arxiv.org/abs/2407.08850)), GPT-4V scored 51.58% on UIClip's pairwise "which design is better" test, around chance, with "realistic-sounding but inaccurate reasoning" ([arXiv 2404.12500](https://arxiv.org/html/2404.12500v1)), and GPT-4 "misdetect[ed] overlaps based on bounding boxes when elements don't visually overlap" in Duan et al. ([arXiv 2403.13139](https://arxiv.org/abs/2403.13139)). Structure fixes much of this: Set-of-Mark annotated screenshots lifted widget-occlusion detection to F1 87.2% ([arXiv 2604.19081](https://arxiv.org/abs/2604.19081)), and a 4B VLM went from 36% to 84% micro-F1 on UI principle violations after RL ([arXiv 2607.20690](https://arxiv.org/abs/2607.20690)). Both vendors document the weaknesses the project's prompt leans on: Anthropic says Claude "can give approximate counts of objects in an image but might not always be precisely accurate, especially with large numbers of small objects" and that "coordinate and localization outputs are approximate" ([Anthropic vision](https://platform.claude.com/docs/en/build-with-claude/vision)); OpenAI lists "Small text", precise spatial localisation and approximate counting as limitations ([OpenAI vision](https://developers.openai.com/api/docs/guides/images-vision)). The project's instruction "Where a goal can be counted, count it" therefore asks for the weakest skill; the fix is for the builder to state expected counts in `design-context.md` so the reviewer verifies rather than counts.

## Loops in the wild stop on hard caps because trend rules do not terminate

Every reference loop design separates the worker from the judge, gives the judge a narrow brief and bounds the loop with something mechanical. Anthropic's evaluator-optimizer pattern is recommended only "when we have clear evaluation criteria, and when iterative refinement provides measurable value", and the same post advises "stopping conditions (such as a maximum number of iterations)" ([Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)). Claude Code's own primitives all carry ceilings: Stop hooks hit "an 8-consecutive-continuation cap", and `/goal` stops when Claude "keeps answering the evaluator without making progress" while its docs suggest adding "or stop after 20 turns" to the condition ([hooks](https://code.claude.com/docs/en/hooks); [/goal](https://code.claude.com/docs/en/goal)). The Ralph Wiggum plugin says "Always rely on --max-iterations as your primary safety mechanism" ([ralph-wiggum](https://github.com/anthropics/claude-code/tree/main/plugins/ralph-wiggum)); superpowers caps fix rounds at five, escalating to "a fresh implementer on a more capable model" from round four and having the controller "adjudicate each open finding yourself" after round five ([subagent-driven-development](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md)); antonmd's Stop-hook gate makes "Later rounds ... verify-only — the reviewer checks whether prior findings were resolved instead of hunting for new ones (this kills the late-round false-positive escalation common to iterated LLM review)" and fails open when Codex errors ([claude-review-pack](https://github.com/antonmd/claude-review-pack)). Anthropic's own harness engineers report that "When asked to evaluate work they've produced, agents tend to respond by confidently praising the work" and that it "took several rounds of this development loop before the evaluator was grading in a way that I found reasonable" ([Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)).

Practitioner issue trackers from 2026 show why a trend rule alone is insufficient. One PR drew "11 consecutive CHANGES_REQUESTED reviews" whose findings shifted category each round — naming, validation, dead code, unicode, stale base, commit types, test naming — because "The review agent reviews each iteration without awareness of the broader trajectory" ([fullsend #1294](https://github.com/fullsend-ai/agents/issues/1294)); on another, "Roughly 17 of 20 findings were generated by the previous round's fix" over nine rounds ([rjmurillo #5487](https://github.com/rjmurillo/ai-agents/issues/5487)); across a fleet of 29 PRs, of 91 Important findings raised after round one "40 (44%) appeared in code the previous fix changed", "19 (21%) were repeats, with 8 re-raised after reasoned declines", and "Rounds 5 and 6 contradicted each other" ([MultiAgency #116](https://github.com/MultiAgency/near-agencies/issues/116)). A spec-review loop produced "Blocking findings per round: 16, 5, 3, 2, 1, 1" — the project's plateau-once rule would have stopped it at the second 1 ([agentrof #427](https://github.com/agentrof/agent-marketplace/issues/427)); another concluded that "PASS requires zero open material findings. Any fresh reviewer context handed a 60 KB spec ... can always generate another string-level finding", after 12 cycles, 81 findings and "64 of 91 branch commits" as review overhead ([gtrabanco #205](https://github.com/gtrabanco/agentic-workflow/issues/205)). Two analyses name the structural problem: a stochastic verifier gives a refinement loop no convergence guarantee, so "The max_iterations cap is a confession" ([TianPan](https://tianpan.co/blog/2026/05/31/the-verifier-loop-that-couldnt-converge)), and a loop reaching its budget "looks identical to a loop exiting on convergence" unless the exit is named ([Contrast Security](https://www.contrastsecurity.com/security-influencers/when-ai-reviewers-cannot-agree)). MCR-Bench's 2,269 real multi-round tasks average 3.8 rounds, with the best model's F1 falling 56% from round 2 to round 10 and "State-Temporal Misalignment (32.5%)" — re-raising resolved defects as new — the top failure ([Vaughan on MCR-Bench](https://codex.danielvaughan.com/2026/09/01/mcr-bench-dynamic-code-review-multi-round-state-tracking-codex-cli/)). Caps in use run from 2 ([gtrabanco](https://github.com/gtrabanco/agentic-workflow/issues/205)) through 3 ([quiet-solar #375](https://github.com/tmenguy/quiet-solar/issues/375)), 4 ([tessl auto-review-loop](https://tessl.io/registry/skills/github/wanshuiyin/Auto-claude-code-research-in-sleep/auto-review-loop--8c21efd9569d3829ffa2e644563bd256c9de45a444c23c47f16dd9e90eb3f128)) and 5 ([superpowers](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md)) to 6 as a non-convergence alarm ([fullsend](https://github.com/fullsend-ai/agents/issues/1294)). Against these numbers the project's rule typically ends at round 2–4, which is where the data say useful findings stop, but its implicit bound (roughly the round-one accepted count plus two) is loose when round one is large; a cap of three with a raised bar afterwards is the modal practitioner choice, and quiet-solar states it as "After round 1 the bar rises: only must-fix issues in the new changes, or regressions, keep the loop going" ([quiet-solar #375](https://github.com/tmenguy/quiet-solar/issues/375)).

The ledger pattern has matured past "settled choices". quiet-solar tracks statuses `open`, `fixed`, `rejected`, `deferred`, `settled`, each "with the round it originated from and the change that resolved it", detects flip-flops (a finding that would "revert or rework a change made to resolve an earlier finding") and auto-rejects them once ruled ([quiet-solar #375](https://github.com/tmenguy/quiet-solar/issues/375)); recoder gives each defect "an identity based on its behavior and cause. A moved line or changed category must not create a new defect", records "one dismissal reason: wrong, not worth fixing, already handled, style preference, or duplicate", and warns "Use wrong findings as evaluation labels. Do not treat other dismissal reasons as false-positive labels" ([recoder #72](https://github.com/aidan-neel/recoder/issues/72)); fullsend found a reviewer re-raising a finding across three rounds although the fixer had marked it "Disagreed" twice, and separately that 3 of 6 findings in one review were "self-dismissed within the same finding text" — the reviewer argued the code was fine, then emitted the finding anyway ([fullsend #1154](https://github.com/fullsend-ai/agents/issues/1154); [fullsend #1106](https://github.com/fullsend-ai/agents/issues/1106)). The project's "reconsider once if re-raised with a reason" is a stricter version of Keel's rule that disproved findings return "only with fresh arguments" ([Keel #18](https://github.com/KBT-0/MyAgentKit_Keel/issues/18)); what is missing is identity by behaviour (a reworded re-raise slips past a text-matched settled choice) and recording accepted findings with the fix that resolved them, which is what enables "finding in code the last fix changed" attribution. No public ledger was found that two different vendors' agents share, so a `decisions.md` read by both harnesses is itself novel.

Tamper protection in the sources is preventive first and detective second. Claude Code's reviewer-subagent recipe is `tools: Read, Glob, Grep`, `disallowedTools: Write, Edit`, `permissionMode: plan` ("recommended for reviewers") ([subagents](https://code.claude.com/docs/en/sub-agents)); agent teams treat inter-agent messages as untrusted — "A teammate can't approve a permission prompt or supply consent on your behalf" ([agent teams](https://code.claude.com/docs/en/agent-teams)). The measured threat is the builder rather than the reviewer: o3 "reward-hacked in 39 of 128 runs on RE-Bench", GPT-5 "cheated in 54% of these impossible tasks", and "Making tests read-only stopped test changes without significantly hurting honest performance" while hiding tests hurt more; the recommended defences are a PreToolUse block on test-path writes, "Get changed files directly from Git, not from the agent's own report", and failing closed when zero tests run ([aimlcompanion](https://aimlcompanion.ai/blog/reward-hacking-coding-agents-2026)). A related loop found assertion text leaking through "error messages, log tails (particularly the final 2000 characters), and retry prompts" let the worker satisfy the assertion instead of the requirement, and that "an information barrier that can be turned off will get turned off on some afternoon when someone is behind schedule" ([dev.to q00](https://dev.to/q00/your-agent-loop-is-teaching-the-model-to-cheat-48oa)). The project's "each round-one fix gets a test" rule has no protection against the builder weakening tests in later rounds; its fingerprint detects reviewer edits after the fact and has no published evaluation, but it is consistent with the keep-a-backstop advice.

On finding format and false positives, the current bar is file and line, a concrete failure scenario and evidence of confirmation, with severity collapsed to two or three levels. Refute-or-Promote's security pipeline, where "Adversarial agents attempt to disprove candidates at each promotion gate", eliminated "Approximately 79% of 171 candidates" before disclosure and recorded a case where "ten reviewers unanimously endorsed a non-existent vulnerability until a single empirical test rejected it" ([arXiv 2604.19049](https://arxiv.org/abs/2604.19049)); structured disagreement between coder, reviewer and critic gave the "Highest F1 among tested methods on SWE-PRBench" ([arXiv 2608.18167](https://arxiv.org/abs/2608.18167)). Ten independent passes over a 359-line C module reached 34%, 61% and 76% cumulative defect coverage at one, three and five passes, with "four of the five most frequently reported findings" false — so a reviewer repeating a finding is not evidence it is real ([braindetox](https://braindetox.kr/en/posts/ai_review_diminishing_returns.html)). Augment's compilation of primary figures adds that Claude Haiku 4.5 scored F1 0.800 on 10–50-line diffs but 0.043 on 150–600-line diffs, a Reflexion-style loop lifted recall from 27.01% to 32.76% while signal-to-noise fell from 5.11 to 1.95, Google's Tricorder kept its "effective false positive rate ... under 10%" by measuring "Not useful" clicks, and a CodeRabbit field study saw "56.3% of agentic reviews rejected by developers" over 31,073 comments ([Augment guide](https://www.augmentcode.com/guides/ai-code-review-accuracy)). The diff-size sensitivity is a second argument for the project's diff budget: a loop that grows the diff degrades its own reviewer.

## Design review needs tiled captures, structured inputs and a delivery check

The project's `screenshot.sh` already uses the best readiness heuristic the headless CLI offers: `--virtual-time-budget` makes Chromium wait while "there are pending network fetches" and then fast-forward timers until the budget is exhausted, approximating "network idle plus settled timers" without a wall-clock sleep ([Chromium headless switches](https://chromium.googlesource.com/chromium/src/+/main/components/headless/command_handler/headless_command_switches.cc)). What the CLI cannot do is click, emulate `prefers-color-scheme` (`--force-dark-mode` applies a filter that "differs from simulating the `prefers-color-scheme: dark` media query that respects sites' native dark mode implementations"), set device scale independently of the window, or capture beyond `--window-size`; the 1440x4000 "full page" is a 4000 px tall viewport, which renders `100vh` layouts and sticky elements differently from a true `fullPage` capture ([Chromium headless docs](https://developer.chrome.com/docs/chromium/headless); [dark-mode screenshot article](https://fullpage-screenshot.ai.studio/articles/screenshot-dark-mode-wrong-theme)). A Playwright script — the pattern in Anthropic's own `webapp-testing` skill, which launches `chromium.launch(headless=True)` and waits for `networkidle` ([webapp-testing](https://github.com/anthropics/skills/blob/main/skills/webapp-testing/SKILL.md)) — replaces the Chrome-finding shell with roughly the same install cost and gains `fullPage`, `mask`, `animations: "disabled"`, `scale: "css"`, `page.emulateMedia({ colorScheme: 'dark' })` and `devices['iPhone 13']` with correct `deviceScaleFactor` and `isMobile` ([Playwright screenshot](https://playwright.dev/docs/api/class-page#page-screenshot); [Playwright emulation](https://playwright.dev/docs/emulation)). For clickable states the builder can use Playwright MCP (`claude mcp add playwright npx @playwright/mcp@latest`; `codex mcp add playwright npx "@playwright/mcp@latest"`), which works from "Playwright's accessibility tree, not pixel-based input" and offers `--headless`, `--device`, `--viewport-size`, `browser_take_screenshot` with `fullPage`, and `--caps=testing` verify tools ([playwright-mcp](https://github.com/microsoft/playwright-mcp)), or Chrome DevTools MCP, whose `emulate` tool sets `colorScheme`, whose `lighthouse_audit` returns accessibility scores, and whose `--screenshotMaxWidth`/`--screenshotMaxHeight` "Downscale images before return"; both default to headed mode, so `--headless` must be passed ([chrome-devtools-mcp tools](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/tool-reference.md); [configuration](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/configuration.md)). shot-scraper's `multi` YAML, with `width`, `height`, `wait_for`, `javascript` and `selector` per shot and a `server:` key that starts the app and kills it afterwards, is the closest existing analogue of the project's script ([shot-scraper multi](https://shot-scraper.datasette.io/en/stable/multi.html)). First-party browsers are out for the headless reviewer: Claude Code's computer use "is not available in non-interactive mode with the `-p` flag" ([computer use](https://code.claude.com/docs/en/computer-use)), and Codex's Chrome extension is "Codex app only — no CLI support" according to a third-party account ([Vaughan on Codex for Chrome](https://codex.danielvaughan.com/2026/05/07/codex-for-chrome-extension-browser-integration-authenticated-workflows/)).

Resolution is the project's most consequential screenshot problem. Anthropic's documented rule resizes to the largest aspect-preserving size within an edge limit (1568 px on the standard tier, 2576 px for Claude 4.7 and later) and a visual-token limit (1568 or 4784 tokens at 28×28 px patches), noting that "The edge limit takes over only for elongated images such as panoramas or tall phone screenshots" ([Anthropic vision](https://platform.claude.com/docs/en/build-with-claude/vision); [vision coordinates](https://platform.claude.com/docs/en/build-with-claude/vision-coordinates)). Applying that formula — a computation from the published rule, not a vendor table — 1440x900 shrinks slightly to about 1372x857 on the standard tier and passes unchanged on high-res; 390x844 is never resized; **1440x4000 shrinks to about 564x1568 on the standard tier (scale 0.39, so 16 px UI text renders at about 6 px) and about 927x2576 on high-res**, making it the capture most likely to produce false "too small or faint to read" findings or to miss real ones. Anthropic's guidance is explicit: "If the image contains important text, make sure it's legible and not too small", "Consider pre-resizing your images, cropping them, or both", "for fine targets, crop the region of interest and send the crop", put "images before text" and label them "Image 1:", "Image 2:" ([Anthropic vision](https://platform.claude.com/docs/en/build-with-claude/vision); [vision coordinates](https://platform.claude.com/docs/en/build-with-claude/vision-coordinates)). Tiling the full-page capture into viewport-height slices of at most 1568 px keeps text legible on both tiers. Codex offers no `detail` control from `codex exec --image`, so pre-sizing is the only lever there; `-i`/`--image` with comma-separated or repeated paths is confirmed in the source while count and size limits are undocumented ([exec cli.rs](https://raw.githubusercontent.com/openai/codex/main/codex-rs/exec/src/cli.rs); [Vaughan on image workflows](https://codex.danielvaughan.com/2026/03/28/codex-cli-image-workflows/)). Delivery itself needs a check: Claude Code issue #25960 reports that in `-p` mode the model fabricated image content with a "100% hallucination rate (20+ tests)" when the Read tool's image data did not actually arrive, while interactive mode reported the failure honestly ([issue #25960](https://github.com/anthropics/claude-code/issues/25960)); other reports show Read rejecting PNGs with large transparent areas ([issue #11560 mirror](https://claudeissues.com/issue/11560-bug-read-tool-crashes-on-pngs-with-large-transparent-areas-400-could-not-process)). A canary — a small PNG with a random word the reviewer must transcribe first, or a requirement to state each screenshot's pixel dimensions — turns silent fabrication into a detectable failure.

The published design-review skills share a checklist and differ in triage. OneRedOak's `design-review` agent, the most complete, drives Playwright MCP through seven phases at 1440/768/375 px — interaction states, "Verify no horizontal scrolling or element overlap", visual polish, keyboard order and "visible focus states", "color contrast ratios (4.5:1 minimum)", form validation and "loading, empty, and error states", design-token use, copy clarity and the "browser console for errors/warnings" — reports as [Blocker]/[High-Priority]/[Medium-Priority]/[Nitpick] with "Issue + Evidence", and insists on "Problems Over Prescriptions: You describe problems and their impact, not technical solutions" ([design-review-agent.md](https://raw.githubusercontent.com/OneRedOak/claude-code-workflows/main/design-review/design-review-agent.md)). Vercel's web-interface-guidelines skill is code-only, with "100+ rules", a terse `file:line - [guideline] fix` format and numeric thresholds a reviewer can apply to a screenshot: input text "≥ 16px on mobile", hit targets of at least 24 px (44 px on mobile), a visible `:focus-visible` ring, `min-w-0` on flex children, and "Prefer APCA over WCAG 2" for contrast ([web-interface-guidelines](https://github.com/vercel-labs/web-interface-guidelines); [command.md](https://raw.githubusercontent.com/vercel-labs/web-interface-guidelines/main/command.md)). Anthropic's `frontend-design` skill is a build skill whose self-critique instruction — "Critique your own work as you build, taking screenshots to review if your environment supports it — a picture is worth 1000 tokens" — and list of AI-aesthetic tells (identical rounded cards with the same shadow, ALL-CAPS eyebrows, "→" appended to buttons) double as review heuristics ([frontend-design](https://github.com/anthropics/skills/blob/main/skills/frontend-design/SKILL.md)). None of them separates "a stated goal the screenshots show is not met" from aesthetic findings the way the project's prompt does, and the VLM evidence says that separation is right: models judge "goal met" and gross breakage far better than abstract quality. The cheap additions are a 768 px pass, a dark-mode capture, a Tab-press capture for focus, and the empty, loading and error states when the task touches them, with `design-context.md` stating which states were not captured so their absence is not reported as a defect.

Objective checks can produce the facts the VLM then interprets. `@axe-core/playwright` returns violations with `impact` (minor to critical), `helpUrl` and the failing nodes, filterable by `wcag2aa` or `wcag22aa` tags ([axe-core-npm](https://github.com/dequelabs/axe-core-npm/blob/develop/packages/playwright/README.md)); Lighthouse needs Node 22 and runs with `--only-categories accessibility --chrome-flags="--headless=new"` ([Lighthouse](https://github.com/GoogleChrome/lighthouse)); contrast is something every source measures with a tool, since no study quantifies how well a model estimates ratios from pixels. Pixel diffing is cheap and bounded: `pixelmatch` "returns the number of mismatched pixels" between same-size PNGs ([pixelmatch](https://github.com/mapbox/pixelmatch)), and Playwright's `toHaveScreenshot` adds `maxDiffPixels`, `mask` and `animations: "disabled"` but warns that "Browser rendering can vary based on the host OS, version, settings, hardware, power source (battery vs. power adapter), headless mode, and other factors" ([Playwright snapshots](https://playwright.dev/docs/test-snapshots)) — so compare only same-machine, same-session before/after captures of pages the task did not touch, and never commit baselines. Argos's ARIA-snapshot diffing, which "compares the accessibility tree (roles, labels, and structure) alongside the pixel screenshot", suggests a free non-pixel check: diff the accessibility snapshot before and after to catch "information no longer reachable" with zero rendering noise ([cloudzy comparison](https://cloudzy.com/blog/argos-vs-lost-pixel-vs-backstopjs-compared/)). SaaS regression tools add accounts and uploads that conflict with a local two-agent loop, and Lost Pixel was archived in April 2026 ([Chromatic Playwright](https://www.chromatic.com/docs/playwright/); [cloudzy](https://cloudzy.com/blog/argos-vs-lost-pixel-vs-backstopjs-compared/)). Finally, because a `-p` run kills background shells "about five seconds after Claude has returned its final result", the builder must keep the app running itself, as the skill already does ([headless](https://code.claude.com/docs/en/headless)).

## Distribution already matches the de facto layout; invocation controls and paths are the gaps

The Agent Skills specification that Anthropic opened on 18 December 2025 is small: a `SKILL.md` with six front-matter keys (`name`, `description`, `license`, `compatibility`, `metadata`, `allowed-tools`), optional `scripts/`, `references/` and `assets/`, three-tier progressive disclosure ("~100 tokens" of metadata at startup, "< 5000 tokens recommended" when activated), "Keep your main `SKILL.md` under 500 lines", relative file references "one level deep", and a `skills-ref validate` reference library ([spec](https://agentskills.io/specification); [skills-ref](https://github.com/agentskills/agentskills/tree/main/skills-ref); [SiliconANGLE](https://siliconangle.com/2025/12/18/anthropic-makes-agent-skills-open-standard/)). The client showcase lists about 47 products including Claude Code, "ChatGPT & Codex", Cursor, Gemini CLI, GitHub Copilot and VS Code ([clients](https://agentskills.io/clients.md)), and the implementation guide names `.agents/skills/` as "a widely-adopted convention for cross-client skill sharing" while noting that "Some implementations also scan `.claude/skills/`" ([adding skills support](https://agentskills.io/client-implementation/adding-skills-support.md)).

The installer's layout is exactly what both harnesses need today, and two probes settle the question. Claude Code 2.1.292 does **not** read `~/.agents/skills`: a probe skill placed there with no symlink was reported as not installed by `claude -p "/zz-probe-agentsdir"`, even though the string `.agents/skills` exists in the binary; it does follow symlinks in personal, project and enterprise locations, loading a target's `SKILL.md` once ([Claude Code skills](https://code.claude.com/docs/en/skills)). Codex 0.160.1 reads `$HOME/.agents/skills`, repo-level `.agents/skills` up to the Git root, `/etc/codex/skills` and bundled system skills — and, by probe, still `~/.codex/skills`, which its bundled `skill-installer` and `skill-creator` continue to target, so a same-named skill there would shadow or duplicate the installed one; there is no `codex skills` subcommand ([Codex skills](https://learn.chatgpt.com/docs/build-skills)). Catalog budgets bound how many skills can coexist: Codex caps the skills list at "2% of the model's context window, or 8,000 characters when the context window is unknown", Claude Code at 1% with each entry's description plus `when_to_use` "truncated at 1,536 chars", dropping descriptions "starting with the skills you invoke least" ([Codex skills](https://learn.chatgpt.com/docs/build-skills); [Claude Code skills](https://code.claude.com/docs/en/skills)). One historical trap for installers: "Before v2.1.280, a file named `manifest.json` in `~/.claude/skills/` caused Claude Code to move the skill folders that file listed into a timestamped folder under `~/.claude/skills/.trash/`" ([Claude Code skills](https://code.claude.com/docs/en/skills)).

Invocation control is where the harnesses diverge and where `ship` is exposed. Claude Code's `disable-model-invocation: true` "Prevents Claude from loading skill automatically; manual invocation only" and removes the description from context, `user-invocable: false` hides a skill from the `/` menu, `context: fork` with `agent:` and `background: false` runs a skill in an isolated subagent and waits, `allowed-tools` pre-approves commands such as `Bash(${CLAUDE_SKILL_DIR}/scripts/render.sh *)`, and a skill named `verify` or `simplify` is auto-run before every commit since v2.1.286 ([Claude Code skills](https://code.claude.com/docs/en/skills)). Codex keeps `SKILL.md` to spec keys and puts behaviour in a sidecar `agents/openai.yaml`, where `policy: allow_implicit_invocation: false` means the skill is not injected into context by default but remains callable as `$skill-name` — the bundled `review-agent` system skill ships exactly that ([Codex skills](https://learn.chatgpt.com/docs/build-skills)). OpenAI's authoring guidance pushes the other way — "Do not infer explicit-only invocation from sensitive operations or required approvals: keep the skill discoverable and require authorization immediately before the actual mutation" — so making `ship` explicit-only is a deliberate choice against that default, one mattpocock's library also makes by putting `disable-model-invocation: true` on its orchestrators ([mattpocock README](https://github.com/mattpocock/skills)). Validator cleanliness is a trade-off: claude.ai upload rejects non-spec keys with "Unexpected key(s) in SKILL.md frontmatter", and Codex's bundled `quick_validate.py` allows only `name`, `description`, `license`, `allowed-tools` and `metadata` — not `compatibility` — and rejects `<` or `>` in descriptions ([Claude Code skills](https://code.claude.com/docs/en/skills)).

Three distribution models sit beside a hand-written installer. Vercel's `skills` CLI (`npx skills add <owner>/<repo>`, with `-g` and `-a` to pick agents) copies to a canonical `.agents/skills/<name>` and symlinks each agent's directory — the same two global paths the installer uses — tracks installs in `skills-lock.json`, offers `check` and `update` against GitHub, and knows 75+ agents; a repository laid out as `skills/<name>/SKILL.md` is discovered without extra files, and skills.sh ranks repositories by installs ([vercel-labs/skills](https://github.com/vercel-labs/skills); [skills CLI options](https://mintlify.wiki/vercel-labs/skills/api/cli-options); [skills.sh](https://skills.sh/)). Claude Code plugin marketplaces add `ref`/`sha` pinning, `renames`, `forceRemoveDeletedPlugins`, opt-in auto-update (off by default for third-party marketplaces), `claude plugin validate` and `claude plugin eval` (v2.1.269+, each case run three times, `--ablation with-without` for a no-plugin baseline), at the cost of namespaced `/plugin:skill` invocation ([marketplace reference](https://code.claude.com/docs/en/plugins/marketplace-reference); [host a marketplace](https://code.claude.com/docs/en/plugins/host-marketplace); [plugin evals](https://code.claude.com/docs/en/plugin-evals)). Codex plugins use `.codex-plugin/plugin.json`, a `~/.agents/plugins/marketplace.json` with `local` or Git sources, `codex plugin marketplace add` and `codex plugin add`; the binary also contains the path `.claude-plugin/plugin.json`, a string-level observation rather than documented behaviour ([OpenAI plugins](https://developers.openai.com/plugins/build/plugins)). The installer's HTML-comment ownership marker has no analogue in any of these; the nearest are the Vercel lockfile and ruler's `.bak` backups with start/end markers ([ruler](https://github.com/intellectronica/ruler)).

The duplicated instruction block is the only portable mechanism, because Codex has no import syntax. Claude Code's `~/.claude/CLAUDE.md` supports `@path` imports to "a maximum depth of four hops", loads user-scope imports without an approval dialog, reads `~/.claude/rules/*.md` for every project, and advises "target under 200 lines per CLAUDE.md file" ([memory docs](https://code.claude.com/docs/en/memory)). Since v2.1.277 Claude Code "can read `AGENTS.md` as your project instructions" when no `CLAUDE.md` exists, so the README's advice to add a `CLAUDE.md` containing `@AGENTS.md` is now optional ("you can leave it") ([memory docs](https://code.claude.com/docs/en/memory)). Codex reads `~/.codex/AGENTS.md`, honours `AGENTS.override.md`, concatenates project files root-down under a `project_doc_max_bytes` cap of 32 KiB, and has no import syntax ([Codex AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)); the AGENTS.md convention is "used by over 60,000 open-source projects" and stewarded by the Agentic AI Foundation ([agents.md](https://agents.md/)).

Authoring guidance from both vendors agrees with what the project already does on two counts and disagrees on two. Descriptions should be third person stating what the skill does and when to use it — Codex adds "Explain exactly when this skill should and should not trigger" and "Include a meaningful boundary when similar requests should not activate the skill" — which the `ship` description ("Use only when the user explicitly asks to ship; never on your own initiative") already satisfies ([Anthropic best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices); [Codex skills](https://learn.chatgpt.com/docs/build-skills)). Scripts belong where "Operations are fragile and error-prone" or a specific sequence must be followed, must "Avoid interactive prompts", and should keep "Predictable output size" because harnesses truncate "10-30K characters" ([Anthropic best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices); [using scripts](https://agentskills.io/skill-creation/using-scripts.md)). The two divergences: the spec and both vendors say to "Use **relative paths from the skill directory root** to reference bundled files" (Claude Code adds `${CLAUDE_SKILL_DIR}` for when the cwd differs), whereas the README's convention "Refer to helper scripts by their installed path, `~/.agents/skills/<name>/...`" ties the skills to one layout and breaks project-scope installs, `--plugin-dir` loading and plugin packaging, where `${CLAUDE_PLUGIN_ROOT}` changes per version ([using scripts](https://agentskills.io/skill-creation/using-scripts.md); [Claude Code skills](https://code.claude.com/docs/en/skills); [plugin manifest](https://code.claude.com/docs/en/plugins/manifest-reference)); and `review-plan` and `review-design` call `~/.agents/skills/review-loop/reviewer.sh`, a cross-skill dependency that both vendors' "Keep each skill focused on one job" guidance discourages. On testing, Anthropic says "Create evaluations BEFORE writing extensive documentation", at least three per skill, across Haiku, Sonnet and Opus; Claude Code offers `/skill-doctor` (context cost, invocation frequency, unused skills) and the `skill-creator` plugin's description tuning that "Generates should/shouldn't-trigger prompts; measures hit rate" ([Anthropic best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices); [Claude Code skills](https://code.claude.com/docs/en/skills)); OpenAI's plugin guidance lists five request categories to test, including "Requests that should not activate the skill" ([OpenAI build skills](https://developers.openai.com/plugins/build/skills)).

## Prioritised improvements, each tied to its evidence

Ordered by value for cost. Each item is tagged **[Verified]** when it rests on documentation or a measurement on the installed Claude Code 2.1.292 and Codex CLI 0.160.1, **[Inference]** when it is reasoning from those facts or from the studies above, and **[Vendor claim]** when the motivating figure comes from the party selling or operating the tool.

1. **Make the Claude reviewer unable to edit, not merely told not to.** Replace `--allowedTools "Bash,Read,Grep,Glob"` with `--permission-mode dontAsk --permission-prompts none`, allow rules `Read`, `Grep`, `Glob`, `Bash(git status *)`, `Bash(git diff *)`, `Bash(git log *)`, `Bash(git show *)`, the project's check commands and `Bash(mkdir -p .local/scratch*)`, and `--disallowedTools "Edit" "Write" "NotebookEdit" "mcp__*"`; read-only shell builtins still run without rules, and anything else is denied instead of executed. Keep the fingerprint as the backstop. **[Verified]**: a bare `Bash` entry approves every shell command, `dontAsk` auto-denies prompts while read-only Bash and allow-listed commands run, and the bare entry is silently dropped in `auto` mode ([CLI reference](https://code.claude.com/docs/en/cli-reference); [permission modes](https://code.claude.com/docs/en/permission-modes); [headless](https://code.claude.com/docs/en/headless)). Whether `npm test`-style commands spawn subprocesses the prefix rules miss needs a local test before adoption **[Inference]**.

2. **Harden and cheapen the `claude -p` launch.** Always pin `--permission-mode`; add `--settings '{"disableAllHooks":true}' --strict-mcp-config` so a reviewer run against an untrusted checkout cannot execute the repository's hooks or `.mcp.json` servers; add `--no-session-persistence`, `--max-turns` and `--max-budget-usd` as circuit breakers; prefer `--safe-mode` (keeps OAuth, drops CLAUDE.md, skills and MCP) over `--bare` unless an API key is acceptable; and use `--output-format json` so the builder can read `result`, `permission_denials` and `total_cost_usd`. **[Verified]**: a `-p` session "runs the hooks in a project's `.claude/settings.json` and connects the servers in its `.mcp.json`, even in a folder you've never trusted" ([permissions](https://code.claude.com/docs/en/permissions)); `--bare` "never reads OAuth credentials" ([headless](https://code.claude.com/docs/en/headless)); a nested one-word `-p` run here cost $0.59 with 73,500 cache-creation tokens (single local sample, so the saving from `--safe-mode` is **[Inference]** until measured).

3. **Fix the Codex launch details.** Drop `-c model_reasoning_effort=high` or expose effort as a knob mirroring `/code-review low|medium|high`, since the user's `~/.codex/config.toml` default is `xhigh` and the README promises the harness default; keep `-s workspace-write` (the only sandbox that lets the reviewer run cache-writing test suites) but tell the prompt that `.git` and `$HOME` are write-protected so denied cache writes are not misreported as project bugs; make the `-o` path absolute via `git rev-parse --show-toplevel`; on a 10-minute timeout resume with `codex exec -o <fresh> resume <session-id> "Reply now with your complete findings..." < /dev/null` instead of restarting; in `--json` mode treat `item.type == "error"` as a warning unless the exit code is 1 (the Superset wrapper's hook-trust notice appears there). **[Verified]** by local probes and the config reference ([config reference](https://learn.chatgpt.com/docs/config-file/config-reference); [sandbox docs](https://learn.chatgpt.com/docs/agent-approvals-security); [turbo codex-exec](https://github.com/tobihagemann/turbo/blob/main/claude/skills/codex-exec/SKILL.md)).

4. **Add a hard round cap and name the exit.** Keep the accepted-count trend rule and the diff budget, add a cap of three review-fix rounds, and have the end-of-loop summary state which exit fired (clean, count rose, second plateau, diff budget, round cap) so a budget exit is never mistaken for convergence. Make rounds two and three verify-only against the previous findings first, then look for new must-fix items. **[Inference]** from controlled evidence that extra rounds add 62% more false positives for +0.08 recall ([arXiv 2603.16244](https://arxiv.org/abs/2603.16244)) and that gains concentrate in the first two repair rounds ([arXiv 2604.10508](https://arxiv.org/abs/2604.10508)); practitioner caps run 2–5 ([quiet-solar #375](https://github.com/tmenguy/quiet-solar/issues/375); [superpowers](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md)); "a loop reaching its budget looks identical to a loop exiting on convergence" ([Contrast Security](https://www.contrastsecurity.com/security-influencers/when-ai-reviewers-cannot-agree)); verify-only later rounds "kill the late-round false-positive escalation" ([claude-review-pack](https://github.com/antonmd/claude-review-pack)).

5. **Borrow the vendors' rubric tests into `reviewer-prompt.md`.** Add: the bug must be introduced by this change ("pre-existing bugs should not be flagged"); speculation that a change "may disrupt another part of the codebase" does not count unless the affected code is "provably affected"; no reliance on "unstated assumptions about the codebase or author's intent"; report only what "the original author would fix if they knew about it", and "prefer outputting no findings" otherwise; body at most one paragraph with no code chunk over three lines, stating the inputs or environment that trigger the failure. Add a per-finding confidence field (`confirmed-by-running | confirmed-by-reading | plausible`) and an explicit "zero findings is a valid result". **[Verified]** text of Codex's rubric ([rubric.md](https://github.com/openai/codex/blob/main/codex-rs/prompts/templates/review/rubric.md)) and Claude's verify vote (binary strings; documented at [code-review docs](https://code.claude.com/docs/en/code-review)); the ">80% sure" floor and "Common False Positives" list are community practice ([ECC code-reviewer](https://github.com/affaan-m/everything-claude-code/blob/main/agents/code-reviewer.md)). Optionally run round one as `codex exec review -s workspace-write -o out.md "<prompt>" < /dev/null` to inherit the JSON rubric, mapping P0/P1 to must-fix and P2/P3 to a "mentioned, not fixed" tail; this is **[Verified]** to accept a custom prompt and `-o`, but the mapping is **[Inference]**, and `-i/--image` and `--worktree` are unavailable on `exec review`, so plain `codex exec` stays for design reviews.

6. **Add a refute step and a referee for disputed findings.** After the reviewer's list, run one more reviewer turn whose only job is to refute each finding by quoting the line that disproves it, and drop refuted items before the builder sees them; send findings the builder still disputes to a fresh third reviewer run (or the user) rather than marking them disputed on the builder's word alone. **[Inference]** from Anthropic's "fresh model try to refute the result" guidance ([best practices](https://code.claude.com/docs/en/best-practices)), Refute-or-Promote's 79% candidate kill rate ([arXiv 2604.19049](https://arxiv.org/abs/2604.19049)), sycophancy evidence that authors capitulate to pushback ([arXiv 2310.13548](https://arxiv.org/abs/2310.13548)), and the finding that "four of the five most frequently reported findings were false positives", so repetition is not confirmation ([braindetox](https://braindetox.kr/en/posts/ai_review_diminishing_returns.html)). Running the reviewer twice with shuffled file order and keeping the intersection is Bugbot's majority-vote trick at double cost **[Vendor claim]** ([Cursor blog](https://cursor.com/blog/building-bugbot)).

7. **Request structured output and a one-line verdict.** Ask both reviewers for `VERDICT: PASS|NEEDS_CHANGES` plus a tally (`2 must-fix, 3 below threshold`) at the top, and use `claude -p --output-format json --json-schema '{...}'` and `codex exec --output-schema schema.json` so `review-loop` parses `must_fix` mechanically and keeps sub-threshold findings visible in a summary without reopening noise. **[Verified]** flags ([headless](https://code.claude.com/docs/en/headless); [Codex non-interactive](https://learn.chatgpt.com/docs/non-interactive-mode)); the "below threshold still appears in the summary" pattern is Qodo's and Claude Code Review's ([Qodo](https://docs.qodo.ai/code-review/severity-thresholds.md); [code-review docs](https://code.claude.com/docs/en/code-review)); community bridges already do this with schema-validated JSON ([claude-codex-bridge](https://github.com/vasilievyakov/claude-codex-bridge)).

8. **Upgrade `decisions.md` into a findings ledger.** Record accepted findings too, with the round of origin and the fix that resolved them; give each finding an identity by behaviour and cause so a reworded re-raise matches; code dismissals as wrong / not worth fixing / already handled / style / duplicate so the final report does not count every rejection as reviewer error; write choices as `Ruling: <what> — <why> — <what it costs if wrong>`; ask the reviewer for a "Declined to judge" list of out-of-scope behaviours it set aside; and in rounds two and three pass the previous findings verbatim with their dispositions. **[Inference]** from practitioner ledgers ([quiet-solar #375](https://github.com/tmenguy/quiet-solar/issues/375); [recoder #72](https://github.com/aidan-neel/recoder/issues/72); [superpowers executing-plans](https://github.com/obra/superpowers/blob/main/skills/executing-plans/SKILL.md); [superpowers code-reviewer](https://github.com/obra/superpowers/blob/main/skills/requesting-code-review/code-reviewer.md)) and from fleet data that 44% of later findings land in code the previous fix changed and 8 of 91 were re-raised after reasoned declines ([MultiAgency #116](https://github.com/MultiAgency/near-agencies/issues/116)).

## Conclusion

The project is ahead of its peers on policy and behind on enforcement. Its must-fix-only brief, trend-based stop, diff budget and ledger anticipate what the strongest 2026 evidence and the surviving industrial deployments converged on, while the mechanics that carry those policies — a reviewer that could edit, an effort flag that lowers the user's default, a screenshot the model cannot read at full size — are the parts the harness vendors and the better community runners have already fixed with documented flags. The field's lesson, stated most bluntly in the reward-hacking literature, is prevent first and detect second; the project currently detects. Closing that gap costs a handful of flags and no change to the design.

The longer-term signal is that both vendors are absorbing single-model review into their own `review` commands and cloud verifiers, and the official Codex plugin for Claude Code has gone three months without a push. What those products cannot offer is the configuration the bias literature favours most: a reviewer from a different vendor, in a fresh process, bound by a shared ledger and a budget. That is the project's durable value, and it is also unmeasured — no study yet quantifies cross-vendor review on real repositories. Logging the loop turns the project from a consumer of this evidence into a source of it.
